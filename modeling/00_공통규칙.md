# 공통 규칙

영역을 진행하며 결정된 프로젝트 공통 사항을 누적한다.

## 확정
| 항목 | 내용 | 결정 시점 |
|---|---|---|
| DBMS | Oracle (Docker의 Oracle 26ai Free 기준). 최신 기능은 불필요하게 쓰지 않고 기본 Oracle SQL과 일반적인 모델링 기법 중심. 버전별 구현 차이는 중요할 때만 설명 | 준비 단계 |
| 명명 | 단수형 snake_case 물리명 + 한글 논리명 병기 | 준비 단계 |
| 용어 | 수업 자료「핵심 데이터 모델링」 용어 기본, 일반 용어 병기 | 준비 단계 |
| 진행 순서 | 고객 → 카테고리 → 상품 → 가격 → 장바구니 → 쿠폰 → 주문 → 결제 | 준비 단계 |
| 범위 | 영역 시작 시 필수/선택/추후 확장을 그때그때 결정 | 준비 단계 |
| 식별자 | 대리키 기본, 업무적으로 고유한 값은 UNIQUE. 단일 대리키 + 비식별 관계가 기본이며, 복합 PK·식별 관계(예: 1:1 종속 테이블의 PK=FK, M:N 교차 테이블)는 필요 시 예외로 검토 | 고객 |
| PK 표기 | `<테이블명>_id`, `NUMBER(19)`, `GENERATED AS IDENTITY` | 고객 |
| 공통 컬럼 | `created_at`, 변경이 일어나는 테이블에만 `updated_at`. 생성자·수정자 컬럼은 학습 범위에서 제외. 추가만 하는 이력 테이블은 업무 일시 컬럼이 `created_at`을 대신 | 고객 |
| 삭제 방식 | 논리 삭제를 일괄 적용하지 않고 엔티티별 요구사항으로 판단. 회원 탈퇴는 행 유지 + 개인정보 삭제·최소화 + 탈퇴 상태 관리 | 고객 |
| 데이터 타입 | 문자열 `VARCHAR2(n CHAR)`, 일시 `TIMESTAMP(6)`, 여부 값 `CHAR(1)` + `CHECK IN ('Y','N')` | 고객 |
| 값 집합 | 값만 제한하면 되는 상태·유형은 `CHECK`, 속성(이름, 서열 등)을 가지면 마스터 테이블 | 고객 |
| 제약 이름 | `pk_<테이블>`, `uq_<테이블>_<컬럼>`, `ck_<테이블>_<규칙>`. FK는 `fk_<자식>_<FK 컬럼>`으로 FK 컬럼명을 넣어 구분한다(같은 부모를 여러 번 참조해도 이름이 겹치지 않음. 예: `fk_member_grade_history_prev_grade_id`, `fk_member_grade_history_new_grade_id`). 복합 FK는 컬럼명을 `_`로 이어 쓴다(예: `fk_member_terms_agreement_terms_id_terms_type`). 식별자 길이 제한 안에서 필요하면 축약한다 | 고객 |
| FK 인덱스 | 생성 여부를 기본적으로 검토하되 모든 FK에 필수로 두지는 않는다. 조회 패턴, 부모 행의 변경·삭제와 잠금, 기존 인덱스와의 중복(복합 인덱스의 선두 컬럼 등)을 고려한다. 부모 행을 삭제하지 않는 설계에서는 ON DELETE 옵션을 지정하지 않는다 | 고객 |
| 비회원 주문 | 허용. 고객 영역에 비회원 엔티티를 만들지 않고, 주문자 정보는 주문 영역에서 스냅샷으로 보존 | 고객 |
