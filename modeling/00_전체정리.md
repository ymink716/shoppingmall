## 1. 전체 엔티티 지도

```
                      [등급]⏸                    [판매자]⏸   [브랜드]⏸
                        │                          │  │         │
[약관]─<[약관 동의]>─[고객]─<[배송지]                 │  └──<[상품]>─┘
                     │ ├─<[인증수단]              │      │ ├─<[옵션 그룹]─<[옵션 값]─<[실측 사이즈]
                     │ ├─<[수신동의]─<[수신동의 이력] │      │ ├─<[단품]─<[단품 옵션 구성]
                     │ ├──[체형정보] (1:1)          │      │ │    └─<[단품 재고 이력]
                     │ ├──[탈퇴] (1:1)              │      │ ├─<[이미지] ├─<[가격 이력] ├─<[상태 이력]
                     │ ├─<[상태 이력]               │      │ └─<[상품 속성값]>─[속성]─<[속성 선택값]
                     │ │                           │      │                    │
                     │ └─<[장바구니상품]>───────────────[단품]   [표준 카테고리]─<[카테고리 속성]
                     │                             │      │      (재귀)  └─<[전시 카테고리 구성]>─[전시 카테고리](재귀)
                     └─<[주문]─<[판매자 주문]>──────┘      │                                   └─<[전시 카테고리 상품]>─[상품]
                          │         │                     │
                          │         └─<[주문상품]>─────────┘
                          │         │      ├─<[주문상품 할인]>─[고객 쿠폰]⏸
                          │         │      └─<[주문상품 상태 이력]
                          │         ├─<[배송]─<[배송상품]>─[주문상품]
                          │         │     └─<[배송 추적 이력]
                          │         └─<[클레임]─<[클레임상품]>─[주문상품]  (교환단품 ○─[단품])
                          │               ├─<[클레임 상태 이력]
                          │               ├─<[클레임 환불]>─[결제]   클레임 환불 ─<[결제 거래](CANCEL, 복합 FK)
                          │               └─<[결제](클레임 비용), [배송](회수·재배송)  (선택 FK)
                          ├─<[주문 배송지 변경 이력]
                          └─<[결제]─┬─[카드 결제] / [가상계좌 결제] / [간편결제]  (상호배타 1:1)
                                    └─<[결제 거래]
⏸ = 아직 설계하지 않은 엔티티 (참조만 둠)
```

**큰 흐름으로 보면**
```
기준정보: 고객 · 카테고리 · 상품(단품)
   ↓ 고객이 단품을 담고
장바구니상품
   ↓ 주문하면 (주문 시점 값을 복사)
주문 → 판매자 주문 → 주문상품
   ↓ 돈을 내고              ↓ 물건을 보냄
결제 → 결제 거래        배송 → 배송상품, 추적 이력
   ↓ 되돌리거나 바꾸면 (판매자 주문 단위)
클레임 → 클레임상품(수량, 회수 금액), 클레임 환불(결제수단별) → 결제 거래(CANCEL)
                                   회수·교환 재배송 → 배송(RETURN·EXCHANGE)
```

## 2. 엔티티별 설계 방법 총정리

표기: ✅ 채택 / △ 일부·조건부 채택 / ❌ 채택 안 함 / ⏸ 다음 회차·보류 / — 해당 없음

### 2-1. 고객 (유형 10가지)
**핵심 질문**: 고객 정보를 테이블로 어떻게 나눌까?

| # | 유형 | 한 줄 정의 | 결과 | 이유 |
|---|---|---|---|---|
| 1 | 단일 테이블형 | 고객 정보를 한 테이블에 모두 | ❌ | 주소·로그인 수단이 여러 개면 반복 컬럼 |
| 2 | 자식 테이블 분리형 (1:N) | 여러 개인 정보를 자식 테이블로 | ✅ | 배송지, 수신동의 |
| 3 | 수직 분할형 (1:1) | 성격이 다른 컬럼을 1:1 테이블로 | △ | 체형정보만 (선택적 존재). 통계 분리는 물리 단계 |
| 4 | 인증수단 분리형 | 로그인 수단(이메일·카카오…)을 별도 테이블로 | ✅ | 한 고객이 여러 수단을 연동 |
| 5 | 회원/비회원형 | 비회원 주문자를 어디에 둘지 | — | 회원만 주문 |
| 6 | 슈퍼타입/서브타입형 | 개인·법인 등 유형별 속성 분리 | ❌ | 고객 유형이 하나 |
| 7 | 이력 관리형 | 상태·동의 변경을 이력으로 | ✅ | 상태 이력, 수신동의 이력 |
| 8 | 개인정보 분리형 (PII Vault, PPT 외) | 개인정보를 별도 저장소로 | △ | 암호화 + 해시 컬럼으로 대신 |
| 9 | 확장 속성형 (EAV/JSON) | 속성을 행이나 JSON으로 | ❌ | 고객 속성은 자주 늘지 않음 |
| 10 | 파티 패턴형 (PPT 외) | 사람·조직을 하나로, 역할을 분리 | ❌ | 고객과 판매자 계정을 분리하기로 함 |

**설계 기법 9가지** (어떤 유형이든 공통으로 정해야 하는 것)
| 기법 | 핵심 | 적용 |
|---|---|---|
| A. 인조 vs 본질 식별자 | 식별자 4요건(유일·최소·불변·존재)으로 판단 | 고객번호 채택, 이메일·휴대폰·CI 탈락 |
| B. 대체 식별자·조건부 유일·외부노출키 | 유일해야 하는 값은 AK로 | 닉네임, CI해시(탈퇴 안 한 고객 중 유일), 고객공개ID(UUID) |
| C. 식별 vs 비식별 관계 | 조합이 업무 규칙이고 자식이 없으면 식별 | 인증수단(식별), 배송지(비식별) |
| D. M:N 해소 | 관계에 속성이 있으면 교차 엔티티 | 약관 동의 |
| E. 파생 속성 판단 | "언제든 정확히 다시 계산할 수 있나?" | 연령 저장 안 함, 현재 등급은 저장 |
| F. 상태 코드 | 배타적 상태는 코드 하나로 | ACTIVE / SUSPENDED / WITHDRAWN |
| G. 탈퇴 처리 | 행은 남기고 개인정보만 파기 | 익명화 + 고객 탈퇴로 CI해시 이동 |
| H. 암호화 + 해시 검색 | 암호문은 검색 불가 → 해시 컬럼 | 휴대폰번호 + 휴대폰번호해시 |
| I. 공통 컬럼 | 테이블 마지막에 시스템 컬럼 4개 | created_by/at, updated_by/at |

### 2-2. 카테고리 (유형 13가지)
**핵심 질문**: 트리를 어떻게 저장할까? 상품은 몇 개 카테고리에 속할까? 관리 분류와 노출 분류가 같은가?

**계층 표현은 "무엇을 저장하느냐"로 나뉩니다**: 부모(2) / 경로(3, 4) / 범위(5, 6) / 모든 조상-자손 관계(7)

| # | 유형 | 저장하는 것 | 결과 | 이유 |
|---|---|---|---|---|
| 1 | 대중소 고정 단계형 | 단계별 엔티티 | ❌ | 카테고리마다 깊이가 다름 |
| 2 | **재귀적 관계형** | 부모 번호 | ✅ | 추가·이동이 쉽고 참조 무결성 보장. 수백 건이라 재귀 쿼리 부담 작음 |
| 3 | 계층 코드형 | 자릿수 코드 | △ | PK로 쓰면 이동 시 바뀜(불변성 위반) → 의미 없는 표시용 코드만 |
| 4 | 경로 저장형 (PPT 외) | "/1/3/12/" | ❌ | 이동 시 하위 전체 갱신 |
| 5 | 중첩 집합형 (PPT 외) | 좌우 번호 범위 | ❌ | 추가·이동이 매우 어려움 |
| 6 | 중첩 구간형 (PPT 외) | 실수 범위 | ❌ | 복잡도 대비 이득 없음 |
| 7 | 클로저 테이블형 (PPT 외) | 조상-자손 모든 쌍 | ❌ | 규모가 작아 불필요 |
| 8 | 혼합형 | 부모 + 깊이·경로 | ❌ | 깊이·경로는 파생 속성 → 물리 단계 역정규화 후보 |
| 9 | DBMS 전용 기능 | CONNECT BY 등 | △ | 조회 방법일 뿐, 모델은 2번 |
| 10 | 문서형 | 트리 JSON | ❌ | 캐시 용도 |
| 11 | 상품 연결 (a 단일 / b 다중 / c 다중 + 대표) | | ✅ 11-a | 여러 곳 노출은 12번이 담당 → 표준까지 다중이면 중복 해결 |
| 12 | **표준/전시 분리형** | 관리 트리 + 노출 트리 | ✅ | 매장 개편이 상품 분류를 흔들지 않음 |
| 13 | 카테고리 속성 정의형 | 카테고리별 입력 항목 | ⏸→✅ | 3회차 상품에서 "속성 체계 통합"으로 설계 |

> 판단 기준: **트리가 얼마나 자주 바뀌나** vs **하위·상위 조회가 얼마나 자주 일어나나**

### 2-3. 상품 (유형 20가지)
**핵심 질문**: 무엇이 상품이고 무엇이 재고 단위인가? 카테고리마다 다른 속성은? 가격·재고는?

|---|---|---|---|---|

| | 5 | 스타일-컬러-사이즈 3계층 | △ | 브랜드 생산 체계용. 실습은 3번으로 컬러별 상품 분리 운영 |

| | 9 | **속성 정의형 (EAV)** | ✅ | 필터·상품정보고시·실측을 **속성 하나로 통합** (속성유형코드) |
| | 10 | JSON 속성형 | ❌ | 검색·제약 불가 |
| C. 가격 | 11 | 가격 속성형 (현재 가격) | ✅ | |
| | 12 | **가격 이력형 (선분 이력)** | ✅ | 특정 시점 가격 조회. 최종 데이터 포함 |
| | 13 | 가격 정책 분리형 | ⏸ | 쿠폰·프로모션 회차 |
| D. 재고 | 14 | 단품 재고 속성형 + 변동 이력 | ✅ | 현재값 + 점 이력 |
| | 15 | 재고 엔티티 분리 (창고별) | ⏸ | 물류센터 1곳 가정 |
| E. 부가 정보 | 16 | 상품 이미지 (색상 연결) | ✅ | |

### 2-4. 장바구니·주문 (유형 22가지)
**핵심 질문**: 주문을 몇 단계로? 주문 당시 값을 어떻게 보존? 상태는 어디에? 할인은 어떻게 나눌까?

| 영역 | # | 유형 | 결과 | 이유 |

### 2-7. 설계 방법을 고를 때 반복해서 쓴 판단 기준
| 판단 기준 | 쓰인 곳 |
|---|---|
| 반복 그룹(1, 2, 3…)이 생기나? → 자식 엔티티로 | 고객 배송지, 주문상품, 결제, 배송 |
| 값이 **바뀌어야** 하나, **그때 값으로 남아야** 하나? | 장바구니(참조) vs 주문(스냅샷), 배송지 |

| 다시 계산할 수 있나? → 파생 속성 | 깊이·경로, 할인율, 품절, 금액 합계, 취소누계, 상품환불금액 |
| 계산할 수 있어도 **그 시점의 판단**이 들어가나? → 저장 | 판매자 주문 배송비, 클레임 할인회수·배송비 조정 금액 |
| 일부만 처리하는 경우가 있나? → 상세 단위로 상태 | 주문상품별 상태, 배송상품 수량 |
| 지금 필요한가? → 아니면 보류하고 넘긴 항목에 기록 | 창고, 세트 상품, 이벤트 원장, PG 원문 |

| 상호배타적 관계 | 결제 서브타입 (하나만). 반대 사례: 전시 카테고리 구성은 표준 연결과 상품 지정을 **둘 다 허용**해서 배타 아님 |
| 복합 FK | 주문상품·배송·클레임 → 판매자 주문 (주문번호, 판매자번호), 수신동의 이력 → 수신동의, **결제 거래 → 클레임 환불 (클레임번호, 결제번호)**: 거래의 결제 = 배분의 결제를 키가 보장 |

### 이력 관리 방법 (PPT)
| 이력 | 점 / 선분 | 최종 데이터 | 비고 |
|---|---|---|---|
| 상품 가격 이력 | **선분** | 포함 | 특정 시점 가격 조회 |
| 단품 재고 이력 | 점 | — | 변동후수량 포함 |
| 고객·상품·주문상품·클레임 상태 이력 | 점 | — | 이전·변경 상태 + 처리자 |
| 수신동의 이력 | 점 | — | 현재값은 수신동의 테이블 |
| 결제 거래 | 점 (원장) | — | 상태 이력을 대신함 |
| 배송 추적 이력 | 점 | — | 이벤트일시 ≠ 등록일시 |
| 주문 배송지 변경 이력 | 점 | **미포함** | 변경 전 값만 |

### 정규화
| 정규형 | 위반 사례 → 해결 |
|---|---|
| 1정규형 (원자성·반복 그룹) | "블랙 / M" → 단품 옵션 구성 / 상품1·상품2 → 주문상품 / 결제수단1·2 → 결제 / 배송지1·2 → 배송지 / 취소수량·반품수량 → 클레임상품 |
| 2정규형 (부분 종속) | 주문 1행 = 상품 1개면 주문자·배송지가 주문번호에만 종속 → 주문 헤더 분리 |
| 3정규형 (이행 종속) | 주문상품에 송장 정보 → 배송 분리 / 주문상품에 상품번호 → 단품으로 구함 / 상품에 카테고리명 → 번호만 |
| 정규화 위반이 **아닌** 것 | 주문 당시 판매가(스냅샷): 결정자가 주문상품이라 다른 속성 |

## 5. 여러 회차에 반복해서 나온 설계 패턴

| 패턴 | 형태 | 사례 |
|---|---|---|
| **현재값 + 이력** | 현재 값은 본 테이블, 변경은 이력 테이블 | 수신동의, 상품 가격, 단품 재고, 배송 상태 |
| **상태코드 + 상태 이력** | 상태코드 + (이전, 변경, 사유, 처리자구분, 처리자ID, 일시) | 고객, 상품, 주문상품, 클레임 |
| **처리자구분코드 + 처리자ID** | 관리자·판매자 테이블이 없어도 누가 했는지 기록 (FK 없음) | 모든 상태 이력, 배송지 변경 이력 |
| **스냅샷** | 그때 값을 복사, 원본 FK도 함께 | 주문자·배송지, 주문상품, 배송비 정책 |
| **인조 식별자의 대가** | 키를 짧게 만든 대신 "같은 부모에 속하나"를 업무 규칙으로 | 단품 옵션 구성의 그룹, 주문상품의 판매자, 배송상품·클레임상품의 판매자 주문 |
| **남은 수량 기준 상태** | 일부만 처리되면 상태를 바꾸지 않고, 전량일 때 바꿈 | 주문상품의 취소·반품·출고·배송완료 |
| **기본 행 하나** | 예외 경로를 없애려고 항상 1행을 둠 | 옵션 없는 상품의 기본 단품 |
| **업무 일시 ≠ 시스템 일시** | 업무 일시 컬럼을 시스템 컬럼과 따로 | 가입일시, 주문일시, 택배 이벤트일시 |
| **미래 확장용 코드** | 지금은 값 하나지만 다음 회차를 위해 코드를 둠 | 배송유형코드(ORDER) → 6회차에서 RETURN·EXCHANGE를 코드값만 추가 |
| **복합 FK로 같은 부모 보장** | 자식이 이미 가진 FK 컬럼을 다른 부모의 복합 FK에 함께 씀 | 결제 거래 (클레임번호, 결제번호) → 클레임 환불 |
| **계획과 실행 분리** | "얼마를 할지"(배분)와 "실제로 됐나"(원장)를 나눔 | 클레임 환불(배분) + 결제 거래(실행) |
| **안분과 비례 회수** | 나눌 때 마지막 행에 끝전, 되돌릴 때 마지막 수량에 잔액 | 4회차 할인 안분 ↔ 6회차 할인회수 |
| **1:M의 FK는 M 쪽에** | 재시도로 여러 행이 생기는 쪽에 FK | 클레임 비용 결제·회수 배송의 클레임번호 |

## 6. 키로 보장할 수 없는 업무 규칙 (유형별)

> 매 회차 "키 구조로 보장되지 않는 규칙"을 따로 적었습니다. 모아 보면 몇 가지 유형으로 나뉩니다.

| 유형 | 왜 키로 안 되나 | 사례 |
|---|---|---|
| **여러 행의 합계·개수** | 제약은 한 행 단위 | 기본 배송지 1개, 결제 합계 = 청구금액, 안분 합계 = 쿠폰액, 배송 수량 ≤ 주문 수량, 판매자 주문은 주문상품 1개 이상, 클레임 수량 ≤ 주문 수량, 클레임 환불 합계 = 환불총액 |
| **조건부 유일** | NULL·상태에 따라 유일 범위가 달라짐 | CI해시, 최상위 카테고리 이름, 송장번호, 결제수단별 유효 결제 1개, 주문상품당 진행 중 클레임 1개 |
| **조건부 필수** | 상태에 따라 필수 여부가 다름 | 탈퇴하지 않은 고객의 이름·휴대폰 |
| **같은 부모 소속 확인** | 인조 식별자로 경로가 끊김 | 단품 옵션 구성의 옵션 값 ↔ 그룹, 주문상품 판매자 = 단품의 판매자, 배송상품·클레임상품 ↔ 판매자 주문, 클레임 비용 결제의 주문 = 클레임의 주문 |
| **유형 일치** | FK는 행 존재만 확인 | 이미지 옵션 값은 COLOR, 실측은 SIZE + MEASURE, 결제수단코드 ↔ 서브타입 |
| **상호배타** | FK로 "하나만"을 표현 불가 | 결제 서브타입 |
| **계층·순환** | 재귀 관계의 깊이·순환 | 카테고리 4단계 이하, 자기 자손을 부모로 못 함, 최하위에만 상품 연결 |
| **상태 전이** | 순서는 값이 아니라 과정 | 주문상품 ORDERED → … → CONFIRMED, 헤더 PAID 전에는 진행 불가 |
| **중복 데이터 정합성** | 의도적 중복 | 현재 가격 = 가격 이력 현재 행, 재고수량 = 마지막 변동후수량 |
| **시점 조건** | 시간에 따라 허용이 다름 | 재가입가능일시, 출고 전에만 배송지 변경, 가상계좌 입금기한, 출고 전에만 취소·배송완료 후에만 반품, 환불 배분 확정 후 수정 금지 |
| **계산 규칙** | 값이 아니라 계산 방법 | 할인 안분 끝전, 비례 회수 끝전, 환불 순서(적립금 → 외부 결제 → 머니), 배송비 재계산, 환불총액 ≥ 0 |

## 7. 검토하면서 고친 것 (오답 노트)

> 추천안을 다시 검토하면서 고친 내용입니다. **처음 판단의 어디가 틀렸는지**를 보는 것이 공부에 가장 도움이 됩니다.

| 회차 | 처음 생각 | 문제 | 고친 결과 | 관련 개념 |
|---|---|---|---|---|
| 1 | 이름·휴대폰 등 NOT NULL | 탈퇴 익명화와 충돌 | NULL 허용 + 조건부 필수 | 실체 무결성 |
| 2 | 표준 카테고리 다중 소속 + 대표 | 전시 카테고리가 이미 다중 노출을 담당 | 단일 소속 | 같은 문제를 두 번 해결 (최소성) |
| 2 | 혼합형(깊이·경로 저장) | 파생 속성, 이동 시 갱신 이상 | 재귀적 관계만 | 파생 속성, 역정규화는 물리 단계 |
| 2 | 대체 식별자 (상위 + 이름) | 상위가 NULL인 최상위끼리는 못 막음 | 업무 규칙 + 조건부 유일 인덱스 | NULL과 유일 제약 |
| 3 | 카테고리 속성 단순 상속 | "상의는 선택, 긴소매만 필수" 표현 불가 | 상속 + 하위 재지정 우선 | |

## 9. 스스로 점검 문제 (답 포함)

> 답을 가리고 먼저 생각해 보세요. GitHub에서는 ▶를 누르면 답이 펼쳐집니다.

**식별자**
1. CI가 고객의 주 식별자가 되지 못한 이유는?
   <details><summary>답</summary>민감정보라 FK로 여기저기 퍼지면 안 되고, 탈퇴 후 재가입하면 같은 CI가 다시 생겨 충돌함. 탈퇴 시 파기되면 존재성도 깨짐 → 고객번호(인조) + CI해시(조건부 대체 식별자)</details>
2. 카테고리 계층 코드(예: 010203)를 PK로 쓰면 식별자 4요건 중 무엇을 어기나?
   <details><summary>답</summary>불변성. 카테고리를 옮기면 코드가 바뀌고 그 코드를 참조하는 상품·주문까지 바뀌어야 함</details>
3. 송장번호가 배송의 주 식별자도, 대체 식별자도 될 수 없는 이유는?
   <details><summary>답</summary>송장 등록 전에는 값이 없고(존재성), 택배사가 일정 기간 후 재사용함(유일성)</details>
4. 주문상품을 PPT 예시처럼 (주문번호 + 일련번호) 식별 관계로 두지 않은 이유와 그 대가는?
   <details><summary>답</summary>판매자 주문까지 상속하면 키가 3개 속성이 되고, 재고 이력·배송상품·클레임·리뷰가 모두 참조함(복합키 단순화). 대가: "주문상품의 판매자 = 단품의 판매자", "배송상품의 주문상품이 그 배송의 판매자 주문에 속함"을 키가 아닌 업무 규칙으로 관리</details>

**관계**
5. 인증수단은 식별 관계, 배송지는 비식별 관계인 이유는?
   <details><summary>답</summary>인증수단은 (고객 + 인증유형) 조합 자체가 "유형당 1개" 규칙이고 자식이 없음. 배송지는 독립적으로 추가·수정·삭제하고 같은 이름 규칙도 없음</details>
6. 단품 옵션 구성의 PK에 옵션값번호가 아니라 옵션그룹번호를 넣은 이유는?
   <details><summary>답</summary>(단품번호 + 옵션그룹번호)로 "단품당 그룹별 값은 1개"를 키가 보장하게 하려고</details>
7. 결제 서브타입과 전시 카테고리 구성 중 상호배타적 관계는 어느 것이고, 다른 하나는 왜 아닌가?
   <details><summary>답</summary>결제 서브타입이 상호배타(결제 하나는 카드·가상계좌·간편결제 중 하나). 전시 카테고리는 "상의 전체 + 추천 상품"처럼 표준 연결과 상품 직접 지정을 함께 쓰려고 둘 다 허용</details>

**속성·정규화**
8. 주문상품의 "주문 당시 판매가"는 3정규형 위반인가?
   <details><summary>답</summary>아님. 상품의 현재 판매가와 다른 속성이고 결정자가 주문상품. 상품 참조형으로 두면 가격 변경 시 지난 주문 금액이 바뀌는 문제가 생김</details>
9. 카테고리 깊이·경로, 할인율, 주문 금액 합계를 저장하지 않은 공통 이유는?
   <details><summary>답</summary>파생 속성이라 언제든 정확히 계산 가능. 저장하면 원본이 바뀔 때 갱신 이상. 성능이 필요하면 물리 단계에서 역정규화</details>
10. 그런데 상품 현재 가격과 단품 재고수량은 이력이 있는데도 저장했다. 왜이고, 대신 무엇이 필요한가?
    <details><summary>답</summary>조회가 매우 잦은 값이라 의도적 중복. 대신 "현재 가격 = 이력의 현재 행", "재고수량 = 마지막 변동후수량" 업무 규칙으로 정합성 관리</details>
11. 송장번호를 주문상품에 두면 어떤 정규형을 어기나?
    <details><summary>답</summary>3정규형. 택배사·배송상태가 주문상품이 아니라 송장번호에 종속(이행 종속)되고, 한 상자의 주문상품마다 반복됨</details>

**이력**
12. 가격 이력은 선분 이력, 재고 이력은 점 이력인 이유는?
    <details><summary>답</summary>가격은 "특정 시점에 얼마였나"(구간 조회)가 중요해 시작·종료일시를 둠. 재고는 "언제 무엇 때문에 얼마나 변했나"(사건)가 중요해 변동 시점만 기록</details>
13. 배송지 변경 이력에 현재 주소를 넣지 않은 이유는?
    <details><summary>답</summary>최종 데이터 미포함 방식. 현재 주소는 주문에만 두어 두 곳에 같은 값이 생기지 않게 함. 주소 변경은 드물어 이력 조회 부담도 작음</details>
14. 결제에는 상태 이력 테이블을 두지 않은 이유는?
    <details><summary>답</summary>결제 상태 변화는 곧 PG 거래 결과라, 거래 원장이 이미 같은 사건을 기록함. 상태 이력을 두면 같은 사건을 두 번 기록</details>

**업무**
15. 예시 주문(티셔츠 38,000 + 데님 59,000, 상품쿠폰 5,900, 장바구니쿠폰 3,000)에서 장바구니쿠폰의 티셔츠 몫은?
    <details><summary>답</summary>상품쿠폰을 뺀 금액 비율 38,000 : 53,100 → 3,000 × 38,000 / 91,100 = 1,251.37 → 1,251원 (끝전 1원은 데님)</details>
16. 장바구니는 참조형, 주문은 스냅샷인 이유는?
    <details><summary>답</summary>장바구니는 항상 현재 가격·재고를 보여 줘야 하고, 주문은 주문 당시 값이 바뀌면 안 됨</details>
17. 가상계좌는 왜 재고를 결제 완료가 아니라 계좌 발급 때 차감하나?
    <details><summary>답</summary>입금까지 며칠 걸릴 수 있어, 그사이 다른 고객이 사면 입금한 뒤 품절을 알게 됨. 대신 입금기한 만료 시 복구</details>
18. 적립금을 결제수단(POINT 결제 행)으로 두면서 주문상품에도 적립금 배분을 남긴 이유는?
    <details><summary>답</summary>결제 행은 "얼마를 냈나"(결제 합계 = 청구금액), 주문상품 배분은 "어느 상품에 썼나"(부분 취소 시 환불). 둘의 합계 일치는 업무 규칙</details>

**클레임**
19. 결제는 슈퍼/서브타입으로 나눴는데 클레임(취소·반품·교환)은 나누지 않은 이유는?
    <details><summary>답</summary>결제수단은 카드사·할부, 계좌번호처럼 고유 속성이 많지만, 클레임 유형별 고유 속성은 교환단품·검수결과 2개뿐이고 흐름·환불 계산이 같음. 클레임상품의 선택 컬럼으로 충분</details>
20. 환불 금액은 주문상품 스냅샷으로 계산할 수 있는데도 저장한 이유는? 상품환불금액은 왜 저장하지 않았나?
    <details><summary>답</summary>끝전(마지막 수량에 잔액)과 배송비 재부과·환불은 앞선 클레임에 따라 결과가 달라지는 "그 시점의 판단"이라 확정 값으로 남김. 판매가 × 수량은 언제 계산해도 같아 파생 속성</details>
21. 티셔츠 2개(장바구니쿠폰 배분 1,251)를 하나씩 두 번 취소하면 회수액은 각각 얼마이고, 왜 그렇게 하나?
    <details><summary>답</summary>floor(1,251 / 2) = 625, 마지막 수량은 잔액 1,251 − 625 = 626. 전부 취소하면 회수 합계가 배분액과 정확히 같아짐 (4회차 안분의 반대)</details>
22. 결제 거래가 클레임 환불을 클레임번호 단독 FK가 아니라 (클레임번호, 결제번호) 복합 FK로 참조하면 무엇이 보장되나?
    <details><summary>답</summary>취소 거래의 결제번호와 환불 배분의 결제번호가 같음. 결제 거래가 이미 가진 결제번호를 FK에 함께 써서 "같은 부모" 확인을 업무 규칙 대신 키에 맡김</details>
23. 교환 배송비 추가 결제의 FK를 클레임에 두지 않고 결제 쪽(claim_id)에 둔 이유와, 그 때문에 고쳐야 했던 5회차 규칙은?
    <details><summary>답</summary>실패 후 재시도로 결제가 여러 행이 될 수 있는 1:M이라 FK는 M 쪽에 둠. 그래서 "APPROVED 결제 합계 = 청구금액", "결제수단별 유효 결제 1개"를 클레임번호가 없는 주문 결제 기준으로 고침</details>
