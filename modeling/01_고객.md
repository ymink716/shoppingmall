# 01. 고객

고객 영역의 학습·설계 문서. 프로젝트 공통 규칙은 [00_공통규칙.md](00_공통규칙.md)를 따른다.

- ②는 기법 자체를 설명하고, ③은 우리 프로젝트의 선택과 근거를, ④는 그 결과인 테이블 설계를 담는다. 같은 내용을 반복하지 않도록 ③과 ④는 ②의 절 번호를 참조한다.
- `▲`는 아직 정해지지 않은 업무 규칙이나 가정이다.

## ① 영역 개요 및 요구사항

### 1.1 역할
고객 영역은 "누가 서비스를 이용하는가"를 다룬다. 회원의 식별과 로그인, 배송지, 등급, 약관 동의, 이용 기록을 관리한다. 주문·쿠폰·장바구니 등 이후 모든 영역이 회원을 참조하므로 설계의 기준점이 된다.

### 1.2 공개 기능과 프로젝트 가정
이메일·소셜 로그인, 회원 등급, 배송지 관리, 회원 탈퇴는 무신사를 비롯한 쇼핑몰에서 일반적으로 제공되는 기능이다. 다만 무신사의 제공 범위와 세부 정책, 내부 DB 구조는 확인하지 않았다. 아래 업무 규칙은 모두 **이 프로젝트가 정한 가정**이다.

### 1.3 범위
| 구분 | 내용 |
|---|---|
| 포함 | 회원, 이메일·복수 소셜 로그인, 회원 등급과 변경 이력, 배송지(기본 배송 요청사항 포함), 회원 탈퇴, 휴면(자체 정책), 약관 동의·고지 기록, 로그인 이력, 체형 정보, 닉네임 |
| 다른 영역 | 장바구니, 쿠폰, 찜, 적립금, 리뷰, 알림(마케팅 발송·수신 설정), 비회원의 주문자 정보(주문) |
| 확장 후보 | 본인인증, 이메일 인증·비밀번호 재설정, 실패 로그인 기록, 휴면 시 개인정보 분리 보관, 재가입 제한, 탈퇴 유예 |

### 1.4 확정한 업무 규칙
| 규칙 | 내용 |
|---|---|
| R1 로그인 수단 | 이메일과 여러 소셜 로그인을 지원하고, 한 회원이 복수의 로그인 수단을 연결할 수 있다. 같은 이메일이라는 이유만으로 소셜 계정을 자동 병합하지 않는다. |
| R2 비회원 주문 | 허용한다. 고객 영역에는 비회원 엔티티를 두지 않고 주문자 정보는 주문 영역에서 스냅샷으로 보존한다. |
| R3 회원 등급 | 등급을 사용한다. 회원의 현재 등급과 등급 변경 이력(점 이력)을 함께 관리하고, 둘의 변경은 한 트랜잭션으로 처리한다. |
| R4 배송지 | 회원은 배송지를 여러 개, 개수 제한 없이 등록한다. 배송지가 하나 이상이면 기본 배송지가 반드시 하나 있다. 삭제는 물리 삭제이고 복구·삭제 이력 조회는 제공하지 않는다. |
| R5 회원 탈퇴 | 즉시 처리한다. 처리가 끝나지 않은 거래가 있으면 탈퇴할 수 없다. 회원 행은 유지하고 개인정보를 삭제·최소화하며, 재가입은 새 회원으로 등록한다. |
| R6 식별자 | 대리키를 기본으로 한다([00_공통규칙.md](00_공통규칙.md)). |
| 추가 | 휴면 상태(자체 서비스 정책), 약관 3종(이용약관·개인정보 처리방침·마케팅 수신), 성공 로그인 이력, 선택 입력 체형 정보, 닉네임 |

## ② 주요 데이터 모델링 기법

### 2.1 식별자: 대리키와 자연키, 식별·비식별 관계
**해결하려는 문제**: 행 하나를 유일하게 가리킬 값(PK)을 무엇으로 할 것인가.

- **자연키**는 이메일처럼 업무에서 의미를 갖는 값이다. 값이 바뀌면 그 값을 FK로 복사해 가진 모든 테이블을 함께 고쳐야 한다. 예를 들어 이메일이 PK라면 주문 1,000건이 이메일을 들고 있고, 이메일을 바꿀 때마다 1,000건을 수정해야 한다.
- **대리키**는 업무적 의미가 없는 번호다. 변하지 않고 FK가 짧다. 대신 업무적으로 고유해야 하는 값(이메일 등)은 UNIQUE 제약으로 따로 보장해야 한다.

**식별 관계와 비식별 관계**: 부모의 PK를 자식 PK의 일부로 쓰면 식별 관계, 일반 컬럼으로만 가지면 비식별 관계다.

```
식별 관계:   address (member_id, address_seq)        ← PK가 복합키
비식별 관계: address (address_id) + member_id (FK)    ← PK는 단일 대리키
```

| 구분 | 장점 | 단점 |
|---|---|---|
| 식별 관계 | 어느 부모에 속하는지가 PK에 드러남. 1:1 종속 테이블, M:N 교차 테이블에 자연스러움 | 복합키 관리가 필요하고, 이 테이블을 참조하는 테이블의 FK도 복합키가 되어 참조 관계와 조인 조건이 복잡해짐 |
| 비식별 관계 | PK가 한 컬럼이라 참조가 단순함 | 소속 관계는 PK가 아니라 FK와 NOT NULL로 보장해야 함 |

### 2.2 UNIQUE 제약과 후보키
PK가 아니어도 유일해야 하는 값(후보키)은 UNIQUE로 보장한다. 알아둘 점은 다음과 같다.

- **복합 UNIQUE의 범위**: `UNIQUE (a, b)`는 `(a, b)` **조합**의 중복만 막는다. NULL 허용 여부, 값의 형식, 허용 값 목록은 NOT NULL·CHECK가 따로 필요하다.
- **Oracle의 특성**: 문자열 비교는 대소문자를 구분한다(`A@x.com`과 `a@x.com`은 다른 값). 단일 컬럼 UNIQUE는 NULL이 여러 개여도 허용한다. 빈 문자열은 NULL로 취급된다.
- **조건부 유일**: "조건에 맞는 행 중에서만 유일"은 함수 기반 UNIQUE 인덱스로 표현한다. 조건에 맞지 않는 행은 키가 NULL이 되어 제외된다.

```sql
-- 예: 회원당 'Y'인 행은 최대 1개
CREATE UNIQUE INDEX uq_example ON t (CASE WHEN flag = 'Y' THEN member_id END);
```

### 2.3 반복 속성 분리와 제1정규형(1NF)
**해결하려는 문제**: 한 회원에게 같은 종류의 값(로그인 수단)이 여러 개 붙을 수 있을 때, 이를 어떻게 표현하는가.

| 형태 | 1NF 관점 |
|---|---|
| 한 컬럼에 값을 묶어 저장 (`'KAKAO:1,NAVER:2'`) | 원자성 위반. 명백한 1NF 위반 |
| 같은 의미의 컬럼을 반복 (`kakao_id`, `naver_id`) | 교과서에서는 반복 그룹으로 1NF 위반 사례로 설명한다. 엄밀하게는 각 컬럼이 원자값이면 형식적으로 1NF를 만족하므로 "1NF 위반으로 흔히 설명되는 설계 결함"에 가깝다 |
| 소셜 연결을 하나로 제한 | 1NF 위반이 아니라 카디널리티를 1로 고정한 설계 |

반복 속성 분리는 1NF만을 위한 기법이 아니라 "회원 1 : 로그인 수단 N"이라는 **카디널리티를 구조에 반영**하는 기법이다. 반복 컬럼 방식은 개수에 상한이 생기고, 조회에 `OR`가 늘고, 구조적 NULL이 많아지며, UNIQUE도 컬럼마다 따로 걸어야 한다.

### 2.4 슈퍼타입-서브타입
회원/비회원처럼 공통 속성과 고유 속성이 갈리는 개체를 표현하는 기법이다. 구현은 세 가지다.

| 방식 | 구조 | 특징 |
|---|---|---|
| 통합 | 한 테이블 + 구분 컬럼 | 단순하지만 타입별 컬럼이 NULL이 되고 제약을 걸기 어렵다 |
| 분리 | 공통 테이블 + 서브타입 테이블 | 정확하지만 테이블과 조인이 늘어난다 |
| 모델링하지 않음 | 엔티티로 만들지 않음 | 지속적으로 관리할 대상이 아닐 때 |

**적용 여부 판단 기준**: 공통·고유 속성의 개수만 보지 않는다. (1) 독립적으로 식별하고 관리해야 하는가, (2) 타입별로 다른 업무 규칙이 있는가, (3) 다른 엔티티와 타입별로 다른 관계를 맺는가를 함께 본다.

### 2.5 이력 관리: 현재값, 점 이력, 선분 이력
**해결하려는 문제**: "지금 값"과 "과거에 어땠는가"를 모두 다뤄야 한다.

| 방식 | 구조 | 특징 |
|---|---|---|
| 현재값만 | 컬럼 하나 | 단순하지만 변경하면 과거가 사라진다 |
| 점 이력 | 변경 **사건**을 한 행씩 기록 (`changed_at`) | 행 추가만 하면 되고 사유·이전 값을 담기 쉽다. 시점 조회는 "그 시점 이전의 마지막 행"을 찾아야 한다 |
| 선분 이력 | 상태가 유지된 **기간**을 한 행으로 기록 (`start`~`end`) | 시점 조회가 쉽다. 변경할 때 이전 행의 종료 시점을 닫아야 하고, 기간 겹침과 "현재 행 1건"을 제약으로 관리해야 한다 |

**점 이력으로도 과거 특정 시점의 값을 조회할 수 있다.** 시점 이전의 마지막 변경 행이 그 시점의 값이다.

```sql
-- 회원 :id의 :t 시점 등급 (같은 시각이면 PK가 큰 행을 최신으로 본다)
SELECT new_grade_id
  FROM member_grade_history
 WHERE member_id = :id AND changed_at <= :t
 ORDER BY changed_at DESC, member_grade_history_id DESC
 FETCH FIRST 1 ROW ONLY;
```
단, 최초 값도 이력으로 기록해야 첫 변경 이전 시점을 조회할 수 있다.

**현재값 + 이력을 함께 둘 때의 정합성**: 현재값 컬럼과 이력이 서로 어긋날 수 있다. (1) 둘의 변경을 한 트랜잭션으로 묶고, (2) "현재 값 = 최신 이력의 새 값"인지 점검하는 쿼리를 둔다. 선분 이력만 단독으로 쓰면 원천이 하나라 이 문제는 없지만 기간 제약 부담이 있다. Oracle에는 기간 겹침을 막는 제약이 없어서 애플리케이션이나 트리거로 보완한다.

### 2.6 코드 테이블과 CHECK 제약
상태나 유형처럼 값 집합이 정해진 컬럼을 어떻게 제한할 것인가. Oracle에는 ENUM이 없다.

| 방식 | 적합한 경우 | 한계 |
|---|---|---|
| CHECK (`IN (...)`) | 값만 제한하면 되고 추가가 드물 때 | 값에 속성(이름, 서열)을 붙일 수 없고, 값 추가는 제약 수정이 필요 |
| 코드(마스터) 테이블 | 값마다 속성이 있거나 값이 자주 추가될 때 | 테이블과 FK가 늘어남 |

### 2.7 "기본 1개" 제약
회원당 여러 행 중 기본 하나를 표시하는 방법이다.

| 방식 | 구조 | 특징 |
|---|---|---|
| A. 행에 표시 | 배송지의 `default_yn` + 함수 기반 UNIQUE 인덱스 | 순환 참조가 없고, 기본이 같은 행의 `member_id`와 묶여 **소유자 일치가 자동으로 보장**된다. 기본 변경 시 행 2개를 갱신한다 |
| B. 부모가 참조 | `member.default_address_id` FK | 기본 1개가 구조로 보장되나 회원↔배송지 **순환 참조**가 생기고, 다른 회원의 배송지를 지정하지 못하게 하려면 복합 FK 같은 추가 장치가 필요하다 |
| C. 전용 테이블 | `member_default_address(member_id PK, address_id)` | 순환은 없으나 테이블이 늘고 소유자 일치 보장에 추가 장치가 필요하다 |

**"최대 1개"와 "정확히 1개"는 다르다.** 세 방식 모두 선언적 제약으로 보장하는 것은 "최대 1개"다. "배송지가 있으면 반드시 1개"는 선언적 제약으로 표현하기 어려워 애플리케이션 규칙(첫 배송지 자동 기본, 기본 삭제 시 승계)으로 지킨다.

### 2.8 삭제 방식: 물리 삭제, 논리 삭제, 개인정보 삭제·최소화
**해결하려는 문제**: 행을 지우면 참조가 끊기고, 지우지 않으면 개인정보가 남는다.

| 방식 | 하는 일 | 적합한 경우 | 비용 |
|---|---|---|---|
| 물리 삭제 | `DELETE`로 행 제거 | 보관 가치가 없고 참조가 없거나 끊겨도 되는 데이터, 파기 대상 개인정보 | 복구 불가. 참조하는 행이 있으면 삭제가 거부된다 |
| 논리 삭제 | "삭제됨" 표시만 | 참조를 유지해야 하거나 복구·이력이 필요한 데이터 | 모든 조회에 제외 조건이 필요하고, 삭제 행이 쌓이며, UNIQUE 제약과 충돌할 수 있다. 개인정보는 DB에 남는다 |
| 개인정보 삭제·최소화 | 행은 유지하고 개인정보 컬럼만 지움(NULL) + 상태 변경 | 참조를 유지하면서 개인정보를 줄여야 하는 데이터 | 개인정보 컬럼이 NULL을 허용해야 해서, 조건부 필수는 CHECK로 보강해야 한다 |

- **다른 테이블이 참조한다고 해서 반드시 논리 삭제가 필요한 것은 아니다.** 참조를 해제(`ON DELETE SET NULL`)하거나 필요한 값을 참조하는 쪽에 복사해 두면(2.10) 물리 삭제할 수 있다.
- **용어 구분**: 익명화는 어떤 방법으로도 개인을 다시 알아볼 수 없는 상태, 가명처리는 추가 정보와 결합해야만 알아볼 수 있는 상태(통계·연구 등 특정 목적과 추가 정보 분리 관리가 전제)다. 회원 행을 유지하면 `member_id`로 주문 등과 연결할 수 있으므로 이 방식은 익명화도 가명처리도 아니다. 그래서 **"개인정보 삭제·최소화 + 탈퇴 상태 관리"**라고 부른다.

### 2.9 NULL 설계
NULL은 "값 없음", "해당 없음", "아직 입력 안 함"이 섞일 수 있어 의미를 정해두어야 한다.

- **구조적 NULL**: 어떤 행에서는 항상 NULL인 컬럼(소셜 로그인 행의 비밀번호). 많아지면 테이블 분리를 고려한다.
- **조건부 필수**: 상태에 따라 필수 여부가 달라지면 NULL 허용 + CHECK로 표현한다(예: 탈퇴 회원만 이름이 NULL 가능).
- Oracle은 빈 문자열을 NULL로 취급하므로 NOT NULL·CHECK가 빈 문자열도 함께 막는다.

### 2.10 스냅샷과 비정규화
같은 값을 중복 저장하는 두 경우는 목적이 다르다.

| 구분 | 목적 | 예 |
|---|---|---|
| 스냅샷(의도적 복사) | 시점의 **사실**을 보존. 원본이 바뀌어도 과거 기록은 그대로여야 함 | 주문 시점의 배송지, 로그인 이력의 로그인 수단 |
| 파생값 저장(비정규화) | 계산하기 비싼 값을 미리 저장해 **조회를 단순화** | 마지막 로그인 일시 |

스냅샷은 복사한 뒤 원본과 관계를 끊는 것이 핵심이다. 파생값은 원본이 바뀔 때 함께 갱신해야 하므로 정합성 관리(같은 트랜잭션)가 필요하다.

### 2.11 1:1 수직 분할
선택 항목이 많고 대부분 비어 있거나 성격이 다른 컬럼을 별도 테이블로 분리한다. 부모의 PK를 그대로 PK로 쓰면(PK = FK) 1:1이 구조로 보장되고 별도 대리키가 필요 없다. 분리한 행의 존재가 "입력했음"을 뜻하게 되고, 삭제도 한 행으로 끝난다.

## ③ 설계 대안 비교 및 선택

### 3.1 식별자 (R6)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 대리키 + 업무 고유 값 UNIQUE, 단일 대리키·비식별 관계가 기본 | 회원에게는 PK로 쓸 자연키가 없다. 이메일은 복수 로그인 수단 중 하나, 연락처는 변경 가능, 탈퇴 시 개인정보를 지우므로 개인정보는 PK가 될 수 없다 | 자연키 PK. 식별 관계는 **원칙이 아니라 기본값에 대한 예외**로 필요할 때 쓴다(체형 정보에 적용, 3.7) |

### 3.2 로그인 수단 (R1)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 회원 1 : N 인증수단, 이메일도 로그인 수단의 한 종류로 통일 (2.3) | 여러 로그인 수단을 하나의 구조와 하나의 UNIQUE 제약으로 관리한다. 구조적 NULL이 `password_hash` 한 컬럼으로 준다 | 이메일만(확장성 없음), 회원 테이블에 소셜 1개(확장성 없음, NULL 많음), 이메일은 회원·소셜만 별도 테이블(조회와 중복 방지 로직이 두 갈래) |

**정책**: 소셜 로그인은 `(provider_type, provider_user_id)`로만 식별한다. 소셜이 알려준 이메일이 기존 회원과 같아도 연결 키로 쓰지 않으며(자동 병합 금지), 소셜 제공자의 이메일이 항상 검증된 것은 아니기 때문에 UNIQUE로도 두지 않는다. 계정 연결의 세부 정책은 미결정이다(5.4).

### 3.3 비회원 주문 (R2)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 허용하되 비회원 엔티티는 만들지 않음. 주문자 정보는 주문 영역에서 스냅샷으로 보존 | 비회원은 계정·등급 등 지속적으로 관리할 정보가 없다. 슈퍼/서브타입의 판단 기준(2.4) 중 독립적 식별·관리 필요성, 타입별 업무 규칙, 타입별 관계가 모두 약하다 | 통합(회원 테이블에 비회원 행이 쌓이고 NULL 컬럼 발생), 분리(테이블과 조인만 늘어나는 과설계), 비허용 |

비회원 주문 조회 인증 방식과 주문자 정보 저장 구조는 주문 영역에서 정한다.

### 3.4 회원 등급 (R3)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 등급 마스터 + 회원의 현재 등급 + **점 이력** (2.5, 2.6) | 구매 실적에 따라 정기적으로 승급·강등될 수 있고, 고객 문의·운영 시 **언제, 왜** 바뀌었는지 확인해야 한다. 등급이 유지된 기간 자체를 관리하는 것보다 변경 시점·사유 추적이 중요하다. 등급은 이름·서열 같은 속성을 가지므로 CHECK가 아니라 마스터 테이블이다 | **선분 이력**: 기간 중복 방지, 기존 이력의 종료 시점 갱신 같은 관리 부담에 비해 이번 요구사항의 이점이 작다. 선분 이력은 가격 영역에서 적용 가능성을 검토한다. 현재값만: 과거가 사라짐. 이력만(현재 등급 컬럼 없음): 현재 등급을 매번 이력에서 찾아야 함 |

- 과거 시점의 등급은 점 이력으로도 조회할 수 있다(2.5). 이를 위해 가입 시 최초 등급도 이력으로 기록한다.
- 현재 등급과 이력의 정합성은 한 트랜잭션 처리와 점검 쿼리로 관리한다(2.5).
- 주문 당시 혜택은 주문에 적용 결과를 스냅샷으로 남기는 방향이며 주문 영역에서 확정한다.

### 3.5 배송지 (R4)
| 항목 | 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|---|
| 기본 1개 | A. `default_yn` + 함수 기반 UNIQUE 인덱스 | 순환 참조가 없고 소유자 일치가 자동 보장된다 (2.7) | B(순환 참조·복합 FK 부담), C(테이블 추가) |
| 개수 | 제한 없음 | 현재 요구사항에 제한이 없다 | 슬롯 구조 등 구조적 강제 |
| 기본 필수 | 하나 이상이면 정확히 1개: 첫 배송지 자동 기본, 기본 삭제 시 남은 배송지 중 하나 승계 (애플리케이션 규칙) | UNIQUE 인덱스는 "최대 1개"만 보장한다 (2.7) | 기본이 없는 상태 허용 |
| 삭제 | 물리 삭제. 복구·삭제 이력 조회는 미포함 | 배송지는 회원이 직접 관리하는 주소록이며 삭제 후 보존·복구 요구가 없다. 주문은 배송지를 참조하지 않고 값을 복사하므로(2.10) 삭제해도 과거 주문이 영향을 받지 않는다 | 논리 삭제: 복구 요구가 없고, 선택하면 기본 배송지 인덱스와 개수 계산에서 삭제 행을 따로 처리해야 한다 |

주소록(현재 유효한 값, 수정 가능)과 주문 배송정보(그 거래의 사실, 변경 불가)는 성격이 달라 분리한다. 개인정보 파기와 거래 기록 보존의 기준도 서로 다르게 적용할 수 있다. 주문 테이블 구조와 참조 여부는 주문 영역에서 확정한다.

### 3.6 회원 탈퇴 (R5)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| **회원 행 유지 + 개인정보 삭제·최소화 + 탈퇴 상태 관리** (2.8) | ① 후속 영역(주문·결제·쿠폰)의 회원 참조 구조를 미리 제약하지 않는다. ② 비회원 주문(회원 없음)과 탈퇴 회원 주문을 상태로 구분할 수 있다. ③ 구현 부담이 작다 | **회원 행 삭제 + 거래 기록만 보존**: 개인정보 최소화에는 더 강하지만 주문·결제·쿠폰의 회원 FK가 모두 "회원 없음"을 표현해야 한다. **별도 보관소 이동**: 설계와 운영이 복잡하다. **논리 삭제**: 개인정보가 DB에 남고 재가입 시 UNIQUE 충돌을 처리해야 한다 |

- **회원 행 보존이 필수인 것은 아니다.** 주문이 회원을 참조한다는 이유만으로 정해진 것이 아니라 위 세 가지 근거로 선택했다.
- 비용: `member_id`로 한 사람의 거래를 묶어 볼 수 있다. 이 연결의 목적은 **법정 보존 기록의 관리와 분쟁 대응**으로 한정하고, 보존 기간이 지나면 회원 행과 연결된 기록을 함께 파기한다(기간·방법은 거래 기록 영역). 거래 기록 설계에서 개인 단위 연결이 필요 없다고 판단되면 회원 행 삭제 방식으로 전환할 수 있다.
- **진행 중 거래가 있으면 탈퇴를 차단한다.** 탈퇴하면 로그인 수단이 삭제되어 회원이 거래를 직접 처리할 수단이 사라지기 때문이다. 진행 중 상태의 정의, 구매확정 후 반품 가능 기간의 포함 여부, 검사와 신규 주문의 경합 처리는 주문 영역에서 정한다. 대안인 탈퇴 유예는 중간 상태와 자동 처리가 필요해 채택하지 않았다.
- **즉시 탈퇴**로 처리한다. 재가입은 새 회원으로 등록한다(인증수단을 삭제하므로 UNIQUE 충돌이 없다).
- 등급 변경 이력은 `member_id`로 다른 데이터와 결합되므로 개인정보에 해당할 수 있고 보존할 업무 목적이 없어 삭제한다.

### 3.7 범위 확장 항목
| 항목 | 선택 | 근거 |
|---|---|---|
| 휴면(`DORMANT`) | 이번 쇼핑몰의 **자체 서비스 정책**으로 정의(법적 의무로 운영하는 것이 아님). 상태 변경 + 로그인 시 해제, 개인정보는 유지 | 학습 목적. 개인정보 분리 보관은 확장 후보. 휴면 판정은 `last_login_at`만으로 가능해 **로그인 이력과는 별개 기능**이다 |
| 마지막 로그인 | `member.last_login_at`에 저장(파생값, 2.10) | 휴면 판정은 전 회원의 마지막 이용일을 대량 조회하는 작업이라 이력 전체를 훑는 비용이 크고, 이력 보관 기간이 휴면 기준보다 짧아지면 계산할 수 없다. 로그인 처리 트랜잭션에서 이력 추가와 함께 갱신한다 |
| 로그인 이력 | 성공 로그인만, IP 포함. 로그인 수단은 `member_auth` FK가 아니라 **복사한 값(스냅샷)** | 시간·수단만 기록하면 `last_login_at`과 중복되어 존재 이유가 약해진다. 보안 점검 목적에 IP가 필요하다. 인증수단은 연결 해제 시 물리 삭제되지만 이력은 사실로 남아야 한다 |
| 약관·동의 | `terms`(약관 종류·버전) + `member_terms_agreement`(회원의 동의·고지 확인 기록, **선분 이력**) | 동의는 상태가 기간 동안 유지되고 "지금 동의 중인가"와 "그 시점에 동의했는가"가 모두 중요하다 |
| 약관 3종의 성격 | `SERVICE`(계약, 필수 동의, 철회=탈퇴) / `PRIVACY_NOTICE`(동의가 아닌 고지, 고지 확인 기록) / `MARKETING_*`(선택 동의, 채널별, 철회 가능·이력 중요) | 모든 항목을 같은 동의로 다루지 않는다. 필수 여부는 약관 유형에서 결정되는 파생 속성이라 `required_yn`은 두지 않는다 |
| 동의 기록의 유일성 | 기록에 `terms_type`을 복사하고 `(terms_id, terms_type)` **복합 FK**로 정합성을 보장한다. **같은 유형의 현재 유효한 기록은 회원당 1건**이다. 새 버전에 동의하면 이전 기록을 `REPLACED`로 종료하고 새 기록을 추가한다. 철회는 `WITHDRAWN`으로 종료한다. **현재 동의 상태 = 해당 유형에 종료되지 않은 기록이 있는가** | `terms_id`는 버전별 행이라, `(member_id, terms_id)`로만 제한하면 같은 유형의 v1과 v2에 대한 동의가 동시에 유효해질 수 있다 |
| 탈퇴 시 동의 이력 | 삭제 | 이용약관 동의는 주문·결제 기록이 거래 사실을 이미 증명하고, 법령상 보존 의무는 확인되지 않았다. 처리방침 고지는 증빙 필요성이 약하고, 마케팅 동의는 탈퇴 후 발송이 끝난다. 법령상 보존 대상으로 확인되면 변경을 검토한다 |
| 마케팅 수신 | **동의**는 고객 영역의 약관·동의 모델(채널별 유형), **알림 발송·수신 설정**은 별도 알림 영역(확장) | 동의 사실과 철회 이력은 고객의 법적 기록이고, 알림 영역은 이 동의를 참조해 발송한다 |
| 체형 정보 | `member_body_profile`로 1:1 분리, `member_id`가 PK이자 FK (2.11) | 선택 항목이라 대부분 비어 있을 수 있고 탈퇴 시 한 행 삭제로 끝난다. 1:1이 구조로 보장된다. **R6 기본 규칙의 첫 예외**다 |
| 닉네임 | `member.nickname` 추가, UNIQUE | 표시 이름을 다른 회원과 구분하기 위해. 탈퇴 시 NULL로 지워 재사용할 수 있다 |
| 배송 요청사항 | `address.delivery_memo`(자주 쓰는 기본값). 실제 주문 시점의 요청사항은 주문 영역에 저장 | 요청사항은 배송지의 고유 속성이다. 주문 시점 값은 스냅샷으로 복사된다(2.10) |

## ④ 실제 테이블 설계

### 4.1 엔티티 개요
| 테이블 | 논리명 | 역할 | 근거 |
|---|---|---|---|
| member | 회원 | 회원 기본 정보, 상태, 현재 등급 | 3.4, 3.6 |
| member_auth | 인증수단 | 이메일·소셜 로그인 수단 | 3.2 |
| grade | 등급 | 등급 마스터 | 3.4 |
| member_grade_history | 회원 등급 변경 이력 | 등급 변경 점 이력 | 3.4 |
| address | 배송지 | 회원의 주소록 | 3.5 |
| terms | 약관 | 약관 유형·버전 마스터 | 3.7 |
| member_terms_agreement | 회원 약관 동의·고지 확인 기록 | 동의·고지 확인의 선분 이력 | 3.7 |
| member_login_history | 회원 로그인 이력 | 성공 로그인 기록 | 3.7 |
| member_body_profile | 회원 체형 정보 | 선택 입력 체형 | 3.7 |

공통 표기: 모든 대리키는 `NUMBER(19)`, `GENERATED AS IDENTITY`, 시각은 `TIMESTAMP(6)`, 문자열은 글자 단위(`CHAR`) 길이다. NN은 NOT NULL이다.

### 4.2 테이블 정의

#### grade (등급)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| grade_id | 등급 ID | NUMBER(19) | PK |
| grade_code | 등급 코드 | VARCHAR2(20) | NN, UNIQUE |
| grade_name | 등급명 | VARCHAR2(50 CHAR) | NN |
| grade_order | 등급 서열 | NUMBER(3) | NN, UNIQUE |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

#### member (회원)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_id | 회원 ID | NUMBER(19) | PK |
| grade_id | 현재 등급 ID | NUMBER(19) | FK → grade, NULL 허용 |
| name | 이름 | VARCHAR2(100 CHAR) | NULL 허용 |
| nickname | 닉네임 | VARCHAR2(30 CHAR) | NULL 허용, UNIQUE |
| phone | 연락처 | VARCHAR2(20 CHAR) | NULL 허용 ▲ 가입 필수 여부 |
| status | 회원 상태 | VARCHAR2(20) | NN, 기본 `'ACTIVE'` |
| last_login_at | 마지막 로그인 일시 | TIMESTAMP(6) | NULL 허용 |
| dormant_at | 휴면 전환 일시 | TIMESTAMP(6) | NULL 허용 |
| withdrawn_at | 탈퇴 일시 | TIMESTAMP(6) | NULL 허용 |
| created_at | 가입(생성) 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- CHECK: `status IN ('ACTIVE','DORMANT','WITHDRAWN')`
- CHECK(상태와 일시의 일관성): `(status='ACTIVE' AND dormant_at IS NULL AND withdrawn_at IS NULL) OR (status='DORMANT' AND dormant_at IS NOT NULL AND withdrawn_at IS NULL) OR (status='WITHDRAWN' AND withdrawn_at IS NOT NULL)`
- CHECK(조건부 필수): `status='WITHDRAWN' OR (name IS NOT NULL AND grade_id IS NOT NULL)` (2.9)

#### member_auth (인증수단)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_auth_id | 인증수단 ID | NUMBER(19) | PK |
| member_id | 회원 ID | NUMBER(19) | NN, FK → member |
| provider_type | 인증 제공자 유형 | VARCHAR2(20) | NN |
| provider_user_id | 제공자 사용자 식별값 | VARCHAR2(255 CHAR) | NN (EMAIL이면 이메일, 소셜이면 제공자 고유 ID) |
| password_hash | 비밀번호 해시 | VARCHAR2(255) | NULL 허용 (EMAIL만 값 있음) |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- UNIQUE `(provider_type, provider_user_id)`: 같은 외부 계정은 하나의 회원에만 연결된다. 이 제약이 막지 못하는 것은 아래 CHECK와 NOT NULL, 그리고 미결정 정책(제공자당 1개 제한)이다.
- CHECK: `provider_type`은 `EMAIL`과 지원 소셜 제공자 목록 ▲
- CHECK: `(provider_type='EMAIL' AND password_hash IS NOT NULL) OR (provider_type<>'EMAIL' AND password_hash IS NULL)`
- CHECK(이메일 정규화): `provider_type<>'EMAIL' OR provider_user_id = LOWER(provider_user_id)`. 입력 시 소문자로 변환하는 것은 애플리케이션 규칙이다.
- `UNIQUE (member_id, provider_type)`은 걸지 않는다 ▲

#### member_grade_history (회원 등급 변경 이력)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_grade_history_id | 이력 ID | NUMBER(19) | PK |
| member_id | 회원 ID | NUMBER(19) | NN, FK → member |
| prev_grade_id | 이전 등급 ID | NUMBER(19) | FK → grade, NULL 허용 (최초 부여는 NULL) |
| new_grade_id | 변경 후 등급 ID | NUMBER(19) | NN, FK → grade |
| changed_at | 변경 일시 | TIMESTAMP(6) | NN |
| reason_type | 변경 사유 유형 | VARCHAR2(30) | NN ▲ 값 목록 |
| reason_note | 사유 메모 | VARCHAR2(500 CHAR) | NULL 허용 |

- CHECK: `prev_grade_id IS NULL OR prev_grade_id <> new_grade_id`
- 행 추가만 하는 테이블이라 `updated_at`이 없고, `changed_at`이 `created_at`을 대신한다.

#### address (배송지)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| address_id | 배송지 ID | NUMBER(19) | PK |
| member_id | 회원 ID | NUMBER(19) | NN, FK → member |
| address_name | 배송지명 | VARCHAR2(50 CHAR) | NULL 허용 |
| recipient_name | 수령인 | VARCHAR2(100 CHAR) | NN |
| recipient_phone | 수령인 연락처 | VARCHAR2(20 CHAR) | NN |
| zip_code | 우편번호 | VARCHAR2(10) | NN |
| address_base | 기본주소 | VARCHAR2(300 CHAR) | NN |
| address_detail | 상세주소 | VARCHAR2(300 CHAR) | NULL 허용 |
| delivery_memo | 기본 배송 요청사항 | VARCHAR2(200 CHAR) | NULL 허용 |
| default_yn | 기본 배송지 여부 | CHAR(1) | NN, 기본 `'N'` |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- CHECK: `default_yn IN ('Y','N')`
- 함수 기반 UNIQUE 인덱스: `(CASE WHEN default_yn='Y' THEN member_id END)` — 회원당 기본 배송지 **최대 1개**. "있으면 정확히 1개"는 애플리케이션 규칙이다(2.7).

#### terms (약관)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| terms_id | 약관 ID | NUMBER(19) | PK |
| terms_type | 약관 유형 | VARCHAR2(30) | NN |
| terms_version | 약관 버전 | VARCHAR2(20) | NN |
| title | 제목 | VARCHAR2(200 CHAR) | NN |
| content | 본문 | CLOB | NN ▲ 저장 방식 |
| effective_at | 시행 일시 | TIMESTAMP(6) | NN |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |

- CHECK: `terms_type IN ('SERVICE','PRIVACY_NOTICE','MARKETING_EMAIL','MARKETING_SMS','MARKETING_PUSH')` ▲ 초기 목록
- UNIQUE `(terms_type, terms_version)`
- UNIQUE `(terms_id, terms_type)` — `member_terms_agreement`의 복합 FK 참조 대상
- 약관은 수정하지 않고 새 버전을 추가하므로 `updated_at`이 없다.

#### member_terms_agreement (회원 약관 동의·고지 확인 기록)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_terms_agreement_id | 기록 ID | NUMBER(19) | PK |
| member_id | 회원 ID | NUMBER(19) | NN, FK → member |
| terms_id | 약관 ID | NUMBER(19) | NN |
| terms_type | 약관 유형 | VARCHAR2(30) | NN (terms에서 복사) |
| agreed_at | 동의(고지 확인) 일시 | TIMESTAMP(6) | NN |
| ended_at | 종료 일시 | TIMESTAMP(6) | NULL 허용 (NULL이면 현재 유효) |
| end_reason | 종료 사유 | VARCHAR2(20) | NULL 허용 |

- 복합 FK `(terms_id, terms_type)` → `terms (terms_id, terms_type)`
- 함수 기반 UNIQUE 인덱스: `(CASE WHEN ended_at IS NULL THEN member_id END, CASE WHEN ended_at IS NULL THEN terms_type END)` — 같은 유형의 현재 유효한 기록은 회원당 1건
- CHECK: `end_reason IN ('WITHDRAWN','REPLACED')`
- CHECK: `(ended_at IS NULL AND end_reason IS NULL) OR (ended_at IS NOT NULL AND end_reason IS NOT NULL)`
- CHECK: `ended_at IS NULL OR ended_at >= agreed_at`
- 종료 시 바뀌는 컬럼이 `ended_at`, `end_reason`뿐이라 `updated_at`이 없다.
- `PRIVACY_NOTICE`의 기록은 동의가 아니라 고지 확인이며, 철회(`WITHDRAWN`)는 `MARKETING_*`에만 쓴다(애플리케이션 규칙).

#### member_login_history (회원 로그인 이력)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_login_history_id | 이력 ID | NUMBER(19) | PK |
| member_id | 회원 ID | NUMBER(19) | NN, FK → member |
| provider_type | 로그인 수단 | VARCHAR2(20) | NN (복사한 값, FK 아님) |
| logged_in_at | 로그인 일시 | TIMESTAMP(6) | NN |
| ip_address | IP 주소 | VARCHAR2(45) | NULL 허용 |

- 행 추가만 하는 테이블이라 `updated_at`이 없고, `logged_in_at`이 `created_at`을 대신한다.
- 복사한 `provider_type`에는 CHECK를 걸지 않는다(허용 값은 `member_auth`에서 검증).

#### member_body_profile (회원 체형 정보)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| member_id | 회원 ID | NUMBER(19) | PK, FK → member |
| height_cm | 키(cm) | NUMBER(4,1) | NULL 허용 |
| weight_kg | 몸무게(kg) | NUMBER(4,1) | NULL 허용 |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- CHECK: `height_cm IS NOT NULL OR weight_kg IS NOT NULL` (빈 행 방지)
- CHECK: 키 50~250, 몸무게 10~300 ▲ 가정한 범위

### 4.3 관계
| 부모 | 자식 | 카디널리티 | 비고 |
|---|---|---|---|
| grade | member | 1 : N | 탈퇴 시 `grade_id`는 NULL |
| member | member_auth | 1 : N | 정상 회원은 최소 1개(애플리케이션 규칙) |
| member | address | 1 : N | |
| member | member_grade_history | 1 : N | |
| grade | member_grade_history | 1 : N | 이전 등급·변경 후 등급 FK 2개 |
| member | member_terms_agreement | 1 : N | |
| terms | member_terms_agreement | 1 : N | 복합 FK |
| member | member_login_history | 1 : N | `member_auth`와는 FK 없음(스냅샷) |
| member | member_body_profile | 1 : 0..1 | PK = FK |

### 4.4 회원 탈퇴 시 처리
**상태 전이**: `ACTIVE → DORMANT`(배치, `last_login_at` 기준) / `DORMANT → ACTIVE`(로그인 시 해제) / `ACTIVE`·`DORMANT → WITHDRAWN`(진행 중 거래가 없을 때)

| 테이블 | 처리 |
|---|---|
| member | 행 유지. `name`, `nickname`, `phone`, `grade_id`, `last_login_at`, `dormant_at`을 NULL로, `status='WITHDRAWN'`, `withdrawn_at` 기록 |
| member_auth, address, member_grade_history, member_terms_agreement, member_login_history, member_body_profile | 물리 삭제. 회원 행이 남으므로 `ON DELETE CASCADE`가 아니라 탈퇴 처리 트랜잭션에서 명시적으로 삭제 |
| grade, terms | 회원과 무관하므로 유지 |

**법적 구분** (일반적으로 알려진 원칙이며 기간과 범위는 시행 법령으로 확인이 필요하다)
| 구분 | 개인정보 보호법의 원칙 | 전자상거래 관련 법령의 보존 의무 |
|---|---|---|
| 요구 | 이용 목적이 끝난 개인정보는 지체 없이 파기 | 일정한 거래 기록은 일정 기간 보존 |
| 대상 | 일반 회원정보(이름, 연락처, 로그인 정보, 저장 배송지, 등급·동의·로그인 이력, 체형 정보) | 계약·청약철회, 대금결제·재화 공급, 소비자 불만·분쟁처리 등의 거래 기록 |
| 보존 시 | 다른 법령상 보존 대상은 다른 정보와 분리해 저장·관리 | 보존 목적(법령 이행) 외로 쓰지 않음 |

보존 의무가 있는 것은 **거래 기록**이지 회원정보 전체가 아니다. 법령상 보존 의무가 확인되지 않은 정보를 증빙이 필요할지 모른다는 이유로 계속 보관하지 않는다.

### 4.5 엔티티별 삭제 정책
회원 탈퇴 시 처리(4.4)는 **회원에게 딸린 데이터**에 대한 것이고, 마스터 데이터의 폐지는 별개의 문제다.

| 엔티티 | 삭제 정책 |
|---|---|
| member | 행을 지우지 않음. 상태와 탈퇴 일시로 관리하고 개인정보는 삭제(논리 삭제 표시 방식이 아님) |
| member_auth, address, member_grade_history, member_terms_agreement, member_login_history, member_body_profile | 물리 삭제(탈퇴 시 또는 해당 기능의 삭제 시). 평소 member_grade_history, member_terms_agreement, member_login_history는 삭제하지 않고 행을 추가하거나 종료만 한다 |
| grade | 폐지 방식 미결정. 회원과 이력이 참조하므로 물리 삭제는 어렵고 비활성 표시 등을 등급 정책이 정해질 때 검토 |
| terms | 약관은 수정·삭제하지 않고 새 버전을 추가 |

### 4.6 정규화 검토
모든 테이블은 3NF를 만족한다. 의도적으로 중복·파생을 둔 곳은 다음과 같다.

| 위치 | 성격 | 정합성 보장 |
|---|---|---|
| `terms.required_yn` 제거 | 필수 여부가 `terms_type`에서 결정되는 파생 속성이라 저장하지 않음 | 약관 유형별 성격은 3.7의 표를 기준으로 애플리케이션이 지킨다 |
| `member_terms_agreement.terms_type` | 현재 유효한 기록을 유형별로 1건으로 제한하기 위한 복사 | `(terms_id, terms_type)` 복합 FK |
| `member.last_login_at` | 파생값 저장 | 로그인 처리 트랜잭션에서 이력 추가와 함께 갱신 |
| `member_login_history.provider_type` | 스냅샷 | 복사 후 관계를 끊음 |
| `member.grade_id` | 현재값(이력의 최신 상태와 중복) | 한 트랜잭션 처리와 점검 쿼리 |

주소는 우편번호·기본주소·상세주소로 나누어 각각 하나의 값으로 저장한다. 수령인과 연락처는 회원 본인과 다를 수 있는 배송지 고유 속성이라 회원 정보와 중복이 아니다.

### 4.7 FK 인덱스 검토
Oracle은 FK 컬럼에 인덱스를 자동으로 만들지 않는다. 인덱스가 없으면 부모 행을 삭제하거나 키를 바꿀 때 자식 테이블에 불필요한 잠금이 걸릴 수 있고 조인이 느려질 수 있다. 다만 모든 FK에 인덱스를 두는 것을 규칙으로 하지 않고, **조회 패턴, 부모 행의 변경·삭제와 잠금, 기존 인덱스와의 중복**을 보고 판단한다. 아래는 현재 요구사항 기준의 검토 결과이며, DDL 작성 시 쿼리 패턴에 따라 다시 확인한다.

| FK 컬럼 | 검토 | 결과 |
|---|---|---|
| member_auth.member_id | 회원의 인증수단 목록 조회가 있고, 기존 UNIQUE는 제공자 기준이라 대신할 수 없다 | 생성 |
| address.member_id | 배송지 목록 조회가 있고, 기본 배송지용 함수 기반 인덱스는 일반 조회에 쓸 수 없다 | 생성 |
| member_grade_history.member_id | 시점 조회용 복합 인덱스 `(member_id, changed_at)`의 선두 컬럼이 대신한다 | 복합 인덱스로 충족 |
| member_grade_history.prev_grade_id, new_grade_id | 등급별 이력 조회 요구가 없고 grade 행의 삭제가 예정되어 있지 않다(폐지 방식은 미결정) | 생략, 필요 시 추가 |
| member.grade_id | 등급별 회원 조회 요구가 없고 위와 같다 | 생략, 필요 시 추가 |
| member_terms_agreement.member_id | 회원의 동의 기록 조회가 있고, 함수 기반 UNIQUE 인덱스는 종료되지 않은 기록만 대상이라 대신할 수 없다 | 생성 |
| member_terms_agreement.(terms_id, terms_type) | 특정 약관 버전의 동의자 조회 요구가 없고 terms 행을 삭제하지 않는다 | 생략, 필요 시 추가 |
| member_login_history.member_id | 복합 인덱스 `(member_id, logged_in_at)`의 선두 컬럼이 대신한다 | 복합 인덱스로 충족 |
| member_body_profile.member_id | PK 인덱스가 있다 | 불필요 |

## ⑤ ERD 및 설계 검토

### 5.1 ERD
[erd/01_고객.drawio](erd/01_고객.drawio) (draw.io에서 열어 수정할 수 있다)

- 핵심(회원), 마스터(등급·약관), 회원 종속 테이블을 색으로 구분했다.
- 회원을 가운데에 두고 종속 테이블을 좌우로, 마스터를 바깥쪽에 배치해 관계선의 교차를 없앴다.
- 관계선은 4.3의 관계를 그대로 표현한다. 등급 → 등급 변경 이력은 FK가 2개(`prev_grade_id`, `new_grade_id`)라 선이 2개다.
- `member_login_history.provider_type`은 복사한 값이라 선이 없다.

### 5.2 주요 설계 결정 요약
- 대리키 + 비식별 관계가 기본이며 체형 정보만 PK=FK 예외로 둔다.
- 로그인 수단은 회원과 분리한 1:N 구조로 통일하고, 이메일 일치만으로 소셜 계정을 병합하지 않는다.
- 회원 등급은 현재 등급 + 점 이력이며, 변경은 한 트랜잭션으로 처리한다.
- 회원 탈퇴는 회원 행을 유지하고 개인정보를 삭제·최소화한다(익명화가 아님).
- 약관 동의는 선분 이력이며 유형당 현재 유효한 기록은 1건이다.

### 5.3 다른 영역과의 연결
| 영역 | 연결 |
|---|---|
| 장바구니·쿠폰·주문·결제 | 회원(`member`)을 참조한다. 탈퇴한 회원의 참조는 유지된다 |
| 가격·쿠폰 | 등급(`grade`)별 혜택은 이 영역에서 정하지 않는다 |
| 주문 | 배송지·주문자 정보는 스냅샷으로 복사한다. 진행 중 거래와 비회원 조회 인증은 주문 영역에서 정한다 |
| 알림(확장) | 마케팅 동의 기록(`member_terms_agreement`)을 참조해 발송한다 |

### 5.4 미결정 사항
| 구분 | 내용 |
|---|---|
| 로그인 | 지원 소셜 제공자 목록, 제공자당 1개 제한 여부, 연결·해제 조건(마지막 수단 해제 허용 여부), 이메일 변경 방식 |
| 등급 | 등급 체계(개수·명칭), 산정 주기와 구매 실적 기준, 미이용 강등 여부, 변경 당시 평가 근거의 저장 방식, 변경 사유 유형 목록, 가입 시 부여하는 기본 등급, 등급 폐지 방식 |
| 약관 | 약관 유형 초기 목록, 본문 저장 방식, 이용약관 동의의 법령상 보존 필요성 확인 |
| 휴면 | 휴면 판정 기간, 사전 통지, 해제 시 본인 확인, `last_login_at`의 초기값 |
| 보관 | IP 주소 보관 기간, 거래 기록 보존 기간 종료 후 회원 행 최종 삭제 |
| 회원 정보 | 가입 필수 항목(연락처 필수 여부), 체형 값 범위 |
| 구현 | 탈퇴 처리와 신규 주문의 경합(진행 중 거래 검사) 처리 → 주문 영역 |

### 5.5 추가 검토 사항
- 확장 후보: 본인인증, 이메일 인증·비밀번호 재설정, 실패 로그인 기록, 휴면 시 개인정보 분리 보관, 재가입 제한, 탈퇴 유예, 알림 영역.
- 선분 이력은 약관 동의에 적용했고, 가격 영역에서 가격 이력에 대한 적용을 다시 검토한다.
