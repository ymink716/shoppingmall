# 1회차: 고객 테이블 설계

> 무신사 기반 쇼핑몰 데이터 모델링 실습
> 진행 방식: ① 설계 유형 정리 → ② 설계 기법 정리 → ③ 테이블 설계 → ④ 컬럼 확인
> DBMS는 미정이므로 컬럼 타입은 도메인으로 표기합니다. 실제 타입은 물리 모델링 단계에서 정합니다.

## 목차
0. 결정 사항 요약
1. 고객 테이블 설계 유형 (1~10)
2. 설계 기법 복습 노트 (A~I)
3. 테이블 설계서
4. 컬럼 확인 포인트와 확정 결과
5. 업무 규칙 목록과 다음 회차로 넘긴 항목

---

## 0. 결정 사항 요약

### 프로젝트 범위
- 참고 서비스: 무신사 (https://www.musinsa.com/)
- 판매 모델: **PB + 입점 혼합형**
- 혜택: 고객 등급과 적립금 포함 (등급과 적립금은 8회차에서 설계)
- 진행 순서: 고객 → 브랜드·판매자 → 카테고리 → 상품 → 장바구니·주문 → 결제·배송 → 클레임 → 등급·적립금 → 쿠폰 → 리뷰 → (정산)

### 고객 업무 규칙 (무신사 기준 추천안으로 확정)
| # | 규칙 | 근거 |
|---|---|---|
| 1 | 회원만 주문할 수 있다 (비회원 주문 없음) | 첫 구매 쿠폰, 적립, 등급 등 가입 유도형 혜택 구조 |
| 2 | 가입할 때 휴대폰 본인인증을 받고, CI로 1인 1계정을 보장한다 | 첫 구매 쿠폰 중복 수령 방지 |
| 3 | 한 고객이 여러 로그인 수단(이메일, 카카오, 네이버, 애플)을 연동할 수 있다. 단, 유형별로 1개씩만 | 국내 대형 커머스 관행 |
| 4 | 판매자 계정과 관리자 계정은 고객과 분리한다 | 무신사 파트너 포털이 별도로 운영됨 |
| 5 | 체형정보(키, 몸무게, 평소 사이즈)는 선택 입력이며 별도 동의를 받는다 | 패션몰 후기·사이즈 추천 |
| 6 | 고객은 현재 등급을 하나 가진다. 산정 방식은 8회차에서 다룬다 | 무신사 레벨 1~9 등급제 |

근거 표시: 무신사 사이트는 대부분 JavaScript로 그려져서 직접 확인한 정보가 적습니다. 위 규칙의 상당수는 공개 기사와 업계 관행을 바탕으로 추론한 것입니다.

## 1. 고객 테이블 설계 유형

설계 유형은 **"고객 정보를 테이블로 어떻게 나눌까"** 에 대한 구조 패턴입니다.
유형마다 **정의 → 해결하는 문제 → 구조와 예시 → 장단점 → 언제 쓰나 → 무신사라면** 순서로 정리했습니다.

### 학습 순서
| 단계 | 유형 | 핵심 질문 |
|---|---|---|
| 기본 | 1. 단일 테이블형 → 2. 자식 테이블 분리형 → 3. 수직 분할형 | 컬럼을 어디에 둘 것인가? |
| 업무 확장 | 4. 인증수단 분리형 → 5. 회원/비회원형 → 6. 슈퍼타입/서브타입형 → 7. 이력 관리형 | 업무 규칙을 어떻게 담을 것인가? |
| 심화 | 8. 개인정보 분리형 → 9. 확장 속성형 → 10. 파티 패턴형 | 규모, 보안, 유연성을 어떻게 확보할 것인가? |

---

### 1. 단일 테이블형
**정의**: 고객에 관한 모든 정보를 테이블 하나에 담습니다.

**구조와 예시**
| 고객번호 | 이메일 | 이름 | 주소1 | 주소2 | 카카오ID | 등급 | 적립금 |
|---|---|---|---|---|---|---|---|
| 1 | a@x.com | 김무신 | 서울… | 부산… | k123 | GOLD | 3200 |
| 2 | NULL | 이사 | 대전… | NULL | k456 | BRONZE | 0 |

- **장점**: 가장 단순하고 조인이 없습니다.
- **단점**
  - 주소1, 주소2처럼 **반복 컬럼**이 생깁니다.
  - NULL이 많아집니다.
  - 주소가 3개 필요해지면 테이블 구조를 바꿔야 합니다.
- **언제**: 프로토타입, 학습 초기
- **무신사라면**: ❌ 배송지와 소셜 계정이 여러 개라서 맞지 않습니다.
- 👉 **나머지 유형은 모두 이 유형의 문제를 하나씩 해결하는 방법**입니다.

---

### 2. 자식 테이블 분리형 (1:N)
**정의**: 고객 한 명이 **여러 개를 가질 수 있는 정보**를 별도 테이블로 분리합니다.

**해결하는 문제**: 1번의 반복 컬럼 (주소1, 주소2, 주소3)

**구조와 예시**
```
고객 1 ──< N 배송지
```
| 배송지번호 | 고객번호 | 배송지명 | 주소 | 기본여부 |
|---|---|---|---|---|
| 10 | 1 | 집 | 서울… | Y |
| 11 | 1 | 회사 | 부산… | N |

- **장점**: 개수 제한이 없고 정규형(1정규형)을 만족합니다.
- **단점**: 조회할 때 조인이 필요합니다.
- **판단 기준**: **같은 성격의 값이 반복**되거나, **종류가 늘어날 수 있으면** 분리합니다.
- **적용 예**: 배송지, 연락처(이메일·전화 여러 개), 수신동의(채널별)
- **무신사라면**: ✅ 배송지, 수신동의

---

### 3. 수직 분할형 (1:1)
**정의**: 한 고객에 대한 정보를 **성격별로 여러 테이블에 1:1로** 나눕니다.

**해결하는 문제**: 컬럼이 많아지고, 성격이 다른 값이 한곳에 섞이는 문제

**구조와 예시**
```
고객(기본) ─1:1─ 고객 프로필 ─1:1─ 고객 통계
```
| 테이블 | 컬럼 | 변경 빈도 |
|---|---|---|
| 고객 | 고객번호, 상태, 등급, 가입일시 | 낮음 |
| 고객 프로필 | 고객번호, 이름, 전화, 생년월일 | 낮음 (개인정보) |
| 고객 통계 | 고객번호, 누적구매액, 최근주문일시, 최근로그인일시 | **매우 높음** |

- **장점**
  - 자주 바뀌는 값이 분리되어 성능이 좋아집니다.
  - 개인정보만 따로 권한과 암호화를 관리할 수 있습니다.
- **단점**: 조인이 늘어나고, 1:1 관계를 유지하는 관리가 필요합니다.
- **언제**: 컬럼이 많고 트래픽이 큰 실서비스
- **주의**: **물리 설계 단계의 선택**입니다. 논리 모델에서는 하나의 고객으로 봅니다.
- **선택적 1:1 분리**도 같은 유형입니다. 일부 고객만 가진 정보(예: 체형정보)를 분리하면 NULL을 줄일 수 있습니다.
- **무신사라면**: ✅ 체형정보 분리. 나머지는 물리 단계에서 결정

---

### 4. 인증수단 분리형
**정의**: "사람(고객)"과 "로그인 방법(계정)"을 분리합니다.

**해결하는 문제**: 카카오ID, 네이버ID, 애플ID 컬럼이 계속 늘어나는 문제, 한 사람이 여러 소셜을 연동하는 상황

**구조와 예시**
```
고객 1 ──< N 고객 인증수단
```
| 고객번호 | 인증유형 | 외부식별값 | 비밀번호해시 |
|---|---|---|---|
| 1 | EMAIL | a@x.com | $2b$… |
| 1 | KAKAO | 98765 | NULL |
| 1 | APPLE | 001.abc | NULL |

- **장점**
  - 로그인 수단을 추가해도 테이블 구조를 바꿀 필요가 없습니다.
  - 연동과 해제가 행 추가/삭제로 끝납니다.
- **단점**: 로그인할 때 조인이 필요합니다.
- **변형**
  - **절충형**: 이메일/비밀번호는 고객에 두고, 소셜 계정만 분리
  - **통합형**: 모든 인증 수단을 한 테이블에 둠 (위 예시)
- **무신사라면**: ✅ 통합형 (소셜 로그인 비중이 큼)

---

### 5. 회원/비회원형
**정의**: 가입하지 않은 주문자를 어떻게 저장할지 정하는 유형입니다.

| 방식 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 5-a. 주문에만 저장 | 주문(주문자명, 주문자전화, 조회비밀번호) | 가장 단순함 | 비회원이 고객으로 관리되지 않음 |
| 5-b. 분리형 | 회원 테이블 + 비회원 테이블 | 둘이 명확하게 구분됨 | 주문이 두 테이블을 참조해야 함 |
| 5-c. 통합형 | 고객(고객유형: 회원/비회원) | 주문의 참조 대상이 하나. 비회원이 가입하면 이력을 이어 갈 수 있음 | 회원 전용 컬럼에 NULL이 생김 |

**5-c 통합형 예시**
| 고객번호 | 고객유형 | 이름 | 전화 | 이메일 |
|---|---|---|---|---|
| 1 | 회원 | 김무신 | 010… | a@x.com |
| 2 | 비회원 | 박구매 | 010… | NULL |

- **무신사라면**: 회원만 주문 가능하도록 정했으므로 **해당 없음**

---

### 6. 슈퍼타입/서브타입형
**정의**: 고객의 **종류마다 필요한 속성이 다를 때**, 공통 속성과 유형별 속성을 나눕니다.

**해결하는 문제**: 개인 고객과 사업자 고객이 한 테이블에 섞이면서 생기는 NULL과 혼란

**구조**
```
고객(공통: 고객번호, 고객유형, 이메일, 상태)
  ├─ 개인 고객(생년월일, 성별)
  └─ 사업자 고객(사업자번호, 상호, 대표자명)
```

**물리 구현 3가지**
| 방식 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 통합 | 한 테이블 + 유형별 컬럼 (NULL 허용) | 조회가 단순함 | NULL이 많고 유형별 필수값을 강제하기 어려움 |
| 분리 | 공통 테이블 + 유형별 테이블 | 정규화되어 있고 제약이 명확함 | 조인 필요 |
| 개별 | 유형별 독립 테이블 | 유형별 조회가 빠름 | 전체 고객 조회 시 UNION 필요 |

- **언제**: B2B 회원, 임직원 회원 등 유형별 속성 차이가 클 때
- **무신사라면**: ❌ 개인 고객만 있음. 단, 2회차(판매자)에서 다시 쓰일 수 있음

---

### 7. 이력 관리형
**정의**: 값이 **바뀐 기록**을 별도로 남기는 유형입니다.

**해결하는 문제**: 현재값만 저장하면 "언제, 왜 바뀌었는지" 알 수 없음

| 방식 | 구조 예시 | 언제 |
|---|---|---|
| 7-a. 변경 이력 | 고객 상태 이력(고객번호, 이전상태, 변경상태, 사유, 변경일시) | 특정 값의 변경 증빙 (상태, 등급, 수신동의). **실무에서 가장 많이 씀** |
| 7-b. 선분 이력 | 고객 이력(고객번호, 이름, 등급, **시작일시, 종료일시**) | "그 시점의 고객 정보" 조회 (분석, 정산) |
| 7-c. 감사 로그 | 감사로그(테이블, 컬럼, 이전값, 이후값, 수정자) | 관리자 수정 추적 |

**7-a 예시: 고객 상태 이력**
| 이력번호 | 고객번호 | 이전상태 | 변경상태 | 사유 | 변경일시 |
|---|---|---|---|---|---|
| 1 | 1 | 정상 | 정지 | 반품 남용 | 2026-03-01 |
| 2 | 1 | 정지 | 정상 | 정지 해제 | 2026-04-01 |

- **무신사라면**: ✅ 7-a (상태 이력, 수신동의 이력, 등급 이력)

### 8. 개인정보 분리형 (PII Vault)
**정의**: 개인정보를 **서비스 테이블과 다른 영역(스키마, DB)** 에 따로 저장합니다.

**구조**
```
[서비스 영역] 고객(고객번호, 상태, 등급)           ← 개인정보 없음
[보안 영역]   고객 개인정보(고객번호, 이름, 전화, 이메일, CI)  ← 암호화, 접근 통제
```

- **장점**: 서비스 DB가 유출돼도 개인정보는 안전합니다. 탈퇴할 때 개인정보 행만 파기하면 됩니다.
- **단점**: 개인정보가 필요한 화면마다 별도로 조회해야 하고 운영이 복잡해집니다.
- **언제**: 규제가 강한 곳, 대규모 서비스
- **무신사라면**: △ 실습에서는 3번 수직 분할 + 컬럼 암호화로 대신해도 충분합니다.

---

### 9. 확장 속성형 (EAV / JSON)
**정의**: 속성을 컬럼이 아니라 **데이터(행 또는 JSON)** 로 저장합니다.

**EAV 예시**
| 고객번호 | 속성명 | 속성값 |
|---|---|---|
| 1 | 선호스타일 | 미니멀 |
| 1 | 선호브랜드 | 무신사 스탠다드 |

- **장점**: 테이블 구조를 바꾸지 않고 속성을 추가할 수 있습니다.
- **단점**
  - 타입 검증이 안 됩니다. 모든 값이 문자열이 됩니다.
  - 필수값을 강제할 수 없습니다.
  - 조회 쿼리가 복잡해집니다.
- **언제**: 검색 조건으로 쓰지 않는 부가정보에만 제한적으로 사용
- **무신사라면**: ❌ 선호 스타일이 필요하다면 **2번 자식 테이블(고객 선호스타일)** 이 더 낫습니다.

### 10. 파티(Party) 패턴형
**정의**: 고객, 판매자, 직원을 모두 **"당사자(Party)"** 로 묶고, **역할**로 구분합니다.

**구조**
```
당사자(당사자번호, 당사자유형: 개인/법인)
  ├─ 개인(이름, 생년월일)
  ├─ 법인(상호, 사업자번호)
  └─ 당사자 역할(당사자번호, 역할: 고객/판매자/직원/공급사)
```

- **장점**: 한 주체가 고객이면서 판매자인 경우를 자연스럽게 표현합니다.
- **단점**: 매우 복잡하고 모든 조회가 길어집니다.
- **언제**: 오픈마켓(개인 간 거래), ERP, 대형 그룹사 통합 시스템
- **무신사라면**: ❌ 고객과 판매자 계정을 분리하기로 했으므로 과한 설계입니다. (USED 개인 판매까지 넣는다면 검토 대상)

## 2. 설계 기법 복습 노트

설계 **유형**이 "테이블을 어떻게 나눌까"였다면, 설계 **기법**은 "어떤 유형이든 공통으로 결정해야 하는 것"입니다.
같은 형식(정의 → 해결하는 문제 → 예시 → 판단 기준 → 이번 적용)으로 정리했습니다.

### 학습 순서
| 단계 | 기법 | 핵심 질문 |
|---|---|---|
| 식별 | A. 인조 식별자 vs 본질 식별자 → B. 대체 식별자·조건부 유일 → C. 식별·비식별 관계 | 행을 무엇으로 구분할 것인가? |
| 관계 | D. M:N 관계 해소 | 다대다를 어떻게 표현할 것인가? |
| 값 | E. 파생 속성 판단 → F. 상태 코드 설계 | 무엇을 저장하고 무엇을 계산할 것인가? |
| 생명주기·보안 | G. 탈퇴 처리 → H. 암호화 + 해시 검색 → I. 공통 컬럼 | 데이터를 어떻게 보호하고 파기할 것인가? |

### A. 인조 식별자 vs 본질 식별자
- **정의**
  - **본질 식별자**: 업무에 원래 있는 값 (이메일, CI)
  - **인조 식별자**: 식별만을 위해 시스템이 만든 값 (순번)
- **해결하는 문제**: 본질 식별자는 값이 바뀌거나, 비어 있거나, 민감정보일 수 있음
- **판단 기준 (식별자 4요건)**
  - 유일성: 각 행을 하나로 구분하는가
  - 최소성: 필요한 최소 속성만으로 구성되는가
  - 불변성: 한번 정하면 바뀌지 않는가
  - 존재성: 모든 행에 값이 있는가

  | 후보 | 유일 | 불변 | 존재 | 결과 |
  |---|---|---|---|---|
  | 이메일 | △ | ❌ | ❌ | 탈락 |
  | 휴대폰번호 | △ (번호 재할당) | ❌ | ✅ | 탈락 |
  | CI | ✅ | ✅ | △ | 민감정보이고 재가입 시 충돌 → 탈락 |
  | 고객번호 | ✅ | ✅ | ✅ | **채택** |
- **이번 적용**: customer_id

### B. 대체 식별자 · 조건부 유일 · 외부노출키
- **정의**: 주 식별자는 아니지만 **유일해야 하는 값**을 대체 식별자(AK)로 지정합니다.
- **해결하는 문제**: 인조 식별자만 두면 같은 사람이 중복 가입하는 것을 막을 수 없음
- **예시**
  - 일반 유일: 닉네임
  - **조건부 유일**: CI해시 (탈퇴하지 않은 고객 중에서만 유일)
  - **외부노출키 (B-2)**: customer_uid. 순번을 URL에 노출하면 회원 수를 추정할 수 있으므로, 외부에는 UUID를 노출
- **이번 적용**: nickname, ci_hash(조건부), customer_uid, auth_type_cd + auth_key_hash

### C. 식별 관계 vs 비식별 관계
- **정의**
  - **식별 관계**: 부모의 키가 자식 **PK의 일부**가 됨
  - **비식별 관계**: 부모의 키가 자식의 일반 FK가 됨
- **예시**

  | 테이블 | 관계 | PK | 이유 |
  |---|---|---|---|
  | 고객 인증수단 | 식별 | 고객번호 + 인증유형 | 조합 자체가 규칙 ("유형당 1개"). 자식 테이블이 없음 |
  | 고객 체형정보 | 식별 (1:1) | 고객번호 | 고객 없이는 의미가 없음 |
  | 배송지 | 비식별 | 배송지번호 | 독립적으로 편집, 삭제함 |
  | 상태 이력 | 비식별 | 이력번호 | 행이 계속 쌓임 |
- **판단 기준**
  - 조합 자체가 업무 규칙이고 자식이 없으면 → 식별 관계
  - 다른 테이블이 참조하거나 독립적으로 관리되면 → 비식별 관계

### D. M:N 관계 해소
- **정의**: 다대다 관계를 **관계 테이블**로 풀어냅니다.
- **해결하는 문제**: 관계형 DB는 M:N을 직접 표현할 수 없음
- **예시**: 고객 N : M 약관 → 약관 동의 (고객번호 + 약관번호, 동의일시, 철회일시)
- **판단 기준**: 관계 자체에 속성(동의일시)이 있으면 반드시 독립 테이블로 만듭니다.
- **이번 적용**: customer_terms_agree

### E. 파생 속성 판단
- **정의**: 다른 값으로 계산할 수 있는 속성입니다.
- **해결하는 문제**: 저장하면 원본과 값이 어긋날 수 있음 (정합성 문제)

  | 값 | 판단 | 이유 |
  |---|---|---|
  | 연령 | 저장 안 함 | 생년월일로 계산 |
  | 적립금 잔액, 누적구매액 | 논리 모델에서 제외 | 이력의 합계. 물리 단계에서 역정규화로 결정 |
  | 현재 등급 | **저장** | 유예 같은 업무 판단이 들어간 결과 |
- **판단 기준**: "언제든 정확히 다시 계산할 수 있는가?" → 그렇다면 파생 속성

### F. 상태 코드 설계
- **정의**: 서로 배타적인 상태를 **하나의 코드 컬럼**으로 표현합니다.
- **해결하는 문제**: 여부 플래그를 여러 개 두면 "탈퇴이면서 정지" 같은 모순이 생김
- **예시**: customer_status_cd = ACTIVE / SUSPENDED / WITHDRAWN
- **함께 쓰는 것**: 상태 이력 테이블 (유형 7-a)

### G. 탈퇴 처리 (익명화 + 분리)
- **정의**: 행은 남기고 개인정보만 파기하며, 재가입 판별용 정보는 따로 보관합니다.
- **해결하는 문제**
  - 행을 삭제하면 → 주문 이력이 깨짐
  - 행을 그대로 두면 → 개인정보가 남아 법 위반 소지
- **예시**: 탈퇴 → 고객의 이름, 휴대폰, CI 등은 NULL, 닉네임은 치환 → CI해시는 고객 탈퇴 테이블로 이동
- **주의**: NOT NULL 제약과 충돌하므로 **조건부 필수 규칙**이 필요합니다 (컬럼 확인 1번)

### H. 암호화 + 해시 검색 컬럼
- **정의**: 개인정보는 암호화하고, 검색에는 **해시 컬럼**을 씁니다.
- **해결하는 문제**: 암호화된 값은 WHERE 조건으로 검색할 수 없음
- **예시**: mobile_no(암호문) + mobile_no_hash(검색용), ci + ci_hash
- **구분**
  - 비밀번호 → 단방향 해시 (복호화 불가)
  - 개인정보 → 양방향 암호화 (복호화 가능)
  - 주민등록번호 → 저장 금지

### I. 공통 컬럼
- **정의**: 모든 테이블에 넣는 관리용 컬럼입니다.
- **예시**: 수업 PPT 기준으로 **테이블 마지막에 시스템 컬럼 4개**를 둡니다: `created_by`(등록자ID), `created_at`(등록일시), `updated_by`(수정자ID), `updated_at`(수정일시)
- **적용 범위**: 이력 테이블처럼 수정하지 않는 테이블에도 일관성을 위해 4개를 모두 둡니다 (수정 값은 등록 값과 같음)
- **등록자ID**: 고객·판매자 담당자·관리자·시스템 중 누구든 될 수 있으므로 FK를 걸지 않습니다
- **주의**: 업무 일시(가입일시)와 시스템 일시(등록일시)를 구분합니다.

### 스스로 점검해 볼 질문
1. CI가 식별자 4요건 중 어떤 문제 때문에 주 식별자로 쓰이지 못했나요? → A
2. 고객 인증수단은 왜 식별 관계이고, 배송지는 왜 비식별 관계인가요? → C
3. 적립금 잔액과 현재 등급 중 어느 것이 파생 속성인가요? 그 이유는? → E
4. 탈퇴 익명화를 적용하면 어떤 제약조건과 충돌하나요? → G
5. 암호화된 휴대폰번호로 계정을 찾으려면 무엇이 필요한가요? → H

## 3. 테이블 설계서

### 3-1. 적용한 유형과 기법
| 적용 | 대상 테이블 |
|---|---|
| **유형 2. 자식 테이블 분리** | 배송지, 고객 수신동의 |
| **유형 3. 수직 분할 (선택적 1:1)** | 고객 체형정보 |
| **유형 4. 인증수단 분리 (통합형)** | 고객 인증수단 |
| **유형 7-a. 변경 이력** | 고객 상태 이력, 수신동의 이력 |
| 기법 D: M:N 관계 해소 | 약관 동의 |
| 기법 G: 탈퇴 익명화 + 탈퇴 정보 분리 | 고객, 고객 탈퇴 |
| 미적용 | 유형 1, 5, 6, 8, 9, 10 |

### 3-2. 관계도
```
등급(8회차) 1 ──< N 고객
고객 1 ──< N 고객 인증수단          [식별]  PK: 고객번호 + 인증유형
고객 1 ──< N 배송지                [비식별] PK: 배송지번호
고객 1 ──< N 고객 수신동의 1 ──< N 수신동의 이력
고객 1 ──○ 0..1 고객 체형정보        [식별]  PK: 고객번호
고객 1 ──< N 약관 동의 >── 1 약관    [M:N 해소]
고객 1 ──< N 고객 상태 이력
고객 1 ──○ 0..1 고객 탈퇴
```

### 3-3. 테이블 정의

표기
- **도메인**: 번호, 명, 코드, 여부(Y/N), 일시, 일자, 해시(64자), 암호문, UUID
- **NULL**: N = 필수, Y = 선택, Y* = 탈퇴 회원만 NULL이고 탈퇴하지 않은 회원은 필수 (조건부 필수)
- 🔒 = 암호화 대상
- 모든 테이블의 마지막에 시스템 컬럼 4개 `created_by`(등록자ID), `created_at`(등록일시), `updated_by`(수정자ID), `updated_at`(수정일시)를 둡니다. 아래 표에서는 생략했습니다. (2회차 카테고리에서 PPT 기준에 맞춰 2개 → 4개로 통일)

#### ① 고객 `customer`
> 적용: 기본 테이블, 인조 식별자(A), 대체 식별자·조건부 유일·외부노출키(B), 상태 코드(F), 탈퇴 익명화(G), 암호화 + 해시(H)

| No | 논리명 | 컬럼명 | 도메인 | NULL | 키 | 설명 |
|---|---|---|---|---|---|---|
| 1 | 고객번호 | customer_id | 번호 | N | PK | 인조 식별자 |
| 2 | 고객공개ID | customer_uid | UUID | N | AK | URL, API에 노출하는 외부키 |
| 3 | 고객명 | customer_name | 암호문 🔒 | Y* | | 본인인증으로 받은 값 |
| 4 | 닉네임 | nickname | 명(30) | N | AK | 후기 작성자 표시용. 탈퇴하면 `탈퇴회원_{고객번호}`로 치환 |
| 5 | 휴대폰번호 | mobile_no | 암호문 🔒 | Y* | | |
| 6 | 휴대폰번호해시 | mobile_no_hash | 해시 | Y* | IX | 계정 찾기 검색용 |
| 7 | 연락이메일 | contact_email | 암호문 🔒 | Y | | 로그인 이메일과는 다른 값 |
| 8 | 생년월일 | birth_date | 일자 | Y* | | 연령은 저장하지 않음 (파생값) |
| 9 | 성별코드 | gender_cd | 코드 | Y* | | F / M / N |
| 10 | CI | ci | 암호문 🔒 | Y* | | |
| 11 | CI해시 | ci_hash | 해시 | Y* | AK(조건부) | 탈퇴하지 않은 고객 중에서 유일 |
| 12 | 본인인증일시 | identity_verified_at | 일시 | N | | |
| 13 | 고객상태코드 | customer_status_cd | 코드 | N | | ACTIVE / SUSPENDED / WITHDRAWN |
| 14 | 등급코드 | grade_cd | 코드 | N | FK | 등급 테이블 참조 (8회차) |
| 15 | 가입경로코드 | join_channel_cd | 코드 | N | | WEB / IOS / ANDROID |
| 16 | 가입일시 | joined_at | 일시 | N | | 업무 일시 (등록일시와 구분) |
| 17 | 최근로그인일시 | last_login_at | 일시 | Y | | |

## 4. 컬럼 확인 포인트와 확정 결과

모두 추천안대로 확정했습니다.

| # | 쟁점 | 내용 | 확정 |
|---|---|---|---|
| 1 | 탈퇴 익명화와 NOT NULL의 충돌 | 이름, 휴대폰, 생년월일 등을 필수로 두면 탈퇴할 때 파기할 수 없음 | 해당 컬럼을 NULL 허용(`Y*`)으로 바꾸고, "탈퇴하지 않은 고객은 필수"를 **조건부 규칙**(CHECK 제약)으로 둠 |
| 2 | 가입일시와 등록일시 중복 | joined_at과 created_at이 사실상 같은 값 | 가입일시(업무 값)와 등록일시(시스템 값)를 모두 유지. 데이터 이관 등으로 달라질 수 있음 |
| 3 | 로그인 이메일 보안 | 인증키에 로그인 이메일이 평문으로 들어감 | EMAIL 유형은 인증키를 암호화하고 인증키해시로 조회 |
| 4 | 처리자 참조 | 관리자 테이블이 아직 없음 | 처리자구분코드 + 처리자ID로 두고, 관리자를 설계할 때 연결 |
| 5 | 닉네임 탈퇴 처리 | 닉네임은 유일해야 하는데 탈퇴 후 재사용이 가능해야 함 | 탈퇴하면 `탈퇴회원_{고객번호}`로 치환 |
| 6 | 고객공개ID 추가 | 1회차 초기 논의에는 없던 컬럼 | 외부노출키(기법 B-2)로 추가 |
| 7 | 고객 통계 분리 | 누적구매액, 최근주문일시 같은 값 | 논리 모델에서는 제외. 물리 단계에서 유형 3(수직 분할)으로 별도 테이블을 둘지 결정 |

### 설계 과정에서 결정한 대안 (복습용)
| 쟁점 | 선택 | 버린 대안 | 이유 |
|---|---|---|---|
| 고객 주 식별자 | 고객번호 + CI 대체 식별자 | CI를 주 식별자로 | 재가입 시 충돌, 민감정보가 FK로 퍼짐 |
| 인증수단 식별 | 식별 관계 (고객번호 + 인증유형) | 비식별 (인증수단번호) | 유형당 1개 규칙, 자식 테이블 없음 |
| 기본 배송지 표현 | 배송지.기본여부 | 고객.기본배송지번호 | 고객 ↔ 배송지 순환 참조를 피함 |
| 약관 재동의 이력 | 현재 상태만 | PK에 동의순번 추가 | 실습 범위 단순화 |
| 수신동의 구조 | 수신동의 테이블(현재값) + 이력 | 고객 컬럼 3개 / 이력만 | 반복 그룹 제거, 채널 추가가 쉬움 |
| 체형정보 위치 | 1:1 분리 | 고객의 선택 컬럼 | 선택적으로 존재하고, 동의 철회 시 행 삭제로 처리 |

## 5. 업무 규칙 목록과 다음 회차로 넘긴 항목

### 키 구조만으로는 보장되지 않는 업무 규칙
- 고객당 기본 배송지(기본여부 = Y)는 1개다 → 물리 단계에서 제약 추가
- 탈퇴하지 않은 고객은 이름, 휴대폰, 생년월일, 성별, CI가 필수다 → 조건부 CHECK
- CI해시는 탈퇴하지 않은 고객 중에서 유일하다 → 조건부 유일 인덱스
- 필수 약관은 철회할 수 없다
- 재가입은 재가입가능일시 이후에만 허용한다

### 시나리오 검증 결과
| # | 시나리오 | 결과 |
|---|---|---|
| 1 | 같은 사람이 이메일과 카카오로 각각 따로 가입 시도 | ✅ CI해시 대체 식별자로 막음 |
| 2 | 카카오 계정 하나를 두 고객에게 연결 시도 | ✅ 인증수단 AK(유형 + 인증키해시)로 막음 |
| 3 | 한 고객이 카카오 계정 2개를 연동 시도 | ✅ 인증수단 PK(고객번호 + 유형)로 막음 |
| 4 | 탈퇴 10일 뒤 재가입 시도 | ✅ 고객 탈퇴의 CI해시와 재가입가능일시로 판단 |
| 5 | 제한 기간이 지난 뒤 재가입 | ✅ 새 고객번호가 생기고, 이전 고객의 CI는 비어 있으므로 충돌 없음 |
| 6 | 기본 배송지가 2개가 되는 경우 | ⚠ 물리 단계에서 제약 추가 필요 |
| 7 | 마케팅 SMS 수신을 끔 | ✅ 수신동의 현재값 변경 + 이력 추가 |
| 8 | 체형정보 수집 동의 철회 | ✅ 체형정보 행 삭제 (후기 스냅샷은 10회차에서 처리) |
| 9 | 관리자가 고객을 정지 처리 | ✅ 상태 이력 추가. 처리자 연결은 관리자 설계 후 |
