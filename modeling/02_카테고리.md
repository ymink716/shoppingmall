# 2회차: 카테고리 테이블 설계

> 무신사 기반 쇼핑몰 데이터 모델링 실습
> 진행 방식: ① 설계 유형 정리 → ② 테이블 설계 → ③ 컬럼 확인
> 용어는 수업 PPT(`DB모델링_기초.pdf`, `DB모델링_all_ppt.pdf`)를 참고합니다. PPT에 없는 실무 용어는 **(PPT 외)** 로 표시합니다.
> DBMS는 미정이므로 컬럼 타입은 도메인으로 표기합니다.

## 목차

## 0. 카테고리는 어떤 엔티티인가

- PPT 분류로 카테고리는 **핵심 엔티티(기준정보)** 중 **"유형 및 분류"** 에 해당합니다. PPT도 예시로 "상품 분류(대중소)"를 들고 있습니다.
- 무신사 관찰
  - 상품 페이지에 `가방 > 숄더백` 같은 계층 경로가 표시됨 (✅ 직접 확인)
  - 아울렛, 부티크, 뷰티 같은 전문관이 따로 운영됨 (📰 기사 확인)
- 카테고리 설계의 핵심 질문
  1. **계층(트리)을 테이블에 어떻게 저장할까?**
  2. **상품과 카테고리를 어떻게 연결할까?**
  3. **관리용 분류와 매장 노출용 분류가 같은가?**

### 예시 트리 (모든 유형에서 공통으로 사용)
```
상의(1)
 ├─ 티셔츠(2)
 │   ├─ 반소매 티셔츠(4)
 │   └─ 긴소매 티셔츠(5)
 └─ 셔츠(3)
가방(6)
 └─ 숄더백(7)
```

## 1. 카테고리 설계 유형

### 학습 순서
| 단계 | 유형 | 핵심 질문 |
|---|---|---|
| 계층 표현 (기본) | 1. 대중소 고정 단계형 → 2. 재귀적 관계형 → 3. 계층 코드형 | 트리를 어떻게 저장할까? |
| 계층 표현 (조회 최적화) | 4. 경로 저장형 → 5. 중첩 집합형 → 6. 중첩 구간형 → 7. 클로저 테이블형 → 8. 혼합형 | 하위·상위 조회를 어떻게 빠르게 할까? |
| 계층 표현 (기타) | 9. DBMS 전용 기능 → 10. 문서형 | DB 기능이나 다른 저장 형태를 쓸까? |
| 상품 연결 | 11. 기본 관계형 / M:N 해소형 / 대표 지정형 | 상품은 카테고리에 몇 개 속하는가? |
| 운영 구조 | 12. 표준/전시 분리형 → 13. 카테고리 속성 정의형 | 관리 분류와 노출 분류가 같은가? |

> 📌 계층 표현 방식은 결국 **무엇을 저장하느냐**로 나뉩니다.
> - 부모를 저장 → 2
> - 경로를 저장 → 3, 4
> - 범위를 저장 → 5, 6
> - 조상-자손 관계를 모두 저장 → 7
>
> 이 네 가지 축을 기억하면 새로운 방식을 만나도 어디에 속하는지 알 수 있습니다.

### 1. 대중소 고정 단계형
**정의**: 계층 단계를 미리 정해 두고, **단계마다 엔티티나 속성**을 따로 둡니다.

**구조와 예시**
```
대분류 1 ──< M 중분류 1 ──< M 소분류
```
| 대분류코드 | 중분류코드 | 소분류코드 | 소분류명 |
|---|---|---|---|
| 01 상의 | 0101 티셔츠 | 010101 | 반소매 티셔츠 |
| 01 상의 | 0101 티셔츠 | 010102 | 긴소매 티셔츠 |
| 02 가방 | 0201 숄더백 | — | — |

- **장점**: 이해하기 쉽고 조회가 단순합니다. 단계별 통계(대분류별 매출)를 내기 쉽습니다.
- **단점**
  - 단계를 늘리려면 엔티티나 속성을 추가해야 합니다 (구조 변경).
  - "가방 > 숄더백"처럼 **단계가 들쭉날쭉한 트리**를 표현하기 어렵습니다.
- **언제**: 단계가 고정된 분류 (유통업 상품 분류, 공공 분류 코드, 레거시 시스템)
- **무신사라면**: △ 카테고리마다 깊이가 다를 수 있어 맞지 않을 수 있습니다.

### 2. 재귀적 관계형 (순환 관계, 자기 참조)
> PPT 용어: **재귀적 관계** (관계 유형 중 하나, 물리 모델링의 관계 설계에서 "계층 관계를 표현할 때 사용")
> 다른 이름: 순환 관계, 자기 참조, 셀프 조인, 인접 목록(Adjacency List, PPT 외)

**정의**: 카테고리 엔티티 하나에 **상위카테고리번호** 속성을 두고, 이 속성이 **같은 엔티티의 카테고리번호를 참조**합니다.
```
카테고리 ─┐
   ▲      │ 상위카테고리번호 (참조 키 → 자기 자신)
   └──────┘
```

**해결하는 문제 (대중소 고정 단계형과 비교)**
| 상황 | 대중소 고정 단계형 | 재귀적 관계형 |
|---|---|---|
| 4단계가 필요해짐 | 엔티티나 속성 추가 (구조 변경) | **인스턴스만 추가** |
| "가방 > 숄더백"은 2단계, "상의 > 티셔츠 > 반소매"는 3단계 | 빈 단계가 생김 | 자연스럽게 표현 |
| 티셔츠를 상의에서 아우터 아래로 이동 | 코드 체계 전체를 재부여 | **상위카테고리번호 하나만 수정** |

**구조와 예시 데이터**
| 카테고리번호 | 상위카테고리번호 | 카테고리명 | 정렬순서 |
|---|---|---|---|
| 1 | NULL | 상의 | 1 |
| 2 | 1 | 티셔츠 | 1 |
| 3 | 1 | 셔츠 | 2 |
| 4 | 2 | 반소매 티셔츠 | 1 |
| 5 | 2 | 긴소매 티셔츠 | 2 |
| 6 | NULL | 가방 | 2 |
| 7 | 6 | 숄더백 | 1 |

- 상위카테고리번호가 NULL이면 **최상위(루트)** 입니다.

**재귀 쿼리가 동작하는 원리**: "상의(1)의 모든 하위 카테고리"를 구할 때
| 반복 | 하는 일 | 찾은 행 |
|---|---|---|
| 시작 (앵커) | 카테고리번호 = 1 | 상의(1) |
| 1회차 | 상위번호가 1인 행 | 티셔츠(2), 셔츠(3) |
| 2회차 | 상위번호가 2 또는 3인 행 | 반소매(4), 긴소매(5) |
| 3회차 | 상위번호가 4 또는 5인 행 | 없음 → **종료** |

표준 SQL (Oracle 11gR2 이상, PostgreSQL·MySQL 8 이상은 `WITH RECURSIVE`)
```sql
WITH sub (category_id, category_name, lvl) AS (
  SELECT category_id, category_name, 1            -- 앵커: 시작점
  FROM category WHERE category_id = 1
  UNION ALL
  SELECT c.category_id, c.category_name, s.lvl + 1 -- 재귀: 자식 찾기
  FROM category c JOIN sub s ON c.parent_category_id = s.category_id
)
SELECT * FROM sub;
```

Oracle 전용 계층 쿼리 (CONNECT BY)
```sql
SELECT LEVEL, LPAD(' ', (LEVEL-1)*2) || category_name AS tree,
       SYS_CONNECT_BY_PATH(category_name, ' > ') AS path
FROM category
START WITH parent_category_id IS NULL               -- 루트부터
CONNECT BY PRIOR category_id = parent_category_id   -- 부모 → 자식 방향
ORDER SIBLINGS BY sort_order;
```
| LEVEL | tree | path |
|---|---|---|
| 1 | 상의 | > 상의 |
| 2 | 　티셔츠 | > 상의 > 티셔츠 |
| 3 | 　　반소매 티셔츠 | > 상의 > 티셔츠 > 반소매 티셔츠 |

- `LEVEL`(깊이), `SYS_CONNECT_BY_PATH`(경로), `CONNECT_BY_ISLEAF`(최하위 여부), `NOCYCLE`(순환 방지)을 바로 쓸 수 있습니다.

반대 방향: 상위 경로 조회 (브레드크럼) — "반소매 티셔츠(4)"에서 루트까지
```sql
SELECT category_name FROM category
START WITH category_id = 4
CONNECT BY PRIOR parent_category_id = category_id;   -- 자식 → 부모 방향
```
→ 반소매 티셔츠, 티셔츠, 상의

- **장점**
  - 구조가 가장 단순합니다 (속성 하나 추가).
  - 깊이에 제한이 없습니다.
  - 추가와 이동이 쉽습니다.
  - 참조 무결성으로 "존재하지 않는 부모"를 막을 수 있습니다.
- **단점**
  - 하위 전체 조회와 경로 조회에 재귀 쿼리가 필요합니다.
  - **순환 참조**(A의 부모가 B, B의 부모가 A)를 참조 무결성만으로는 막지 못합니다.
  - 트리가 크고 조회가 아주 많으면 반복 재귀가 부담이 됩니다.
- **함께 정하는 것**
  | 항목 | 내용 |
  |---|---|
  | 순환 방지 | 이동할 때 "새 부모가 자기 자손이 아닌지" 검사. Oracle은 `NOCYCLE`로 조회 시 무한 루프 방지 |
  | 깊이 제한 | 예: 최대 4단계 |
  | 루트 표현 | 상위번호 NULL vs 가상 루트(0번) 하나 두기 |
  | 인덱스 | 상위카테고리번호에 인덱스 (자식 찾기가 재귀의 핵심 연산) |
  | 성능 보완 | 깊이와 경로를 함께 저장 → 8번 혼합형 |
- **언제**: 대부분의 쇼핑몰 카테고리. **가장 기본이 되는 유형**
- **무신사라면**: ✅ 기본 구조로 적합

### 3. 계층 코드형 (자릿수 코드)
**정의**: 코드의 **자릿수 자체가 계층**을 나타냅니다. 하나의 엔티티에 모든 단계를 넣고 단계 속성을 둡니다.

| 카테고리코드 | 카테고리명 | 단계 |
|---|---|---|
| 01 | 상의 | 1 |
| 0101 | 티셔츠 | 2 |
| 010101 | 반소매 티셔츠 | 3 |
| 02 | 가방 | 1 |
| 0201 | 숄더백 | 2 |

**하위 조회**: `WHERE category_cd LIKE '01%'`

- **장점**: 코드만 보고 계층을 알 수 있습니다. 조회가 쉽고 엑셀이나 외부 시스템과 주고받기 좋습니다.
- **단점**
  - 단계별 자릿수 제한 (2자리면 단계마다 최대 99개)
  - **카테고리를 이동하면 코드가 바뀌어서**, 그 코드를 참조하는 상품과 주문 데이터까지 영향을 받습니다. 식별자의 **불변성**을 어깁니다.
- **비교**: 1번 고정 단계형을 엔티티 하나로 합친 형태이면서, 4번 경로 저장형의 일종이기도 합니다.
- **언제**: 공공 분류, ERP 품목 분류, 개편이 드문 분류. **국내 SI에서 매우 흔함**
- **실무 팁**: 기본 키는 인조 식별자로 두고, 계층 코드는 **별도 속성(표시용)** 으로 두면 이동 문제를 피할 수 있습니다.

### 4. 경로 저장형 (Path Enumeration, PPT 외)
**정의**: 루트부터 자기까지의 **경로 문자열**을 저장합니다.

| 카테고리번호 | 카테고리명 | 경로 |
|---|---|---|
| 1 | 상의 | /1/ |
| 2 | 티셔츠 | /1/2/ |
| 4 | 반소매 티셔츠 | /1/2/4/ |
| 7 | 숄더백 | /6/7/ |

**하위 조회**: `WHERE path LIKE '/1/%'`

- **장점**
  - 하위 전체 조회가 LIKE 한 번으로 끝납니다.
  - 브레드크럼(상의 > 티셔츠 > 반소매)을 바로 만들 수 있습니다.
- **단점**
  - 노드를 이동하면 **하위 노드 전체의 경로를 갱신**해야 합니다 (갱신 이상).
  - 경로 문자열은 참조 무결성으로 보장할 수 없습니다.
  - 경로 값 하나에 여러 값이 들어 있으므로 **1정규형(원자성) 관점에서 논란**이 있습니다.
- **언제**: 조회가 많고 이동이 드문 트리
- **무신사라면**: △ 단독으로 쓰기보다 2번과 함께 쓰는 혼합형(8번)으로 활용

### 5. 중첩 집합형 (Nested Set, PPT 외)
**정의**: 트리를 깊이 우선으로 돌면서 각 노드에 **왼쪽값(lft)과 오른쪽값(rgt)** 을 매깁니다. 하위 노드는 부모의 범위 안에 들어갑니다.

| 카테고리번호 | 카테고리명 | lft | rgt |
|---|---|---|---|
| 1 | 상의 | 1 | 10 |
| 2 | 티셔츠 | 2 | 7 |
| 4 | 반소매 티셔츠 | 3 | 4 |
| 5 | 긴소매 티셔츠 | 5 | 6 |
| 3 | 셔츠 | 8 | 9 |

**하위 조회**: `WHERE lft BETWEEN 1 AND 10`

- **장점**: 하위 전체 조회가 매우 빠릅니다.
- **단점**
  - 노드 하나만 추가해도 **그 뒤 노드 전체의 lft, rgt를 다시 계산**해야 합니다.
  - 이해하기 어렵고 잘못되면 복구도 어렵습니다.
- **언제**: 거의 바뀌지 않는 트리 (조직도 스냅샷, 정적 분류)
- **무신사라면**: ❌ 카테고리 개편과 추가가 잦은 쇼핑몰에는 맞지 않습니다.

---

### 6. 중첩 구간형 (Nested Intervals, PPT 외)
- 5번 중첩 집합형을 개선한 방식입니다. 정수 대신 **분수나 실수 구간**을 써서, 노드를 추가해도 다른 노드의 값을 다시 계산하지 않아도 됩니다.
- 이론적으로는 흥미롭지만 실무에서는 거의 쓰지 않습니다. **이름만 알아 두면 충분합니다.**

---

### 7. 클로저 테이블형 (Closure Table, PPT 외)
**정의**: **조상-자손의 모든 관계**를 별도 엔티티에 저장합니다. 자기 자신과의 관계(깊이 0)도 저장합니다.
```
카테고리 1 ──< M 카테고리 경로(조상번호, 자손번호, 깊이)
```
| 조상번호 | 자손번호 | 깊이 |
|---|---|---|
| 1 | 1 | 0 |
| 1 | 2 | 1 |
| 1 | 4 | 2 |
| 2 | 2 | 0 |
| 2 | 4 | 1 |
| 4 | 4 | 0 |

**하위 조회**: `SELECT descendant_id FROM category_closure WHERE ancestor_id = 1`

- **장점**
  - 하위 전체 조회와 상위 경로 조회가 모두 조인 한 번으로 끝납니다.
  - 참조 무결성으로 보장할 수 있습니다.
- **단점**
  - 행이 많아집니다 (노드 수 × 평균 깊이).
  - 노드를 이동하면 관계 행을 지우고 다시 넣어야 합니다.
- **언제**: 트리 조회가 아주 많고 깊이가 깊을 때 (댓글 트리, 대규모 분류)
- **무신사라면**: △ 카테고리 깊이가 3~4단계 정도라면 과할 수 있습니다.

### 8. 혼합형 (재귀적 관계 + 깊이·경로 파생 속성)
**정의**: 2번 재귀적 관계를 기본으로 하고, 조회용으로 **깊이와 경로를 같이 저장**합니다.

| 카테고리번호 | 상위카테고리번호 | 카테고리명 | 깊이 | 경로 |
|---|---|---|---|---|
| 1 | NULL | 상의 | 1 | /1/ |
| 2 | 1 | 티셔츠 | 2 | /1/2/ |
| 4 | 2 | 반소매 티셔츠 | 3 | /1/2/4/ |

- **장점**
  - 상위카테고리번호(참조 키)로 참조 무결성을 보장합니다.
  - 하위 조회는 경로로 빠르게 합니다.
- **단점**: 깊이와 경로는 **파생 속성**이라 부모번호와 어긋나지 않게 관리해야 합니다. PPT 용어로 **역정규화** 또는 **중복 컬럼 추가**입니다.
- **언제**: 실무 쇼핑몰에서 흔한 절충안
- **무신사라면**: △ 성능이 필요할 때 물리 모델링 단계에서 적용

### 9. DBMS 전용 기능
| DBMS | 기능 | 특징 |
|---|---|---|
| PostgreSQL | `ltree` 확장 | 경로 저장형을 DB가 지원 (`'상의.티셔츠.반소매'`), 전용 인덱스와 연산자 |
| SQL Server | `hierarchyid` 타입 | 계층 위치를 이진값으로 저장, 전용 함수 제공 |
| Oracle | `CONNECT BY` 구문 | 별도 타입은 없지만 재귀적 관계형 조회를 강력하게 지원 |

- **장점**: 성능과 편의 기능이 좋습니다.
- **단점**: 특정 DBMS에 묶입니다.

### 11. 상품 연결 방식
**해결하는 문제**: "후드 집업"은 아우터인가요, 상의인가요?

| 방식 | 구조 | PPT 용어 | 장점 | 단점 |
|---|---|---|---|---|
| 11-a. 단일 소속 | 상품.카테고리번호 | 기본 관계, 1:M | 단순함. 카테고리별 통계가 명확함 | 여러 카테고리에 노출할 수 없음 |
| 11-b. 다중 소속 | 상품 카테고리(상품번호 + 카테고리번호) | M:N 해소, 교차 엔티티 | 여러 카테고리에 노출 가능 | 통계가 중복 집계될 수 있음 |
| 11-c. 다중 소속 + 대표 | 11-b + 대표여부 (또는 상품.대표카테고리번호) | M:N 해소 + 기본 관계 | 노출은 여러 곳에, 통계와 수수료는 대표 기준으로 | 대표가 1개라는 규칙을 관리해야 함 |

**함께 정할 규칙**: 상품은 **최하위(leaf) 카테고리에만** 연결할 수 있는가?
- 대부분의 쇼핑몰은 최하위에만 연결합니다. 그래야 "상의" 같은 상위 카테고리에 상품이 애매하게 섞이지 않습니다.

### 12. 표준 카테고리 / 전시 카테고리 분리형
**정의**: **관리용 분류(표준)** 와 **매장에 보이는 분류(전시)** 를 별도 트리로 둡니다.

**해결하는 문제**
- 상품 분류는 안정적이어야 합니다 (수수료, 통계, 상품정보고시 기준).
- 반면 매장 메뉴는 자주 바뀝니다 (시즌 기획, 전문관, "여름 필수템" 같은 테마).
- 하나의 트리로 둘 다 처리하면 매장 메뉴를 개편할 때마다 상품 분류가 흔들립니다.

**구조**
```
표준 카테고리(트리) 1 ──< M 상품                       ← 상품마다 1개, 관리 기준
전시 카테고리(트리) ──< 전시 카테고리 구성 >── 표준 카테고리   ← 노출용, 자주 바뀜
                  ──< 전시 카테고리 상품 >── 상품
```

**예시**
| 전시 카테고리 | 연결된 것 |
|---|---|
| 아울렛 > 상의 | 표준 "상의" 하위 전체 + 할인 조건 |
| 부티크 > 가방 | 표준 "가방" 중 부티크 판매자 상품 |
| 여름 필수템 | 상품 직접 지정 |

- **장점**: 매장 개편과 상품 관리가 서로 영향을 주지 않습니다.
- **단점**: 트리가 2개라 관리 포인트가 늘어납니다.
- **언제**: 전문관, 기획전, 다채널 운영이 있는 중대형 커머스
- **무신사라면**: ✅ 아울렛, 부티크, 뷰티 같은 전문관이 있으므로 검토 가치가 큼 (📰 전문관 운영 / 💭 내부 구조는 추론)

### 13. 카테고리 속성 정의형
**정의**: 카테고리마다 **상품이 가져야 할 속성 목록**을 정의합니다.

**해결하는 문제**
- 상의는 실측 항목이 "총장, 어깨너비, 가슴단면"입니다.
- 하의는 "허리단면, 허벅지, 밑단"입니다.
- 신발은 "발볼, 굽높이"입니다.
- 필터 항목(핏, 소재, 기장)도 카테고리마다 다릅니다.

**구조**
```
카테고리 1 ──< M 카테고리 속성(카테고리번호, 속성코드, 필수여부, 정렬순서)
속성 1 ──< M 속성값(속성코드, 값)        예: 핏 → 슬림/레귤러/오버
```
| 카테고리 | 속성 | 필수 |
|---|---|---|
| 상의 | 총장, 어깨너비, 가슴단면, 소매길이 | Y |
| 하의 | 총장, 허리단면, 허벅지단면, 밑단단면 | Y |
| 상의 | 핏(필터) | N |

- **장점**: 카테고리에 맞는 입력 화면과 필터를 데이터로 관리할 수 있습니다.
- **단점**: 구조가 EAV(고객 유형 9번)에 가까워져 복잡해집니다.
- **상위에서 상속**: "상의"에 정의한 속성을 "반소매 티셔츠"가 물려받을지 정해야 합니다.
- **무신사라면**: ✅ 실측 사이즈표와 필터가 핵심 기능이라 필요. 다만 **4회차(상품)와 강하게 연결**되므로 거기서 함께 다룹니다.

## 2. 추천 조합과 재검토

처음 제안한 조합은 **2번 재귀적 관계 기반 8번 혼합형 + 11-c 다중 소속·대표 + 12번 표준/전시 분리**였습니다.
테이블을 설계하면서 다시 검토해 보니 두 군데를 고치는 것이 낫습니다.

| 처음 제안 | 재검토 결과 | 이유 |
|---|---|---|
| 11-c 다중 소속 + 대표 | **11-a 단일 소속** (표준 카테고리 기준) | 12번 전시 카테고리가 이미 "여러 곳에 노출"을 담당합니다. 표준 쪽까지 다중 소속으로 만들면 **같은 문제를 두 군데서 해결**하게 되어 중복(최소성 위반)입니다 |
| 8번 혼합형 (깊이·경로 저장) | **2번 재귀적 관계** (깊이·경로는 저장하지 않음) | 카테고리는 수백 건 규모라 재귀 쿼리 비용이 작습니다. 깊이와 경로는 **파생 속성**이고, 저장하면 이동할 때 **갱신 이상**이 생깁니다. 성능 문제가 확인되면 물리 모델링에서 역정규화로 추가합니다 |

**최종 추천 조합**: **2. 재귀적 관계** + **11-a. 단일 소속** + **12. 표준/전시 분리** (+ 3번 계층 코드는 표시용 속성으로만 활용 여부를 컬럼 확인에서 결정)

## 3. 테이블 설계 (논리 모델링 절차)

PPT의 논리 모델링 절차 순서로 진행합니다.
> 엔티티 도출 및 식별 → 엔티티 정의 → 관계 도출 및 정의 → 속성 도출 및 정의 → 식별자 지정 → 도메인 지정 → 데이터 모델 검토

### 3-1. 엔티티 도출 및 식별
| 엔티티 | 분류 (PPT) | 설명 |
|---|---|---|
| **표준 카테고리** | 핵심 엔티티 (유형 및 분류) | 상품을 관리하는 기준 분류 |
| **전시 카테고리** | 핵심 엔티티 (유형 및 분류) | 매장 메뉴, 전문관, 테마 기획 등 고객에게 보이는 분류 |
| **전시 카테고리 구성** | 파생 엔티티 (교차) | 전시 카테고리 M:N 표준 카테고리를 해소 |
| **전시 카테고리 상품** | 파생 엔티티 (교차) | 전시 카테고리 M:N 상품을 해소 (상품은 4회차에서 설계) |
| 카테고리 속성 | — | ⏸ 4회차(상품)에서 설계 |
| 카테고리 변경 이력 | 파생 엔티티 (이력) | ❓ 컬럼 확인 10번에서 결정 |

### 3-2. 엔티티 정의
| 엔티티 | 정의 | 발생 규칙 |
|---|---|---|
| 표준 카테고리 | 상품을 하나의 기준으로 분류하기 위한 계층형 분류 체계 | 운영자가 등록. 최대 4단계. 상품은 최하위 카테고리 1개에만 속함 |
| 전시 카테고리 | 고객 화면(메뉴, 전문관, 기획)에 노출하기 위한 계층형 분류 체계 | 운영자가 등록. 노출 기간을 가질 수 있음 |
| 전시 카테고리 구성 | 전시 카테고리에 어떤 표준 카테고리의 상품을 보여 줄지 정한 연결 정보 | 전시 카테고리 하나에 표준 카테고리 0개 이상 |
| 전시 카테고리 상품 | 전시 카테고리에 직접 지정한 상품 | 테마 기획처럼 표준 분류로 묶이지 않는 상품 모음 |

### 3-3. 관계 도출 및 정의
| 관계 | 관계 유형 | 관계수 | 선택성 | 식별자 상속 | 설명 |
|---|---|---|---|---|---|
| 표준 카테고리 → 표준 카테고리 (상위-하위) | **재귀적 관계** | 1:M | 선택-선택 (최상위는 부모가 없고, 최하위는 자식이 없음) | 비식별 관계 | 상위카테고리번호 |
| 전시 카테고리 → 전시 카테고리 (상위-하위) | **재귀적 관계** | 1:M | 선택-선택 | 비식별 관계 | 상위전시카테고리번호 |
| 전시 카테고리 → 전시 카테고리 구성 | 기본 관계 | 1:M | 필수-선택 | **식별 관계** | M:N 해소 |
| 표준 카테고리 → 전시 카테고리 구성 | 기본 관계 | 1:M | 필수-선택 | **식별 관계** | M:N 해소 |
| 전시 카테고리 → 전시 카테고리 상품 | 기본 관계 | 1:M | 필수-선택 | **식별 관계** | M:N 해소 |
| 상품 → 전시 카테고리 상품 | 기본 관계 | 1:M | 필수-선택 | **식별 관계** | 상품은 4회차 |
| 표준 카테고리 → 상품 | 기본 관계 | 1:M | 카테고리 쪽 선택, 상품 쪽 필수 | 비식별 관계 | 상품.카테고리번호 (4회차) |

**관계도**
```
                 ┌──────────┐
                 ▼          │ 상위 (재귀적 관계)
          [표준 카테고리] ───┘
            │1        │1
            │         └──────────────< M [상품] (4회차, 비식별)
            │
            └─< M [전시 카테고리 구성] >M ─┐
                                          │1
                 ┌──────────┐             │
                 ▼          │ 상위        │
          [전시 카테고리] ───┘─────────────┘
                  │1
                  └─< M [전시 카테고리 상품] >M ── 1 [상품] (4회차)
```

**검토 포인트: 상호배타적 관계인가?**
전시 카테고리는 "표준 카테고리 연결"과 "상품 직접 지정" 두 가지로 내용을 채웁니다. 둘 중 하나만 허용하면 PPT의 **상호배타적 관계**가 됩니다.
- 추천: **둘 다 허용 (배타 아님)**. 예를 들어 전문관에서 "표준 상의 전체 + 추천 상품 몇 개"를 함께 보여 줄 수 있습니다. 규칙도 단순해집니다. (컬럼 확인 8번)

### 3-4. 속성 도출·식별자 지정·도메인 지정 (테이블 정의)

**표기**
- 도메인: 번호, 명, 코드, 여부(Y/N), 일시, 숫자

- 키: PK(기본 키), FK(참조 키), AK(대체 식별자)
- 시스템 컬럼: PPT 기준 **테이블 마지막에 4개**(등록자ID, 등록일시, 수정자ID, 수정일시)를 추가합니다. 아래 표에서는 생략했습니다. (1회차 고객 문서에도 4개로 통일함)

### 3-5. 데이터 모델 검토

**제약 조건 (PPT 4가지)**
| 제약 | 적용 |
|---|---|
| 키 제약조건 | 모든 PK 중복 금지. 대체 식별자: 카테고리코드, (상위카테고리번호 + 카테고리명) |
| 실체 무결성 | PK와 필수 속성 NOT NULL |
| 영역 무결성 | 여부 속성은 Y/N, 전시유형코드는 정해진 코드값, 노출종료일시 ≥ 노출시작일시 |
| 참조 무결성 | 상위카테고리번호는 NULL이거나 존재하는 카테고리번호. 교차 엔티티의 FK는 모두 존재하는 값 |

**참조 무결성으로 막지 못하는 것 (업무 규칙으로 관리)**
- **순환 참조**: 상의의 부모를 반소매 티셔츠로 바꾸면, 참조 무결성은 통과하지만 트리가 순환합니다.
- **최대 깊이**: 5단계 카테고리 생성
- **최하위에만 상품 연결**

**함수 종속과 정규화**
| 점검 | 결과 |
|---|---|
| 1정규형 (원자성) | ✅ 경로 속성을 저장하지 않아 다중 값 문제 없음 |
| 2정규형 (부분 종속) | ✅ 교차 엔티티의 하위포함여부, 정렬순서는 (전시카테고리번호 + 카테고리번호) 전체에 종속 |
| 3정규형 (이행 종속) | ✅ 깊이·경로는 상위카테고리번호를 거쳐 결정되는 값이라 저장하지 않음 |
| 갱신 이상 | ✅ 상품에는 카테고리명을 저장하지 않고 카테고리번호(FK)만 둠 → 카테고리명을 바꿔도 상품 수정 불필요 |

**시나리오 검증**
| # | 시나리오 | 결과 |
|---|---|---|
| 1 | "티셔츠"를 "아우터" 아래로 이동 | ✅ 상위카테고리번호 하나만 수정 (경로를 저장하지 않으므로 갱신 이상 없음) |
| 2 | 상의의 부모를 반소매 티셔츠로 변경 | ⚠ 순환 참조. 업무 규칙(이동 전 자손 여부 검사)으로 막아야 함 |
| 3 | 하위 카테고리가 있는 카테고리 삭제 | ✅ 참조 무결성 위반으로 막힘 → 사용여부 N으로 처리 |
| 4 | 상품이 연결된 카테고리 삭제 | ✅ 같은 방식 |
| 5 | 같은 부모 아래 "티셔츠"를 하나 더 생성 | ✅ 대체 식별자(상위카테고리번호 + 카테고리명)로 막힘. ⚠ 단, **최상위끼리는 상위카테고리번호가 NULL이라 막히지 않을 수 있음** (확인 3번) |
| 6 | "아울렛 > 상의" 전문관 구성 | ✅ 전시 카테고리 구성에 표준 "상의" + 하위포함여부 Y. ⚠ 할인 상품만 보여 주는 조건은 보류 |
| 7 | "여름 필수템" 기획 | ✅ 전시 카테고리 상품에 직접 지정 |
| 8 | 크리스마스 기획 메뉴를 12월에만 노출 | ✅ 노출시작일시, 노출종료일시 |
| 9 | 5단계 카테고리 생성 | ⚠ 업무 규칙(최대 4단계)으로 검사 |

## 4. 컬럼 확인 포인트 (자체 검토 후 확정)

추천안을 하나씩 다시 검토했습니다. 11개 모두 추천안대로 확정하되, 검토 과정에서 **보완이 필요한 업무 규칙 4개**를 찾아 5장에 추가했습니다.

| # | 쟁점 | 확정 | 검토 내용 |
|---|---|---|---|
| 1 | 깊이·경로·최하위여부 (파생 속성) | **저장 안 함** | 카테고리는 수백 건 규모라 재귀 쿼리(Oracle `CONNECT BY`) 비용이 작음. 저장하면 이동 시 하위 전체를 갱신해야 하는 갱신 이상이 생김. 성능 문제가 확인되면 물리 모델링에서 역정규화 |
| 2 | 최상위 표현 | **상위카테고리번호 NULL** | 참조 무결성 정의(NULL이거나 존재하는 값)에 그대로 맞음. 가상 루트는 의미 없는 인스턴스가 하나 생김 |
| 3 | 최상위끼리 이름 중복 | **금지** | 대체 식별자(상위카테고리번호 + 카테고리명)는 NULL 때문에 최상위끼리를 막지 못함 → 업무 규칙 + 물리 단계의 조건부 유일 인덱스로 보완 |
| 4 | 카테고리코드 | **추가** | URL, 외부 연동에 쓰는 **불변** 코드. 계층 의미를 넣으면 이동할 때 바뀌므로(식별자 불변성 위반) 의미 없는 코드로 둠 |
| 5 | 삭제 처리 | **사용여부 N** | 하위나 상품이 있으면 참조 무결성 때문에 어차피 삭제할 수 없음. ➕ 검토 중 발견: **상위가 미사용이면 하위도 노출하지 않는다**, **미사용 카테고리에 신규 상품을 연결할 수 없다** 규칙이 필요 |
| 6 | 상품 연결 | **최하위만** | ➕ 검토 중 발견: 최하위였던 카테고리에 하위를 새로 만들면 기존 상품이 상위 카테고리에 남게 됨 → **하위를 만들려면 기존 상품을 먼저 하위로 옮겨야 한다** 규칙이 필요 |
| 7 | 전시유형코드 | **MENU / SHOP / THEME** | 매장 메뉴, 전문관, 테마 기획을 구분. ➕ 검토 중 발견: **하위 전시 카테고리는 상위와 같은 유형**이어야 트리가 섞이지 않음 |
| 8 | 전시 카테고리 구성 방식 | **표준 연결과 상품 직접 지정 둘 다 허용** | 상호배타적 관계로 만들면 "상의 전체 + 추천 상품" 같은 구성을 못 함. 같은 상품이 두 경로로 중복 노출될 수 있으므로 조회할 때 중복 제거 |
| 9 | 전문관 노출 조건 (할인, 판매자) | **보류** | 상품 가격, 판매자, 프로모션이 정해진 뒤 설계 |
| 10 | 카테고리 변경 이력 | **관리 안 함** | 개편이 드묾. 최종 변경은 시스템 컬럼(수정자ID, 수정일시)으로 추적. 상품의 카테고리 변경 이력은 상품 회차에서 판단 |
| 11 | 시스템 컬럼 | **PPT 기준 4개로 통일** | `created_by`, `created_at`, `updated_by`, `updated_at`. 이력 테이블에도 일관성을 위해 모두 둠. 등록자는 고객·판매자·관리자·시스템이 모두 될 수 있으므로 FK를 걸지 않음. **1회차 고객 문서에도 반영 완료** |

## 5. 업무 규칙과 다음 회차로 넘긴 항목

### 키 구조만으로는 보장되지 않는 업무 규칙
- 카테고리를 이동할 때 새 부모가 자기 자손이면 안 된다 (순환 방지)
- 표준 카테고리는 최대 4단계다
- 상품은 표준 카테고리의 최하위에만 연결한다
- 최상위 카테고리끼리도 이름이 중복되면 안 된다
- 노출종료일시는 노출시작일시보다 늦어야 한다
- ➕ 상위 카테고리가 미사용이면 하위 카테고리도 노출하지 않는다
- ➕ 미사용 카테고리에는 신규 상품을 연결할 수 없다
- ➕ 상품이 연결된 최하위 카테고리에 하위를 만들려면, 기존 상품을 먼저 하위 카테고리로 옮겨야 한다
- ➕ 하위 전시 카테고리의 전시유형코드는 상위와 같아야 한다
