# 02. 카테고리

카테고리 영역의 학습·설계 문서. 프로젝트 공통 규칙은 [00_공통규칙.md](00_공통규칙.md)를 따른다.

- ②는 기법 자체를 설명하고, ③은 우리 프로젝트의 선택과 근거를, ④는 그 결과인 테이블 설계를 담는다. 같은 내용을 반복하지 않도록 ③과 ④는 ②의 절 번호를 참조한다.
- `▲`는 아직 정해지지 않은 업무 규칙이나 가정이다.

---

## ① 영역 개요 및 요구사항

### 1.1 역할
카테고리 영역은 "상품을 어떤 분류 체계로 찾고 보여줄 것인가"를 다룬다. 분류 체계(계층)와 상품이 그 분류에 속하는 관계를 관리한다. 상품 목록 탐색과 상품 등록이 모두 이 영역을 참조한다.

### 1.2 공개 기능과 프로젝트 가정
상의·하의처럼 대분류 아래 소분류로 상품을 탐색하는 기능은 무신사를 비롯한 패션 쇼핑몰에서 일반적으로 제공된다. 다만 무신사의 실제 분류 깊이, 한 상품이 여러 카테고리에 속하는지, 내부 DB 구조는 확인하지 않았다. 아래 업무 규칙은 모두 **이 프로젝트가 정한 가정**이다.

### 1.3 범위
| 구분 | 내용 |
|---|---|
| 포함 | 카테고리(2단계 계층, 이름·노출 순서·노출 여부), 상품-카테고리 소속(N:M) |
| 다른 영역 | 상품 테이블(`product`) 자체와 `product_category.product_id`의 FK 제약(상품), 카테고리별 필터·속성(상품) |
| 확장 후보 | 카테고리 이동·병합, 3단계 이상으로의 확장, 상위 카테고리 비노출의 하위 전파 규칙, 카테고리별 노출 기간 |

### 1.4 확정한 업무 규칙
| 규칙 | 내용 |
|---|---|
| C1 계층 | 카테고리는 자기 참조 관계로 관리하고 **최대 2단계**(최상위 + 하위)로 제한한다. |
| C2 소속 | 상품과 카테고리는 N:M이다. 상품 하나가 여러 카테고리에 속할 수 있고 개수 제한은 없다. |
| C3 연결 대상 | 상품은 **2단계 카테고리(`parent_id IS NOT NULL`)에만** 연결한다. 상위 카테고리의 상품 목록은 그 아래 하위 카테고리에 속한 상품을 조회해서 보여주므로 상위에는 연결하지 않는다. |
| C4 이름 | 같은 부모 아래에서 카테고리 이름은 중복될 수 없다. |
| C5 노출 | 카테고리에는 표시 순서와 노출 여부가 있다. 노출 여부는 삭제와 별개다. |
| C6 삭제 | 하위 카테고리나 소속 상품이 있는 카테고리는 삭제할 수 없다. 숨기려면 노출 여부를 끈다. |
| 애플리케이션 검증 | 최대 2단계, 순환 방지, C3(연결 대상)는 애플리케이션이 검증한다. |

## ② 주요 데이터 모델링 기법

### 2.1 계층 구조 표현
**해결하려는 문제**: 대분류 → 소분류 같은 트리를 관계형 테이블에 어떻게 담을 것인가.

| 방식 | 구조 | 특징 |
|---|---|---|
| 인접 목록 | 각 행이 부모 ID(`parent_id`)를 가짐 | 가장 단순하고 이동·추가가 쉽다. 깊이가 정해지지 않은 트리의 "전체 하위 조회"는 재귀 쿼리가 필요하다 |
| 경로 열거 | 각 행이 경로 문자열(`/1/5/12`)을 가짐 | 하위 조회가 `LIKE '/1/5/%'`로 쉽다. 경로가 문자열이라 FK로 보호되지 않고, 이동 시 하위 전체의 경로를 고쳐야 한다 |
| 중첩 집합 | 각 행이 좌·우 번호 범위를 가짐 | 하위 조회가 범위 비교 하나로 빠르다. 노드 추가·이동 때마다 많은 행의 번호가 바뀌어 쓰기가 비싸다 |
| 클로저 테이블 | 모든 조상-자손 쌍을 별도 테이블에 저장 | 임의 깊이 조회와 이동이 모두 유연하다. 테이블이 하나 더 생기고 쌍 관리가 필요하다 |
| 고정 깊이 컬럼 | `level1_id`, `level2_id`처럼 단계마다 컬럼 | 깊이가 확정이면 단순하지만 깊이를 늘리려면 구조를 바꿔야 한다 |

선택은 요구사항에서 갈린다. 변동이 드물고 깊이가 2단계로 작으면 인접 목록으로 충분하다. 임의 깊이의 하위 조회가 잦거나 이동이 많아지면 클로저 테이블 같은 방식을 검토한다.

### 2.2 자기 참조 관계 (인접 목록의 구현)
**원리**: 한 테이블의 FK가 같은 테이블의 PK를 가리킨다. 부모가 없는 행(최상위)은 FK를 NULL로 둔다.

```
category
category_id | parent_id | name
1           | NULL      | 상의          ← 최상위
2           | 1         | 티셔츠        ← 하위 (부모 = 상의)
3           | 1         | 셔츠
4           | NULL      | 하의
5           | 4         | 팬츠
```

- **순환**: 자기 자신을 부모로 지정하면(`parent_id = category_id`) 순환이다. CHECK로 막을 수 있다. 서로를 부모로 삼는 순환(A→B→A)은 CHECK로 막을 수 없다. 이번처럼 **"부모는 최상위여야 한다(최대 2단계)"**를 지키면 구조적으로 순환이 생길 수 없고, 이 검증은 애플리케이션이 한다.
- **삭제**: 자식이 있는 부모를 삭제하면 FK가 거부한다(`ON DELETE`를 지정하지 않는 기본 동작).
- **Oracle의 UNIQUE와 NULL**: 복합 UNIQUE에서 키 컬럼이 모두 NULL인 행은 검사 대상이 아니지만, 일부만 NULL이면 나머지 값이 같을 때 중복으로 본다. 그래서 `UNIQUE (parent_id, name)` 하나로 최상위 카테고리끼리의 이름 중복(`parent_id`가 NULL)도 막는다.

### 2.3 N:M 관계와 교차 테이블
**해결하려는 문제**: 상품 하나가 여러 카테고리에 속하고, 카테고리 하나에 여러 상품이 속한다. 관계형 모델은 한 컬럼에 여러 값을 담을 수 없으므로([01_고객.md](01_고객.md) 2.3의 원자성 문제와 같은 이유다) N:M을 직접 표현하지 못한다.

**원리**: N:M을 두 개의 1:N으로 풀어 **교차 테이블**(연결 테이블)로 표현한다.

```
product            product_category                category
product_id         product_id | category_id         category_id
101                101        | 2                   2  티셔츠
102                101        | 5                   5  팬츠
                   102        | 2
```
상품 101은 티셔츠와 팬츠에 속하고, 카테고리 2(티셔츠)에는 상품 101과 102가 속한다.

한쪽에 컬럼을 늘리는 방식(`category_id1`, `category_id2`)은 개수에 상한이 생기고 조회가 복잡해지므로 쓰지 않는다. 교차 테이블은 관계 자체의 속성(연결 일시 등)도 담을 수 있다.

### 2.4 교차 테이블의 식별자
| 방식 | 구조 | 특징 |
|---|---|---|
| 복합 PK | `PK (product_id, category_id)` | **같은 쌍의 중복을 PK가 막는다.** 별도 대리키와 UNIQUE가 필요 없다. 다른 테이블이 교차 행을 참조하면 그 FK도 복합이 된다 |
| 대리키 + UNIQUE | `PK (id)` + `UNIQUE (product_id, category_id)` | 교차 행을 다른 테이블이 단일 컬럼으로 참조할 수 있다. 컬럼과 인덱스가 하나 더 든다 |

복합 PK는 기본으로 검토할 수 있는 방식이지 모든 교차 테이블에 강제하는 규칙이 아니다. 교차 행을 다른 테이블이 참조하거나, 같은 쌍이 반복될 수 있거나(예: 기간별 소속), 교차 행에 독립적인 속성·생명주기가 있으면 대리키가 더 맞을 수 있다.

**인덱스의 선두 컬럼**: 복합 PK `(product_id, category_id)`의 인덱스는 `product_id`로 시작하므로 "상품의 카테고리 조회"에는 쓰이지만 "카테고리의 상품 조회"에는 쓰이지 않는다. 후자를 위한 인덱스는 따로 둔다.

## ③ 설계 대안 비교 및 선택

### 3.1 계층 구조 (C1)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| **인접 목록**(자기 참조, 테이블 1개), 최대 2단계 | 깊이가 2단계로 고정이고 변동이 드물다. 2단계에서는 "하위 목록"이 `parent_id = :id` 한 번의 조회라 재귀 쿼리도 필요 없다 (2.1) | 경로 열거·중첩 집합·클로저 테이블은 임의 깊이 조회·이동을 위한 장치라 이번 요구사항에는 과하다. 고정 깊이 컬럼은 깊이를 늘릴 때 구조를 바꿔야 한다 |

- 최대 2단계, 순환 방지는 애플리케이션이 검증한다(C1). 2단계 제한이 지켜지면 순환은 구조적으로 생기지 않는다(2.2).
- 깊이를 늘려야 하면 인접 목록을 유지하고 재귀 쿼리를 쓰거나 클로저 테이블 도입을 검토한다. 이 경우 C3(연결 대상)의 정의도 함께 다시 정해야 한다.

### 3.2 상품-카테고리 관계와 식별자 (C2, C3)
| 항목 | 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|---|
| 관계 | **N:M**, 교차 테이블 `product_category` (2.3) | 상품 하나를 여러 하위 카테고리에서 찾을 수 있게 한다. 같은 대분류든 다른 대분류든 제한하지 않는다 | 1:N(상품의 `category_id` 하나): 구조가 가장 단순하지만 여러 카테고리 소속을 표현할 수 없다 |
| 연결 대상 | **2단계 카테고리(`parent_id IS NOT NULL`)에만 연결**. 상위 카테고리의 상품은 하위 카테고리를 거쳐 조회 | 상위에도 연결하면 같은 상품이 상위와 하위에 중복 연결되어 어긋날 수 있다 | 상위에도 직접 연결 |
| 식별자 | **복합 PK** `(product_id, category_id)` (2.4) | 교차 행을 다른 테이블이 참조할 계획이 없고, 같은 (상품, 카테고리) 쌍은 한 번만 존재해야 하므로 PK가 중복 방지까지 맡는다. R6의 "M:N 교차 테이블은 예외로 검토"의 첫 적용이다 | 대리키 + UNIQUE: 참조·반복 쌍이 필요하지 않아 컬럼·인덱스만 늘어난다 |
| 대표 카테고리 | **두지 않음** | 현재 대표 카테고리를 쓰는 명확한 업무 요구사항이 없다. 필요해지면 `product_category`에 표시 컬럼을 추가하고 함수 기반 UNIQUE 인덱스로 "상품당 최대 1개"를 보장하는 방식을 검토한다([01_고객.md](01_고객.md) 2.7과 같은 원리) | 처음부터 `primary_yn` 포함 |

- **C3는 "리프(자식 없는 카테고리)에만 연결한다"와 같은 말이 아니다.** 하위 카테고리가 없는 최상위 카테고리도 자식이 없지만, 이 프로젝트는 `parent_id IS NOT NULL`인 카테고리에만 연결한다. 이렇게 정의하면 나중에 최상위 카테고리 아래에 하위를 추가해도 "상위에 상품이 연결된 상태"가 생기지 않는다. 검증도 `parent_id IS NOT NULL` 한 가지로 끝난다. 이 규칙은 선언적 제약으로 표현하기 어려워 애플리케이션이 검증한다.

### 3.3 노출·이름·삭제 (C4~C6)
| 항목 | 선택 | 근거 |
|---|---|---|
| 이름 | `UNIQUE (parent_id, name)` | 같은 부모 아래 이름 중복을 막는다. 서로 다른 부모 아래에는 같은 이름(예: 상의/기타, 하의/기타)이 허용된다. Oracle은 `parent_id`가 NULL인 최상위끼리도 같은 이름을 막는다 (2.2) |
| 노출 | `display_yn` + `display_order` | 숨기는 것과 지우는 것은 다르다. 상품이 연결된 카테고리를 숨겨도 소속 데이터는 그대로 남는다 |
| 삭제 | 자식 카테고리·소속 상품이 **없을 때만 물리 삭제**. FK가 거부 | 카테고리는 보관·복구 요구가 없고, 사용 중인 카테고리는 숨김으로 충분하다. `ON DELETE CASCADE`는 소속이 조용히 사라지므로 쓰지 않는다 |

## ④ 실제 테이블 설계

### 4.1 엔티티 개요
| 테이블 | 논리명 | 역할 | 근거 |
|---|---|---|---|
| category | 카테고리 | 2단계 분류 체계 | 3.1, 3.3 |
| product_category | 상품 카테고리 | 상품-카테고리 N:M 교차 | 3.2 |

`product`(상품)는 상품 영역에서 정의한다. 이 영역에서는 외부 참조로만 표시한다.

공통 표기: 대리키는 `NUMBER(19)`, `GENERATED AS IDENTITY`, 시각은 `TIMESTAMP(6)`, 문자열은 글자 단위(`CHAR`) 길이다. NN은 NOT NULL이다.

### 4.2 테이블 정의

#### category (카테고리)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| category_id | 카테고리 ID | NUMBER(19) | PK |
| parent_id | 상위 카테고리 ID | NUMBER(19) | FK → category, NULL 허용 (NULL이면 최상위) |
| name | 카테고리명 | VARCHAR2(50 CHAR) | NN |
| display_order | 표시 순서 | NUMBER(5) | NN |
| display_yn | 노출 여부 | CHAR(1) | NN, 기본 `'Y'` |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- CHECK `ck_category_display_yn`: `display_yn IN ('Y','N')`
- CHECK `ck_category_parent_self`: `parent_id IS NULL OR parent_id <> category_id` (자기 자신을 부모로 지정 금지)
- UNIQUE `uq_category_parent_id_name`: `(parent_id, name)` (2.2)
- FK `fk_category_parent_id`: `parent_id` → `category (category_id)`, ON DELETE 옵션 없음
- 애플리케이션 검증: 부모는 최상위여야 한다(최대 2단계, 순환 방지).
- `display_order`는 같은 부모 아래에서의 순서이며 유일성은 강제하지 않는다 ▲

#### product_category (상품 카테고리)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| product_id | 상품 ID | NUMBER(19) | PK(복합), FK → product (상품 영역) |
| category_id | 카테고리 ID | NUMBER(19) | PK(복합), FK → category |
| created_at | 연결 일시 | TIMESTAMP(6) | NN |

- PK `pk_product_category`: `(product_id, category_id)` (2.4)
- FK `fk_product_category_category_id`: `category_id` → `category (category_id)`, ON DELETE 옵션 없음
- FK `fk_product_category_product_id`: 상품 영역에서 `product`와 함께 정의한다.
- 애플리케이션 검증: 연결 대상 카테고리는 `parent_id IS NOT NULL`이어야 한다(C3).
- 행을 추가하거나 삭제만 하고 수정하지 않으므로 `updated_at`이 없다. 연결을 바꿀 때는 행을 지우고 새로 추가한다.

### 4.3 관계
| 부모 | 자식 | 카디널리티 | 비고 |
|---|---|---|---|
| category | category | 1 : N (0..1 : 0..N) | 자기 참조. 최상위는 부모 없음, 최대 2단계 |
| category | product_category | 1 : N | 하위(2단계) 카테고리만 연결(애플리케이션 규칙) |
| product | product_category | 1 : N | 상품 영역의 외부 참조. 두 1:N으로 상품-카테고리 N:M을 표현 |

### 4.4 삭제·비활성 정책
| 상황 | 처리 |
|---|---|
| 카테고리를 화면에서 숨김 | `display_yn = 'N'`. 소속 데이터는 유지 |
| 하위 카테고리도 소속 상품도 없는 카테고리 삭제 | 물리 삭제 |
| 하위 카테고리 또는 소속 상품이 있는 카테고리 삭제 | FK가 거부. 하위·소속을 먼저 정리해야 한다 |
| 상품 삭제·비활성 | 상품 영역에서 정한다. `product_category` 행 처리 방식도 그때 정한다 |

### 4.5 정규화 검토
두 테이블 모두 3NF를 만족한다. `product_category`는 키 외 컬럼이 `created_at`뿐이고 이는 키 전체에 종속된다. 의도적인 중복·파생은 없다.

### 4.6 FK 인덱스 검토
공통 규칙(조회 패턴, 부모 행 변경·삭제와 잠금, 기존 인덱스와의 중복)에 따라 검토한다.

| FK 컬럼 | 검토 | 결과 |
|---|---|---|
| category.parent_id | "하위 카테고리 목록" 조회가 있고, `UNIQUE (parent_id, name)`의 선두 컬럼이 대신한다 | UNIQUE 인덱스로 충족 |
| product_category.category_id | "카테고리별 상품 목록" 조회가 있고, 복합 PK는 `product_id`로 시작해 대신할 수 없다 (2.4) | 생성: `(category_id, product_id)` |
| product_category.product_id | 복합 PK의 선두 컬럼이 대신한다 | PK 인덱스로 충족 |

## ⑤ ERD 및 설계 검토

### 5.1 ERD
[erd/02_카테고리.drawio](erd/02_카테고리.drawio) (draw.io에서 열어 수정할 수 있다)

- 카테고리는 핵심 테이블, 교차 테이블은 종속 테이블 색으로 구분하고, 상품 영역에서 정의할 `product`는 회색 외부 참조(PK만 표시)로 그렸다.
- `category`의 자기 참조선(0..1 : 0..N)과 4.3의 관계를 그대로 표현한다.

### 5.2 주요 설계 결정 요약
- 계층은 인접 목록(자기 참조) + 최대 2단계로 하고, 최대 2단계·순환 방지는 애플리케이션이 검증한다.
- 상품-카테고리는 N:M이며 교차 테이블 `product_category`로 표현한다.
- 교차 테이블은 복합 PK를 쓴다. 이는 이번 요구사항에 맞는 선택이며 모든 교차 테이블의 규칙이 아니다.
- 상품은 2단계 카테고리(`parent_id IS NOT NULL`)에만 연결한다. 상위 카테고리의 상품은 하위를 거쳐 조회한다.
- 대표 카테고리는 요구사항이 없어 두지 않았다.

### 5.3 미결정·추후 검토 사항
| 구분 | 내용 |
|---|---|
| 노출 | 상위 카테고리가 비노출일 때 하위 카테고리의 노출 규칙(조회 시 부모의 `display_yn`도 확인할지) ▲ |
| 표시 순서 | 같은 부모 아래 `display_order`의 유일성 강제 여부 ▲ |
| 상품 영역 | `product` 테이블 정의, `product_category.product_id` FK, 상품 삭제·비활성 시 소속 행 처리 |
| 확장 | 3단계 이상 확장(재귀 쿼리·클로저 테이블 검토, C3 재정의), 카테고리 이동·병합, 대표 카테고리, 카테고리별 필터·속성 |

### 5.4 다른 영역과의 연결
| 영역 | 연결 |
|---|---|
| 상품 | `product`가 `product_category`를 통해 카테고리에 연결된다. 상품 등록 시 2단계 카테고리만 선택할 수 있도록 검증한다 |
| 주문·결제 | 카테고리를 직접 참조하지 않는다. 주문 시점의 상품 정보는 주문 영역에서 스냅샷으로 보존한다 |
