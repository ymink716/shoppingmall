# 03. 상품

상품 영역의 학습·설계 문서. 프로젝트 공통 규칙은 [00_공통규칙.md](00_공통규칙.md)를 따른다.

- ②는 기법 자체를 설명하고, ③은 우리 프로젝트의 선택과 근거를, ④는 그 결과인 테이블 설계를 담는다. 같은 내용을 반복하지 않도록 ③과 ④는 ②의 절 번호를 참조한다. 고객·카테고리 영역에서 이미 설명한 기법은 해당 문서의 절을 가리킨다.
- `▲`는 아직 정해지지 않은 업무 규칙이나 가정이다.

## ① 영역 개요 및 요구사항

### 1.1 역할
상품 영역은 "누가, 무엇을, 어떤 단위로 판매하는가"를 다룬다. 판매자와 브랜드, 상품의 기본·상세 정보, 색상·사이즈 같은 옵션 조합(SKU)과 재고, 이미지, 판매 상태를 관리한다. 가격, 장바구니, 주문이 이 영역의 상품과 SKU를 참조하므로 이후 영역의 기준점이 된다.

### 1.2 공개 기능과 프로젝트 가정
브랜드별 상품 탐색, 색상·사이즈 선택, 품절 표시, 상품 상세 정보와 사이즈 안내는 무신사를 비롯한 패션 쇼핑몰에서 일반적으로 제공되는 기능이다. 다만 무신사의 제공 범위, 입점 구조, 내부 DB 구조는 확인하지 않았다. 아래 업무 규칙은 모두 **이 프로젝트가 정한 가정**이다.

### 1.3 범위
| 구분 | 내용 |
|---|---|
| 포함 | 판매자, 판매자 직원 계정, 브랜드, 상품(식별·분류·상태), 상품 상세(소재·제조·보증 정보), SKU(옵션 조합·재고·판매 허용), 상품 이미지 |
| 다른 영역 | 카테고리 계층과 소속(카테고리, 이 영역은 `product_category`의 `product_id` FK만 연결), 가격·할인(가격), 장바구니, 재고 차감과 동시성(주문), 배송 정책·출고지·반품지·정산(확장) |
| 확장 후보 | 직원 역할·권한, 독립 추가 구매 상품, 바코드·GTIN(SKU 단위), 사이즈 실측의 구조화, 재고 입출고 이력, 브랜드 컬렉션 테이블, 옵션 마스터, 쇼핑몰 자체 상품 관리코드 |

### 1.4 확정한 업무 규칙
| 규칙 | 내용 |
|---|---|
| P1 판매 구조 | 판매자 1 : N 브랜드(브랜드는 정확히 한 판매자에 소속), 판매자 1 : N 직원 계정. 상품은 브랜드에 속하고 판매자는 브랜드를 통해 확인한다. 같은 브랜드를 여러 독립 판매자가 취급하는 구조는 제외한다. 직원 계정은 고객 계정과 분리하고 이메일·비밀번호로 로그인하며 역할별 권한은 제외한다. |
| P2 상품 식별 | `product_id`는 내부 식별자, `model_number`는 고객에게 보이는 **브랜드 품번**이다. 같은 브랜드에서 같은 품번으로 상품 페이지를 둘 이상 등록하지 않는다. 브랜드명도 전체에서 중복을 금지한다. 둘 다 이 프로젝트가 채택한 업무 규칙이다. |
| P3 옵션 | 색상·사이즈는 기본 구매 옵션이며 상품에 따라 쓰거나 쓰지 않는다. 판매자가 정의하는 추가 옵션 그룹은 상품당 최대 1개이고, 선택값은 고객이 하나만 고른다. 옵션 값은 판매자가 직접 입력하며 마스터 테이블은 없다. 실제 판매할 조합만 SKU로 만들고, 옵션이 없는 상품도 SKU를 하나 갖는다. |
| P4 재고·판매 허용 | 재고는 SKU별 현재 수량이다. SKU마다 판매 허용 여부가 있다. 품절은 재고 수량에서 계산하고 저장하지 않는다. |
| P5 상품 상태 | `DRAFT → ON_SALE → SUSPENDED ↔ ON_SALE`, `ON_SALE·SUSPENDED → ENDED`, `ENDED → SUSPENDED`. 한 번 게시된 상품은 `DRAFT`로 돌아가지 않는다. `ENDED` 상품은 복구해서 같은 상품·같은 품번으로 재판매할 수 있다. |
| P6 게시 조건 | 게시(`ON_SALE`로 전환)할 때 대표 이미지 정확히 1개, SKU 1개 이상, 추가 옵션과 색상·사이즈 사용 여부의 일관성, 2단계 카테고리 1개 이상 소속, 성별·착용 계절 입력을 확인한다. |
| P7 상품 상세 | 기본정보와 상세정보(긴 설명, 소재, 세탁·취급, 제조·보증 정보)는 1:1로 분리한다. |
| P8 이미지 | 대표·갤러리·상세 설명용 이미지를 한 테이블에서 관리하고 경로만 저장한다. 대표 이미지는 상품당 최대 1개다. |
| P9 사이즈 실측 | 구조화된 테이블로 저장하지 않는다. 사이즈표는 상세 이미지나 상세 설명에 포함한다. |
| P10 삭제 | 판매 이력이 있는 상품은 삭제하지 않고 `ENDED`로 관리한다. `DRAFT`이면서 다른 데이터가 참조하지 않는 상품만 물리 삭제한다. |

## ② 주요 데이터 모델링 기법

### 2.1 상품과 SKU: 보이는 단위와 파는 단위
**해결하려는 문제**: 고객은 "OO 후드티"를 보고 고르지만, 실제로 재고를 세고 주문하는 것은 "OO 후드티 / 블랙 / M"이다.

| 구분 | 상품(product) | SKU |
|---|---|---|
| 의미 | 상품 페이지 하나(이름, 브랜드, 분류, 설명) | 상품 + 옵션 조합 하나, 재고의 최소 단위 |
| 개수 | 1 | 옵션 조합 수만큼 (색상 3 × 사이즈 4 = 12) |
| 참조하는 곳 | 카테고리, 브랜드, 상세 페이지 | 재고, 장바구니, 주문 |

상품만 두면 "블랙 M의 재고 0"을 둘 곳이 없고, 조합마다 상품 행을 만들면 이름·브랜드·카테고리가 반복된다. 그래서 상품 1 : N SKU로 나눈다.

### 2.2 옵션 표현 방식
| 방식 | 구조 | 특징 |
|---|---|---|
| 고정 컬럼 | SKU에 `color_name`, `size_name` 컬럼 | 가장 단순하다. 같은 조합 중복과 같은 종류 값 중복이 구조와 UNIQUE로 해결된다. 옵션 종류를 늘리려면 컬럼을 추가해야 한다 |
| 종류·값 분리 | `option_type`, `option_value`, `sku_option_value` 교차 테이블 | 종류가 몇 개든 행으로 표현한다. 조합 중복과 같은 종류 값 중복을 막으려면 복합 FK·조합 키 같은 추가 장치가 필요하다 |
| EAV | `(sku_id, 속성명, 속성값)` 행 | 가장 유연하지만 값이 모두 문자열이라 타입·제약을 걸 수 없고 조회가 복잡하다 |

이 영역에서는 색상·사이즈의 일부 또는 전부를 쓰는 요구라서 고정 컬럼이 충분하다. 판매자가 정의하는 추가 옵션은 컬럼 하나(`extra_option_value`)와 상품의 그룹 이름 컬럼 하나(`extra_option_name`)로 흡수한다.

### 2.3 복합 UNIQUE와 NULL (Oracle)
**해결하려는 문제**: 옵션이 NULL일 수 있는 SKU에서 같은 조합의 중복을 어떻게 막는가.

Oracle의 복합 UNIQUE는 다음처럼 동작한다.
- 키 컬럼이 **모두** NULL인 행은 검사 대상이 아니다.
- 일부만 NULL이면 NULL이 **아닌** 컬럼 값이 같을 때 중복으로 본다.

```
UNIQUE (product_id, color_name, size_name, extra_option_value)   -- product_id는 NOT NULL
(101, '블랙', 'M',  NULL)  (101, '블랙', 'M',  NULL)  → 중복, 거부
(101, NULL,  NULL, NULL)  (101, NULL,  NULL, NULL)  → 중복, 거부 (product_id가 NULL이 아니므로)
```
`product_id`가 NOT NULL이라 옵션이 모두 NULL인 SKU(옵션 없는 상품)도 상품당 하나만 만들어진다. UNIQUE가 막지 못하는 것은 "상품에 SKU가 최소 하나 있어야 한다"는 규칙이고, 이는 별도로 관리한다. Oracle은 빈 문자열을 NULL로 취급하고 `'블랙'`과 `'블랙 '`은 다른 값이므로 입력값의 공백 제거는 애플리케이션이 맡는다.

같은 원리로 `UNIQUE (brand_id, model_number)`는 `model_number`가 NOT NULL이어야 의도대로 동작한다. NULL을 허용하면 브랜드당 NULL 품번 한 건만 들어간다.

### 2.4 저장 상태와 파생 상태
**해결하려는 문제**: "품절"을 컬럼으로 저장할 것인가, 계산할 것인가.

`sold_out_yn` 같은 컬럼을 두면 `stock_qty`와 같은 사실을 두 곳에 저장하게 되어 어긋날 수 있다(재고는 바꿨는데 품절 컬럼은 그대로). 재고 수량에서 계산할 수 있는 값은 **파생 상태**로 두고 조회 때 계산한다. 반대로 판매자의 의사(판매 중지)는 재고로 알 수 없는 별도의 사실이라 저장한다.

| 구분 | 상태 | 이유 |
|---|---|---|
| 저장 | `sale_yn`(SKU 판매 허용), `product.status` | 판매자·운영자의 결정이며 다른 값으로 유도할 수 없다 |
| 파생 | 품절, 구매 가능 여부 | `stock_qty`와 저장된 상태에서 계산할 수 있다 |

### 2.5 상태 전이와 조건부 필수
상태 컬럼은 값 집합(CHECK)만으로는 **어떤 순서로 바뀌는지**를 표현하지 못한다. 전이 규칙은 애플리케이션이 지키고, 상태와 일관되어야 하는 같은 테이블 안의 컬럼은 CHECK로 보강한다.

- **조건부 필수**: 상태에 따라 필수 여부가 달라지는 컬럼은 NULL을 허용하고 CHECK로 "DRAFT가 아니면 필수"를 표현한다([01_고객.md](01_고객.md) 2.9).
- **이벤트 일시와 상태의 정합성**: `published_at`은 최초 게시 시점이라 `DRAFT`이면 NULL, 그 외에는 값이 있다. 이 CHECK가 성립하려면 게시된 상품이 `DRAFT`로 돌아가지 않는다는 전이 규칙이 전제다.

### 2.6 1:1 수직 분할의 근거
[01_고객.md](01_고객.md) 2.11은 선택 항목이 많고 대부분 비어 있는 경우의 분할을 다뤘다. 상품 상세의 분리 근거는 다르다. **CLOB 컬럼이라서가 아니라**, 상품 목록 조회는 기본정보만 읽고 상세 페이지에서만 상세정보를 읽는 **접근 패턴**이 다르고, 기본정보(분류·상태)와 상세 콘텐츠(설명·제조·보증)의 **관리 책임**이 다르기 때문이다. 부모의 PK를 PK로 쓰는 공유 PK 방식이라 1:1이 구조로 보장되고 별도 대리키가 필요 없다. 분리 비용은 상품 생성 때 두 테이블에 행을 만들어야 한다는 점이다.

### 2.7 한 테이블에서 종류 구분과 "최대 1개"
이미지는 대표·갤러리·상세 설명용으로 역할이 다르지만 속성(경로, 순서)이 같으므로 `image_type` 컬럼으로 구분해 한 테이블에 둔다. "대표는 상품당 최대 1개"는 [01_고객.md](01_고객.md) 2.7의 방식 A처럼 **함수 기반 UNIQUE 인덱스**로 보장한다. 대표 이미지가 정확히 1개여야 한다는 조건은 UNIQUE로 표현할 수 없어 게시 조건(애플리케이션)에서 확인한다. 이미지 파일은 DB가 아닌 파일 저장소에 두고 경로만 저장한다.

### 2.8 값 조합을 코드 하나로 표현하기
착용 계절은 봄·여름·가을·겨울 중 1~4개를 고를 수 있다. 선택은 15가지 조합(4 + 6 + 4 + 1)뿐이므로, 이 영역에서는 교차 테이블 대신 **조합마다 정해진 코드 하나**를 컬럼에 저장한다.

| 방식 | 특징 |
|---|---|
| 조합 코드 컬럼 + CHECK | 구조가 단순하다. 허용 목록 밖의 문자열(`SUMMER_SPRING`처럼 순서가 다른 같은 조합 포함)은 CHECK가 거부한다. 특정 계절 검색은 그 계절을 포함한 모든 코드를 나열해야 한다 |
| 교차 테이블 (`product_season`) | 계절별 검색·집계가 자연스럽다. 테이블과 조인이 늘고, "최소 1개"는 별도 관리가 필요하다 |

이는 여러 계절 선택이라는 요구를 닫힌 집합의 **코드 하나로 취급**하는 의도적 단순화다. 코드를 내부에서 분해해서 쓰지 않는다는 전제이며, 계절별 검색·집계가 중요해지면 교차 테이블로 바꾼다.

### 2.9 구조화할 것인가
사이즈별 실측을 테이블에 저장하면 사이즈 선택 시 치수 표시, 비교, 체형 기반 추천이 가능하다. 그러나 이 기능이 요구사항에 없다면 저장·검증 비용(테이블, 항목 CHECK, 사이즈 문자열 일치 검증)만 늘어난다. 데이터를 구조화할지는 **그 데이터를 검색·비교·계산할 기능이 있는가**로 판단한다. 요구가 생기면 테이블을 추가할 수 있지만, 이미지로 올린 기존 치수는 다시 입력해야 한다.

## ③ 설계 대안 비교 및 선택

### 3.1 판매 구조 (P1)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 판매자 1 : N 브랜드 : N 상품. 브랜드와 판매자를 개념적으로 분리 | 브랜드는 고객에게 보이는 이름이고 판매자는 계약·정산의 주체다. 한 판매자가 여러 브랜드를 운영할 수 있다. 상품은 `brand_id`만 참조하고 판매자는 브랜드를 통해 확인하므로 `product.seller_id`를 두지 않는다(`product → brand → seller` 이행 종속 방지) | 브랜드와 판매자를 한 엔티티로 통합(브랜드 정보가 판매자 행에 반복됨), 브랜드-판매자 N:M(여러 독립 판매자가 같은 브랜드를 취급, 이번 프로젝트에서 제외) |

- 판매자 1 : N 직원 계정. 직원 계정은 고객(`member`)과 다른 주체이고 로그인 방식이 달라 별도 테이블이다. 이메일·비밀번호 로그인만 두고 역할·권한은 확장 후보로 남긴다.
- **구조 결정과 업무 규칙을 구분한다.** "브랜드는 한 판매자에 속한다"는 구조(`brand.seller_id NOT NULL`)이고, "브랜드명은 전체에서 중복 불가"는 별도로 채택한 업무 규칙이다. 후자는 판매자 1:N 관계에서 자동으로 나오지 않는다. 고객 화면에서 브랜드를 이름으로 구분하기 위한 규칙이다.

### 3.2 상품 식별 (P2)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| `product_id`(내부 PK) + `model_number`(브랜드 품번, NOT NULL) + `UNIQUE (brand_id, model_number)` | 고객이 상세 페이지에서 확인하고 다른 곳에서 같은 모델을 검색할 때 쓰는 값이다. 품번은 브랜드가 부여하므로 브랜드와 함께 쓸 때 의미가 있다. 서로 다른 브랜드의 같은 문자열은 허용한다 | 품번 전역 UNIQUE(다른 브랜드의 같은 문자열이 충돌), 판매자 단위 UNIQUE(`product.seller_id` 중복 필요), 쇼핑몰 자체 상품 관리코드(구체적인 업무 목적이 아직 없음) |

- 이 UNIQUE는 `model_number`가 세계적으로 유일한 표준 번호라는 뜻이 아니라 **우리 쇼핑몰의 업무 규칙**이다.
- **전제**: 실제 브랜드는 기본 품번을 여러 색상이나 여러 상품 페이지에서 공유하기도 한다. 이 규칙에서는 같은 품번으로 상품 페이지를 둘 이상 등록할 수 없으므로, 색상 차이는 한 상품 페이지의 SKU 옵션(`color_name`)으로 등록한다.
- 판매 종료(`ENDED`)된 상품도 품번을 계속 점유한다. 같은 품번을 다시 판매하려면 새로 등록하지 않고 기존 상품을 복구한다(3.5).
- `model_number`는 SKU의 식별자가 아니다. 바코드·GTIN은 요구사항이 없어 두지 않으며, 필요하면 SKU 단위에서 검토한다.
- 품번 검색 기능을 만들 때는 `model_number` 단독 인덱스를 검토한다. `UNIQUE (brand_id, model_number)`는 `brand_id`가 선두라 품번만으로 검색할 때는 효율이 낮다.

### 3.3 옵션과 SKU (P3)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| 고정 컬럼(2.2): `sku.color_name`, `size_name`, `extra_option_value` (모두 NULL 허용 문자열)와 `product.extra_option_name`. 마스터 테이블 없음, 값은 판매자가 입력 | 색상·사이즈의 일부 또는 전부를 쓰는 요구는 NULL 허용 컬럼으로 표현된다. 같은 조합의 중복은 복합 UNIQUE 하나로, 같은 종류 값의 중복은 컬럼 구조로 해결된다(2.3) | 종류·값 분리(요구 대비 조인과 보장 장치가 늘어남), EAV(타입·제약 불가), 옵션 마스터 테이블(상품별 허용 값 테이블까지 필요해짐) |

- 추가 옵션 값은 `기모/롱기장`처럼 여러 조건이 결합된 문자열도 **값 하나**로 취급하고 내부를 분해하지 않는다.
- **구매 가능한 옵션 목록은 해당 상품의 SKU에서 중복 제거해 조회한다.** 별도의 허용 옵션 목록 없이 등록된 SKU 조합이 구매 가능 옵션의 기준이다.
- 옵션 표시 순서 컬럼은 두지 않는다. SKU의 순서와 색상·사이즈·추가 옵션 값별 순서는 서로 다른 개념이라 SKU 컬럼 하나로 표현할 수 없다. 정렬은 SQL `ORDER BY`나 애플리케이션이 맡고, 판매자가 옵션 순서를 지정하는 기능은 제외한다.
- 입력 표기(`블랙`/`검정`)의 일관성과 공백 제거는 애플리케이션이 검증한다. 색상·사이즈로 상품을 필터링하는 요구가 생기면 표기 일관성을 다시 검토한다.
- **상품의 모든 SKU는 색상·사이즈·추가 옵션의 사용 여부가 같아야 한다**(예: 블랙/M과 색상 없는 M이 한 상품에 섞이지 않음). 선언적 제약 하나로 표현하기 어려워 게시 조건에서 검증한다.

### 3.4 재고와 품절 (P4)
| 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|
| `sku.stock_qty`(NOT NULL, 0 이상)에 현재 수량 저장. 품절은 파생(2.4) | 요구사항은 "현재 수량 하나"이고, 재고는 모든 SKU가 항상 갖는 값이라 분리의 이점이 작다 | 별도 재고 테이블(1:1 분리), 입출고 이력 테이블(이력 조회 요구 없음), 품절 컬럼 저장(중복) |

| 파생 상태 | 정의 |
|---|---|
| SKU 품절 | `sale_yn = 'Y'` AND `stock_qty = 0` |
| SKU 구매 가능 | 상품 `ON_SALE` AND `sale_yn = 'Y'` AND `stock_qty > 0` AND 브랜드·판매자 `ACTIVE` |
| 상품 품절 | `sale_yn = 'Y'`인 SKU가 1개 이상이고 그 SKU가 모두 `stock_qty = 0` |

- **품절과 판매 중지는 다르다.** `sale_yn = 'Y'`이고 재고 0이면 판매는 허용된 품절이고, `sale_yn = 'N'`이면 재고가 있어도 구매할 수 없다. 고객 화면에서 품절 SKU는 표시하되 선택할 수 없고, 판매 중지 SKU는 옵션 목록에서 제외한다.
- `sale_yn = 'Y'`인 SKU가 없는 상품은 "품절"이 아니라 구매 불가다. SKU 품절이 `product.status`를 자동으로 바꾸지 않는다.
- 주문이 SKU를 참조하므로 판매를 멈춘 SKU는 삭제하지 않고 `sale_yn = 'N'`으로 관리한다. 판매 중지 SKU의 옵션 조합도 UNIQUE에 남으므로 재개할 때는 새로 등록하지 않고 `'Y'`로 되돌린다.
- 재고 차감 시점과 동시성 제어(원자적 갱신, 잠금)는 주문 영역에서 다룬다.

### 3.5 상품 상태와 게시 (P5, P6)
| 상태 | 의미 |
|---|---|
| DRAFT | 등록 중이며 한 번도 게시하지 않음 |
| ON_SALE | 게시되어 판매 중 |
| SUSPENDED | 일시 판매 중지 |
| ENDED | 판매 종료(필요하면 복구 가능) |

**전이**: `DRAFT → ON_SALE`, `ON_SALE ↔ SUSPENDED`, `ON_SALE·SUSPENDED → ENDED`, `ENDED → SUSPENDED`. `DRAFT`는 게시하거나 삭제만 가능하고, 게시된 상품은 `DRAFT`로 돌아가지 않는다. `ENDED` 상품은 바로 재개하지 않고 `SUSPENDED`로 복구한 뒤 상품정보와 게시 조건을 확인해 `ON_SALE`로 전환한다.

- **복구하면 `product_id`와 `model_number`를 유지한다.** `published_at`은 **최초** 게시 시각이므로 재판매나 상태 변경 때 초기화하거나 다시 기록하지 않는다.
- 재고 0은 `ON_SALE` 전환을 막는 조건이 아니다(품절은 파생 상태).
- 상태 전이 규칙은 애플리케이션이 지키고, `published_at`과 `status`의 일관성은 CHECK가 보장한다(2.5).
- 상태 값에 속성(이름, 서열)이 없으므로 코드 테이블이 아니라 CHECK를 쓴다([01_고객.md](01_고객.md) 2.6).

**게시 조건** (`SUSPENDED → ON_SALE` 전환 시에도 확인한다. `ENDED`에서 복구한 상품은 반드시 이 경로를 거친다)
| 규칙 | 보장 방식 |
|---|---|
| 대표(`MAIN`) 이미지 정확히 1개 | 최대 1개는 DB, "있어야 함"은 애플리케이션 |
| SKU 1개 이상 | 애플리케이션 |
| 추가 옵션 일관성: `extra_option_name`이 없으면 SKU 값도 없고, 있으면 SKU마다 값이 있음 | 애플리케이션 |
| 색상·사이즈 사용 여부가 모든 SKU에서 같음 | 애플리케이션 |
| 2단계 카테고리(`parent_id IS NOT NULL`)에 1개 이상 소속 | 애플리케이션 |
| 상품 생성 시 `product_detail` 행을 함께 생성 | 애플리케이션 |
| `target_gender`, `wear_season` 입력 | DB CHECK |
| `published_at`은 최초 게시 때만 기록하고 이후 변경하지 않음 | 기록 정합성은 CHECK, 불변은 애플리케이션 |
| 게시 시점의 브랜드·판매자가 `ACTIVE` ▲ | 애플리케이션 |

여러 테이블에 걸친 규칙은 이번 프로젝트에서 복잡도를 고려해 애플리케이션 검증을 기본으로 한다. 기본 제약(PK·FK·UNIQUE·CHECK)만으로 표현하기 어렵다는 뜻이지 DB로 보장할 방법이 전혀 없다는 뜻은 아니다.

### 3.6 상품 상세, 이미지, 실측 (P7~P9)
| 항목 | 선택 | 근거 | 채택하지 않은 대안 |
|---|---|---|---|
| 상세 정보 | `product_detail` 1:1 분리, PK=FK (2.6). 모든 컬럼 NULL 허용 | 목록과 상세의 접근 패턴·관리 책임이 다르다. 상품에 따라 소재·제조 정보가 없을 수 있다 | `product`에 통합 |
| 이미지 | `product_image` 한 테이블, `image_type`으로 구분, 대표 최대 1개는 함수 기반 UNIQUE (2.7) | 역할만 다르고 속성이 같다 | 종류별 테이블 분리, `product.main_image_url` 컬럼(대표 이미지 정보가 두 곳에 나뉨) |
| 사이즈 실측 | 구조화하지 않음. 상세 이미지 또는 상세 설명에 사이즈표 포함 (2.9) | 실측을 검색·비교·계산하는 기능이 없다. 기준 사이즈표를 제공하고 롱·숏 같은 추가 옵션의 차이는 설명·이미지로 안내한다 | `product_size_spec` 테이블(요구 없는 기능을 위한 비용) |

`display_order`는 이미지 표시 순서이고 SKU 옵션 순서와는 별개의 요구사항이다. 같은 값의 순서는 `product_image_id`로 정렬하며 UNIQUE는 걸지 않는다(순서를 교환할 때 일시적으로 충돌하기 때문).

### 3.7 분류 속성 (target_gender, wear_season, collection)
| 항목 | 선택 | 근거 |
|---|---|---|
| 대상 성별 | `product.target_gender` (`MALE`, `FEMALE`, `UNISEX`), 상품 상세가 아닌 `product` | 검색·필터링에 쓰는 분류 속성이라 기본정보에 둔다 |
| 착용 계절 | `product.wear_season`: 15개 조합 코드 하나 + CHECK (2.8) | 교차 테이블 없이 단순하게 표현하는 의도적 단순화 |
| 출시 컬렉션 | `collection_year`(NUMBER(4)) + `collection_season`(`SS`, `FW`), 둘 다 NULL이거나 둘 다 값 | 모든 상품이 정식 컬렉션 소속은 아니다. 별도 컬렉션 테이블은 만들지 않는다 |
| 최초 게시 | `published_at` | 쇼핑몰에 처음 게시된 시각 |

착용 계절, 출시 컬렉션, 최초 게시는 서로 독립이다. 2026 FW 컬렉션의 기모 후드티가 봄·가을·겨울용일 수 있고, 게시 시점은 컬렉션과 별개다.

**착용 계절 코드 15개**: 계절은 항상 `SPRING → SUMMER → AUTUMN → WINTER` 순서로 이어 쓰고, 네 계절 모두는 `ALL`이다.
| 개수 | 코드 |
|---|---|
| 1 | `SPRING`, `SUMMER`, `AUTUMN`, `WINTER` |
| 2 | `SPRING_SUMMER`, `SPRING_AUTUMN`, `SPRING_WINTER`, `SUMMER_AUTUMN`, `SUMMER_WINTER`, `AUTUMN_WINTER` |
| 3 | `SPRING_SUMMER_AUTUMN`, `SPRING_SUMMER_WINTER`, `SPRING_AUTUMN_WINTER`, `SUMMER_AUTUMN_WINTER` |
| 4 | `ALL` |

한계: 특정 계절로 검색하면 그 계절을 포함한 코드를 모두 골라야 한다(예: "봄"은 8개 코드). 코드와 계절의 대응은 애플리케이션이 상수로 관리한다.

### 3.8 삭제 정책 (P10)
| 엔티티 | 정책 |
|---|---|
| product | 판매 이력이 있으면 삭제하지 않고 `ENDED`. `DRAFT`이고 참조가 없을 때만 물리 삭제하며, 이때 자식(`product_category`, `product_image`, `sku`, `product_detail`)을 애플리케이션이 먼저 삭제한다 |
| sku | 판매 중지는 `sale_yn`. 물리 삭제는 참조가 없는 경우만 |
| product_image, product_detail | 상품과 생명주기가 같다. 이미지는 교체 시 물리 삭제 |
| seller, brand | 상태로 관리한다. 하위 데이터가 없을 때만 물리 삭제하며 FK가 거부한다 |
| seller_staff | 상태(`INACTIVE`)로 관리한다 |

물리 삭제는 FK가 참조 중인 행의 삭제를 거부하는 기본 동작에 맡기고 `ON DELETE` 옵션은 쓰지 않는다. `ON DELETE CASCADE`는 의도하지 않은 연쇄 삭제를 일으킬 수 있다.

### 4.1 엔티티 개요
| 테이블 | 논리명 | 역할 | 근거 |
|---|---|---|---|
| seller | 판매자 | 입점 판매업체(계약 단위) | 3.1 |
| seller_staff | 판매자 직원 계정 | 판매자 포털 로그인 계정 | 3.1 |
| brand | 브랜드 | 고객에게 보이는 브랜드, 한 판매자에 소속 | 3.1 |
| product | 상품 | 상품 페이지의 기본정보·분류·상태 | 3.2, 3.5, 3.7 |
| product_detail | 상품 상세 | 상세 설명, 소재, 제조·보증 정보 | 3.6 |
| sku | 판매 단위 | 옵션 조합, 재고, 판매 허용 | 3.3, 3.4 |
| product_image | 상품 이미지 | 대표·갤러리·상세 설명용 이미지 | 3.6 |

`product_category`는 카테고리 영역([02_카테고리.md](02_카테고리.md))에서 정의했고, 이 영역에서는 `product_id`의 FK만 추가한다.

공통 표기: 대리키는 `NUMBER(19)`, `GENERATED AS IDENTITY`, 시각은 `TIMESTAMP(6)`, 문자열은 글자 단위(`CHAR`) 길이다. NN은 NOT NULL이다. 컬럼명 `size_name`은 `size`가 Oracle 예약어라서 쓰지 못해 정했고, 일관성을 위해 `color_name`을 쓴다.

#### product (상품)
| 컬럼 | 논리명 | 타입 | 제약 |
|---|---|---|---|
| product_id | 상품 ID | NUMBER(19) | PK |
| brand_id | 브랜드 ID | NUMBER(19) | NN, FK → brand |
| model_number | 브랜드 품번(모델번호) | VARCHAR2(100 CHAR) | NN |
| product_name | 상품명 | VARCHAR2(200 CHAR) | NN |
| target_gender | 대상 성별 | VARCHAR2(10) | NULL 허용 (DRAFT가 아니면 필수) |
| wear_season | 착용 계절 조합 | VARCHAR2(30) | NULL 허용 (DRAFT가 아니면 필수) |
| collection_year | 컬렉션 연도 | NUMBER(4) | NULL 허용 |
| collection_season | 컬렉션 시즌 | VARCHAR2(10) | NULL 허용 |
| extra_option_name | 추가 옵션 그룹 이름 | VARCHAR2(50 CHAR) | NULL 허용 |
| status | 판매 상태 | VARCHAR2(20) | NN, 기본 `'DRAFT'` |
| published_at | 최초 게시 일시 | TIMESTAMP(6) | NULL 허용 (DRAFT는 NULL) |
| created_at | 생성 일시 | TIMESTAMP(6) | NN |
| updated_at | 수정 일시 | TIMESTAMP(6) | NN |

- UNIQUE `uq_product_brand_id_model_number`: `(brand_id, model_number)` (3.2, 2.3)
- CHECK `ck_product_status`: `status IN ('DRAFT','ON_SALE','SUSPENDED','ENDED')`
- CHECK `ck_product_target_gender`: `target_gender IS NULL OR target_gender IN ('MALE','FEMALE','UNISEX')`
- CHECK `ck_product_wear_season`: `wear_season IS NULL OR wear_season IN (3.7의 15개 코드)`
- CHECK `ck_product_collection_season`: `collection_season IS NULL OR collection_season IN ('SS','FW')`
- CHECK `ck_product_collection_pair`: `(collection_year IS NULL AND collection_season IS NULL) OR (collection_year IS NOT NULL AND collection_season IS NOT NULL)`
- CHECK `ck_product_publish_required`: `status = 'DRAFT' OR (target_gender IS NOT NULL AND wear_season IS NOT NULL)` (2.5)
- CHECK `ck_product_published_at`: `(status = 'DRAFT' AND published_at IS NULL) OR (status <> 'DRAFT' AND published_at IS NOT NULL)` (2.5)
- `collection_year`의 범위 CHECK는 두지 않는다 ▲ (`NUMBER(4)`는 음수도 허용하므로 필요하면 하한을 추가).
- 가격 컬럼은 없다(가격 영역). 판매자 ID도 없다(`brand`를 통해 확인).

| manufacturer_name | 제조자(업체) | VARCHAR2(200 CHAR) | NULL 허용 |
| origin_country | 제조국 | VARCHAR2(100 CHAR) | NULL 허용 |
| warranty_info | 품질보증 안내 | VARCHAR2(500 CHAR) | NULL 허용 |
| as_contact | A/S 책임자·연락처 | VARCHAR2(200 CHAR) | NULL 허용 |
| manufacture_info | 제조연월 안내 | VARCHAR2(100 CHAR) | NULL 허용 |

- `as_contact`는 상품별로 별도 A/S 안내가 필요할 때만 쓴다. 비어 있으면 `seller.cs_phone`으로 안내하며 판매자 연락처를 상품마다 반복 저장하지 않는다.

| color_name | 색상 | VARCHAR2(50 CHAR) | NULL 허용 |
| size_name | 사이즈 | VARCHAR2(30 CHAR) | NULL 허용 |

- FK `fk_product_category_product_id`: `product_id` → `product (product_id)`, ON DELETE 옵션 없음

### 4.3 관계
| 부모 | 자식 | 카디널리티 | 비고 |
|---|---|---|---|
| seller | seller_staff | 1 : N | |
| seller | brand | 1 : N | 브랜드는 정확히 한 판매자 |
| brand | product | 1 : N | 판매자는 브랜드를 통해 확인 |
| product | product_detail | 1 : 0..1 | PK = FK. DB 구조상 0..1이고 상품 생성 시 함께 생성하는 것은 애플리케이션 규칙 |
| product | sku | 1 : N | 최소 1개는 애플리케이션 규칙 |
| product | product_image | 1 : N | |
| product | product_category | 1 : N | 카테고리와 N:M(카테고리 영역) |

### 4.4 상태 값
| 대상 | 값 |
|---|---|
| product.status | `DRAFT`, `ON_SALE`, `SUSPENDED`, `ENDED` |
| sku.sale_yn | `Y`, `N` |
| seller.status | `ACTIVE`, `SUSPENDED` |
| brand.status, seller_staff.status | `ACTIVE`, `INACTIVE` |

구매 가능 여부는 저장하지 않고 3.4의 정의로 계산한다.

### 4.5 정규화 검토
모든 테이블은 3NF를 만족한다. 의도적인 설계는 다음과 같다.

| 위치 | 성격 |
|---|---|
| `product.seller_id` 없음 | `brand`가 판매자를 결정하므로 두면 이행 종속이 된다 |
| `sku`의 옵션 문자열 | SKU 자체의 속성이다(반복이 3NF 위반은 아님). 표기 일관성은 애플리케이션 검증 |
| `wear_season` 코드 | 15개 조합을 코드 하나로 취급하는 의도적 단순화(2.8) |
| `extra_option_name`(상품)과 `extra_option_value`(SKU) | 두 테이블에 걸쳐 의미가 연결되며 일관성은 게시 조건에서 검증 |
| 품절 컬럼 없음 | 재고에서 파생 |

### 4.6 FK 인덱스 검토
| FK 컬럼 | 검토 | 결과 |
|---|---|---|
| brand.seller_id | 판매자의 브랜드 목록 조회가 있고 기존 인덱스가 대신하지 못한다 | 생성 |
| seller_staff.seller_id | 판매자의 직원 목록 조회가 있고 `email` UNIQUE가 대신하지 못한다 | 생성 |
| product.brand_id | `UNIQUE (brand_id, model_number)`의 선두 컬럼이 대신한다 | UNIQUE 인덱스로 충족 |
| sku.product_id | `UNIQUE (product_id, …)`의 선두 컬럼이 대신한다 | UNIQUE 인덱스로 충족 |
| product_image.product_id | 이미지 목록 조회용 복합 인덱스 `(product_id, image_type, display_order)`의 선두 컬럼이 대신한다. 함수 기반 UNIQUE 인덱스는 일반 조회에 쓸 수 없다 | 복합 인덱스로 충족 |
| product_detail.product_id | PK 인덱스가 있다 | 불필요 |
| product_category.product_id | 복합 PK의 선두 컬럼이 대신한다 | PK 인덱스로 충족 |

상품 검색·필터링용 인덱스(성별, 계절, 상태 등)는 조회 패턴이 정해질 때 검토한다.

## ⑤ ERD 및 설계 검토

### 5.1 ERD
[erd/03_상품.drawio](erd/03_상품.drawio) (draw.io에서 열어 수정할 수 있다)

- 판매자·브랜드·직원은 마스터, `product`는 핵심, `product_detail`·`sku`·`product_image`는 종속 테이블 색으로 구분했다.
- 회색 테이블은 카테고리 영역에서 정의한 `category`, `product_category`이며 PK 컬럼만 표시한다. `product → product_category` 관계가 두 영역을 연결한다.
- 관계선은 4.3의 관계를 그대로 표현한다. `product_detail`은 PK = FK인 1 : 0..1 관계다.

### 5.2 주요 설계 결정 요약
- 판매자 1:N 브랜드 구조이고, 상품은 브랜드를 통해 판매자와 연결된다.
- 상품은 내부 PK(`product_id`)와 브랜드 품번(`model_number`, 브랜드별 유일)으로 식별한다.
- 상품(보이는 단위)과 SKU(파는 단위)를 분리하고, 옵션은 SKU의 고정 컬럼 + 복합 UNIQUE로 관리한다.
- 품절은 재고에서 계산하는 파생 상태이고, 판매 중지는 별도로 저장한다.
- 상품 상태는 `DRAFT → ON_SALE`, `ENDED`는 `SUSPENDED`로 복구할 수 있으며 `published_at`은 최초 게시일을 유지한다.
- 상세정보와 이미지는 분리하고, 사이즈 실측은 구조화하지 않는다.

### 5.3 미결정·추후 검토 사항
| 구분 | 내용 |
|---|---|
| 판매자·직원 | 직원 역할·권한, 브랜드 소속 판매자 변경 정책, 판매자 계약 종료 시 대표자명·사업장 주소 등 개인정보의 보존·파기, 판매자 정산·배송 정보 |
| 상품 분류 | 컬렉션 시즌이 SS·FW 외로 늘어날 때의 CHECK 수정, `collection_year` 범위 CHECK |
| 상품 정보 제공 | `product_detail`의 항목은 의류에서 일반적으로 알려진 항목이지만 상품군(신발, 가방 등)별 필수 항목과 필수 여부는 시행 고시로 확인해야 하며, 색상·치수 항목과 `sku`·사이즈표의 대응도 확인 필요 |
| 옵션 | 옵션 표기 일관성과 정렬(자유 입력의 정렬은 보장되지 않음), 색상·사이즈 필터 요구가 생길 때의 재검토 |
| 검색 | 품번 검색용 `model_number` 단독 인덱스, 계절·성별·상태 필터 인덱스 |
| 게시 | 게시 시점의 브랜드·판매자 활성 상태 확인 방식 |

### 5.4 다른 영역과의 연결
| 영역 | 연결 |
|---|---|
| 카테고리 | `product_category`가 `product`와 `category`를 N:M으로 연결한다. 상품 게시 시 2단계 카테고리 소속을 확인한다 |
| 가격 | 상품·SKU의 가격·할인, 옵션별 추가금은 가격 영역에서 정한다 |
| 장바구니·주문 | SKU를 참조한다. 판매자·상품·옵션 정보는 주문 시점 스냅샷으로 보존한다 |
| 주문 | 재고 차감 시점과 동시성 제어를 정한다 |
| 확장 | 배송 정책, 정산, 직원 권한, 바코드·GTIN(SKU 단위), 독립 추가 구매 상품 |
