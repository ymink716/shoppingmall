# 3회차: 상품 테이블 설계

> 무신사 기반 쇼핑몰 데이터 모델링 실습
> 진행 방식: ① 설계 유형 정리 → ② 테이블 설계 → ③ 컬럼 확인
> 용어는 수업 PPT를 참고합니다. PPT에 없는 실무 용어는 **(PPT 외)** 로 표시합니다.
> DBMS는 미정이므로 컬럼 타입은 도메인으로 표기합니다.

## 목차
0. 상품은 어떤 엔티티인가
1. 상품 설계 유형 (1~20)
2. 추천 조합
3. 테이블 설계 (논리 모델링 절차)
4. 컬럼 확인 포인트와 확정 결과
5. 업무 규칙과 다음 회차로 넘긴 항목

## 0. 상품은 어떤 엔티티인가

- PPT 분류로 상품은 **핵심 엔티티(기준정보)** 중 **"업무주체 및 대상"** 에 해당합니다 (행위의 대상).
- 앞 회차와의 관계
  - 표준 카테고리(2회차 파일 `02_카테고리.md`): 상품은 최하위 카테고리 1개에 속함
  - 브랜드·판매자: PB + 입점 혼합형, 판매자와 브랜드는 M:N (상세 설계는 브랜드·판매자 회차)
- 무신사 관찰
  - 상품 상세에 브랜드, 가격, 적립금, 쿠폰, 카테고리 경로가 표시됨 (✅ 직접 확인)
  - 옵션, 실측 사이즈표, 모델 착용 정보, 상품정보고시, 후기 구성은 JavaScript로 그려져서 **확인하지 못함** (💭 패션 커머스 일반 구조로 추론)

### 상품 설계의 핵심 질문
1. **상품과 실제 판매 단위(재고 단위)를 어떻게 나눌까?** → 유형 1~6
2. **카테고리마다 다른 속성을 어떻게 담을까?** → 유형 7~10
3. **가격을 어떻게 관리할까?** → 유형 11~13
4. **재고를 어떻게 관리할까?** → 유형 14~15
5. **이미지, 실측, 상태, 구성 상품 같은 부가 정보는?** → 유형 16~20

### 용어 정리 (이 문서에서)
| 용어 | 뜻 | 예시 |
|---|---|---|
| 상품 | 고객이 상품 상세 페이지에서 보는 단위 | "베이직 반소매 티셔츠" |
| 옵션 그룹 | 고객이 고르는 선택 항목의 종류 | 색상, 사이즈, 용량 |
| 옵션 값 | 옵션 그룹 안의 선택지 | 블랙, 화이트 / S, M, L |
| **단품** (SKU, PPT 외) | 옵션 조합까지 정해진 **실제 판매·재고 단위** | "베이직 반소매 티셔츠 / 블랙 / M" |

### 예시 상품 (모든 유형에서 공통으로 사용)
```
베이직 반소매 티셔츠 (상의 > 티셔츠 > 반소매 티셔츠)
  색상: 블랙, 화이트, 네이비
  사이즈: S, M, L, XL
  → 단품 3 × 4 = 12개, 단품마다 재고가 따로 있음
```

## A. 상품과 판매 단위

### 1. 단일 상품형
**정의**: 옵션 없이 **상품 = 판매 단위 = 재고 단위**로 봅니다.

| 상품번호 | 상품명 | 판매가 | 재고수량 |
|---|---|---|---|
| 1 | 베이직 반소매 티셔츠 블랙 M | 19,000 | 30 |
| 2 | 베이직 반소매 티셔츠 블랙 L | 19,000 | 12 |

- **장점**: 가장 단순합니다.
- **단점**: 색상 3개 × 사이즈 4개면 상품이 12개가 됩니다. 상세 페이지, 후기, 이미지가 12군데로 흩어집니다.
- **언제**: 옵션이 없는 상품만 파는 곳 (도서, 단일 규격 상품)
- **무신사라면**: ❌

---

### 2. 옵션 조합 행형
**정의**: 상품 아래에 **옵션 조합을 문자열로 가진 행**을 둡니다.
```
상품 1 ──< M 상품 옵션(옵션명 문자열, 추가금, 재고)
```
| 옵션번호 | 상품번호 | 옵션명 | 추가금 | 재고 |
|---|---|---|---|---|
| 1 | 1 | 블랙 / M | 0 | 30 |
| 2 | 1 | 블랙 / L | 0 | 12 |
| 3 | 1 | 화이트 / XL | 1,000 | 5 |

- **장점**: 단순하고, 상세 페이지가 하나로 모입니다.
- **단점**
  - "블랙 / M"은 **복합 속성**입니다 (1정규형 원자성 위반). "블랙인 단품만" 찾으려면 문자열을 잘라야 합니다.
  - 색상별 이미지, 사이즈별 실측을 연결할 대상이 없습니다.
- **언제**: 소규모 쇼핑몰, 쇼핑몰 솔루션의 단순 옵션
- **무신사라면**: ❌ 색상 필터, 색상별 이미지, 사이즈별 실측이 필요함

---

### 3. 범용 옵션 + 단품형 (옵션 정의와 단품 분리)
**정의**: **옵션 그룹 → 옵션 값**을 정의하고, **단품은 옵션 값의 조합**으로 만듭니다.
```
상품 1 ──< M 옵션 그룹 1 ──< M 옵션 값
상품 1 ──< M 단품
단품 M ──< 단품 옵션 구성 >── M 옵션 값        ← M:N 해소 (교차 엔티티)
```

**예시 데이터**
옵션 그룹
| 옵션그룹번호 | 상품번호 | 옵션그룹명 | 옵션유형 |
|---|---|---|---|
| 10 | 1 | 색상 | COLOR |
| 11 | 1 | 사이즈 | SIZE |

옵션 값
| 옵션값번호 | 옵션그룹번호 | 옵션값명 |
|---|---|---|
| 100 | 10 | 블랙 |
| 101 | 10 | 화이트 |
| 110 | 11 | M |
| 111 | 11 | L |

단품과 단품 옵션 구성
| 단품번호 | 재고 | | 단품번호 | 옵션그룹번호 | 옵션값번호 |
|---|---|---|---|---|---|
| 1000 | 30 | | 1000 | 10 | 100 (블랙) |
| | | | 1000 | 11 | 110 (M) |

- **장점**
  - 옵션 축의 개수와 이름이 자유롭습니다 (의류: 색상·사이즈, 뷰티: 용량·호수, 가방: 색상만).
  - 옵션 값 단위로 이미지, 실측을 연결할 수 있습니다.
  - 정규형을 만족합니다.
- **단점**
  - 엔티티가 많고, 단품의 옵션 조합을 보려면 조인이 필요합니다.
  - "단품의 옵션 값은 같은 상품의 것이어야 한다", "같은 조합의 단품이 두 개 있으면 안 된다"는 규칙을 키로 보장하기 어렵습니다.
- **언제**: 여러 카테고리를 파는 종합몰, 입점형 마켓
- **무신사라면**: ✅ 의류 외에 가방, 신발, 뷰티, 라이프도 팔기 때문에 유력

---

### 4. 고정 축형 (색상 × 사이즈 전용 엔티티)
**정의**: 옵션 축을 **색상과 사이즈로 고정**하고, 각각 전용 엔티티를 둡니다.
```
상품 1 ──< M 상품 색상
상품 1 ──< M 상품 사이즈
단품 = 상품 + 색상 + 사이즈 (AK)
```
| 단품번호 | 상품번호 | 색상번호 | 사이즈번호 | 재고 |
|---|---|---|---|---|
| 1000 | 1 | 100 (블랙) | 110 (M) | 30 |

- **장점**: 패션에 딱 맞고 이해하기 쉽습니다. 색상과 사이즈를 단품의 참조 키로 바로 가지므로 조인이 단순합니다. "같은 조합 중복 금지"를 대체 식별자로 보장할 수 있습니다.
- **단점**: 용량, 호수, 각인 같은 **다른 옵션 축을 표현할 수 없습니다**.
- **언제**: 의류·신발 전문몰
- **무신사라면**: △ 의류만 보면 최적이지만, 뷰티·라이프 상품이 있어 한계가 있음 (00 초기 설계안이 이 방식)

---

### 5. 스타일-컬러-사이즈 3계층형 (패션 업계 방식, PPT 외)
**정의**: 패션 업계의 상품 체계인 **스타일(품번) → 컬러웨이 → 사이즈(단품)** 를 3단계 엔티티로 둡니다.
```
스타일(품번) 1 ──< M 컬러웨이 1 ──< M 사이즈 단품
```
- 컬러웨이가 독립 엔티티라서, **이미지·모델컷·상품 페이지가 컬러 단위**로 나뉩니다.
- **장점**: 브랜드의 생산·물류 체계(품번-컬러-사이즈)와 그대로 맞습니다.
- **단점**: 패션 외 상품에 맞지 않습니다. 계층이 고정됩니다.
- **언제**: 브랜드 자사몰, SPA 브랜드, ERP와 연동이 중요한 곳
- **무신사라면**: △ PB(무신사 스탠다드) 쪽에는 잘 맞지만 전체 플랫폼에는 3번이 유연함. 💭 무신사는 일부 상품을 컬러별로 별도 상품 페이지로 운영하는 것으로 보이는데, 이 경우 3번 구조에서 "컬러마다 상품을 따로 만들고 사이즈만 옵션으로 두는" 방식으로 표현 가능

---

### 6. 상품 마스터 / 판매 상품 분리형 (카탈로그형, PPT 외)
**정의**: **제품 자체의 정보(상품 마스터)** 와 **판매자가 파는 조건(판매 상품)** 을 분리합니다.
```
상품 마스터(제품명, 브랜드, 스펙, 이미지) 1 ──< M 판매 상품(판매자, 가격, 재고, 배송)
```
- **해결하는 문제**: 같은 나이키 신발을 판매자 3곳이 팔면, 상품 정보가 3번 중복되고 후기도 흩어집니다.
- **장점**: 상품 정보 중복이 없고, 가격 비교와 최저가 노출이 가능합니다.
- **단점**: 구조가 복잡하고, 판매자마다 다른 옵션·사진을 허용하기 어렵습니다.
- **언제**: 오픈마켓 가격비교(카탈로그 매칭), 리셀 플랫폼(같은 모델을 여러 판매자가 판매)
- **무신사라면**: △ 판매자-브랜드가 M:N이라 같은 브랜드 상품을 여러 판매자가 팔 수는 있지만, 대부분 판매자가 직접 상품을 등록하는 구조로 보임 (💭). **보류**하고 필요하면 확장

## B. 카테고리별로 다른 속성

**해결하는 문제**: 상의는 핏·기장·소매, 신발은 굽높이·발볼, 뷰티는 용량·피부타입, 상품정보고시 항목도 품목마다 다릅니다.

### 7. 컬럼 나열형
**정의**: 모든 카테고리의 속성을 상품 엔티티의 속성으로 다 나열합니다.

| 상품번호 | 핏 | 기장 | 굽높이 | 발볼 | 용량 | 피부타입 |
|---|---|---|---|---|---|---|
| 1 (티셔츠) | 오버 | 숏 | NULL | NULL | NULL | NULL |
| 2 (운동화) | NULL | NULL | 3cm | 보통 | NULL | NULL |

- **장점**: 조회가 단순하고, 타입과 필수 여부를 정확하게 정할 수 있습니다.
- **단점**: NULL이 대부분이고, 카테고리가 늘 때마다 속성을 추가해야 합니다.
- **언제**: 카테고리가 몇 개 안 되는 전문몰

### 8. 슈퍼타입/서브타입형 (PPT: 슈퍼타입/서브타입 관계, 일반화/특수화)
**정의**: 상품(공통)을 슈퍼타입으로, 의류·신발·가방·뷰티를 서브타입으로 둡니다.
```
상품(공통: 상품명, 가격, 브랜드)
  ├─ 의류 상품(핏, 기장, 소매)
  ├─ 신발 상품(굽높이, 발볼)
  └─ 뷰티 상품(용량, 피부타입, 사용기한)
```
- **장점**: 유형별 속성의 타입과 필수 여부를 정확하게 지킬 수 있습니다.
- **단점**: 상품 유형이 늘면 엔티티가 늘어납니다. 유형이 수십 개면 관리가 어렵습니다.
- **물리 설계 (PPT)**: 슈퍼타입 기준 / 서브타입 기준 / 슈퍼타입·서브타입 테이블 설계 중 선택
- **언제**: 상품 유형이 몇 개로 안정적이고, 유형별 업무 처리가 다를 때

### 9. 속성 정의형 (EAV, PPT 외)
**정의**: 카테고리마다 **어떤 속성이 필요한지**를 데이터로 정의하고, 상품은 **속성 값**을 행으로 저장합니다. (카테고리 유형 13번과 짝)
```
속성(속성명, 속성유형, 입력방식) 1 ──< M 속성 선택값
카테고리 M ──< 카테고리 속성 >── M 속성       ← 카테고리마다 필요한 속성
상품 M ──< 상품 속성값 >── M 속성              ← 상품마다 입력한 값
```
| 상품번호 | 속성 | 값 |
|---|---|---|
| 1 | 핏 | 오버 |
| 1 | 기장 | 숏 |
| 2 | 굽높이 | 3cm |

- **장점**: 카테고리와 속성이 늘어도 구조를 바꾸지 않습니다. 필터 항목을 운영자가 관리할 수 있습니다.
- **단점**: 값의 타입 검증과 필수 여부를 키·제약으로 보장하기 어렵습니다. 조회 쿼리가 복잡합니다.
- **언제**: 종합몰, 입점형 마켓 (카테고리 수백 개)

### 10. JSON 속성형 (PPT 외)
**정의**: 카테고리별 속성을 상품의 JSON 속성 하나에 넣습니다.
```json
{"핏": "오버", "기장": "숏", "소매": "반소매"}
```
- **장점**: 가장 유연하고 조회 시 조인이 없습니다.
- **단점**: 1정규형(원자성)을 어깁니다. 필터 검색과 통계가 어렵고 검증이 안 됩니다.
- **언제**: 화면 표시용 부가 정보, 검색엔진에 넘기는 데이터

### 속성 유형 비교
| 유형 | 유연성 | 타입·필수 보장 | 필터 검색 | 복잡도 | 무신사 |
|---|---|---|---|---|---|
| 7. 컬럼 나열 | 낮음 | ✅ | 쉬움 | ★ | ❌ |
| 8. 슈퍼/서브타입 | 중간 | ✅ | 쉬움 | ★★★ | △ 공통 속성만 |
| 9. 속성 정의(EAV) | **높음** | △ (속성 정의로 일부 보완) | 가능 | ★★★ | ✅ 필터·고시·실측 |
| 10. JSON | 매우 높음 | ❌ | 어려움 | ★ | ❌ |

> 📌 실무에서는 **7번(모든 상품 공통 속성) + 9번(카테고리별 속성)** 을 섞는 경우가 가장 많습니다. 성별, 시즌처럼 거의 모든 패션 상품에 있는 값은 상품의 속성으로 두고, 카테고리마다 달라지는 것만 속성 정의로 관리합니다.

## C. 가격

### 11. 가격 속성형
**정의**: 상품에 **정가, 판매가**를 속성으로 둡니다. 현재 값만 저장합니다.
- **장점**: 단순합니다.
- **단점**: 언제 얼마였는지 알 수 없습니다. 가격 변경 분쟁("어제는 더 쌌다")에 대응할 수 없습니다.
- **참고**: 주문 시점 가격은 주문 상품에 **복사해서 저장**(스냅샷, PPT 외)하므로 주문 금액은 영향을 받지 않습니다 (주문 회차).

### 12. 가격 이력형 (PPT: 이력 관리 방법)
**정의**: 가격이 바뀔 때마다 이력을 남깁니다.

| 방식 | 구조 | 특징 |
|---|---|---|
| 점 이력 | (상품번호, 변경일시, 판매가) | 바뀐 시점만 기록. 특정 시점의 가격을 찾으려면 "그 시점 이전 중 최신"을 찾아야 함 |
| **선분 이력** | (상품번호, 적용시작일시, 적용종료일시, 판매가) | `시작 ≤ 기준시점 < 종료`로 바로 조회. 기간이 겹치지 않게 관리해야 함 |

PPT의 다른 선택지
- **속성 전체 vs 속성 일부**: 상품 전체를 이력으로 남길지, 가격만 남길지 → **가격만** 남기는 것이 일반적
- **최종 데이터 포함 vs 미포함**: 현재 가격도 이력에 넣을지 → 넣으면 이력만 봐도 되지만, 상품의 현재가와 **중복**됨

### 13. 가격 정책 분리형 (PPT 외)
**정의**: 상품에는 **기본 가격**만 두고, 할인은 **별도 정책 엔티티**로 관리합니다.
```
상품(정가) ──< 할인 정책(할인유형, 할인율/금액, 기간, 대상)
최종 판매가 = 정가 - 적용 가능한 할인 (계산)
```
- **장점**: 기간 할인, 회원 등급 할인, 타임 세일을 상품 수정 없이 운영할 수 있습니다.
- **단점**: 최종 가격이 **파생 속성**이 되어, 조회할 때마다 계산하거나 따로 저장(역정규화)해야 합니다.
- **언제**: 프로모션이 많은 대형 커머스
- **무신사라면**: ✅ 필요하지만 **쿠폰·프로모션 회차**에서 다룸. 상품 회차에서는 판매자가 정하는 판매가까지만 설계

## D. 재고

### 14. 단품 재고 속성형
**정의**: 단품에 **재고수량** 속성을 둡니다.
- **장점**: 단순하고 조회가 빠릅니다.
- **단점**: 창고가 여러 개면 표현할 수 없습니다. 재고가 왜 변했는지 알 수 없습니다 → **재고 변동 이력**(PPT 파생 엔티티: 이력)을 함께 둡니다.

### 15. 재고 엔티티 분리형
**정의**: 재고를 **단품 × 창고** 단위의 별도 엔티티로 둡니다.
```
단품 M ──< 재고(단품번호 + 창고번호, 수량) >── M 창고
```
- **장점**: 무신사 물류센터 재고와 브랜드 창고 재고를 나눠 관리할 수 있습니다.
- **단점**: 주문할 때 어느 창고에서 출고할지(할당) 로직이 필요합니다.
- **무신사라면**: 💭 "무신사 배송"과 "브랜드 배송"이 나뉘는 것으로 보여 장기적으로 필요. 실습에서는 판매자 직접 배송을 가정해 **보류**

### 재고를 저장하는 두 가지 관점 (PPT 외)
| 방식 | 뜻 | 특징 |
|---|---|---|
| 현재 수량 저장 | 단품.재고수량을 바로 증감 | 빠름. 이력이 없으면 원인 추적 불가 |
| 원장(이력) 합산 | 입고·출고 이력을 모두 더해서 현재 수량 계산 | 정확하지만 느림. 현재 수량은 파생 속성 |
| **둘 다 (실무)** | 현재 수량 + 변동 이력 | 현재 수량은 역정규화로 보고, 이력과 주기적으로 맞춰 봄 |

## E. 부가 정보

### 16. 상품 이미지
| 방식 | 구조 | 특징 |
|---|---|---|
| 상품 속성 | 대표이미지URL 하나 | 여러 장을 저장할 수 없음 (다중 속성 문제) |
| **상품 이미지 엔티티** | 상품 1:M 이미지 (유형, 순서) | 일반적 |
| **+ 옵션 값 연결** | 이미지에 옵션값번호(색상) 선택 참조 | 색상을 고르면 해당 색상 사진으로 바뀌는 화면 지원 |

### 17. 실측 사이즈
**정의**: **사이즈(옵션 값) × 측정 항목**의 값입니다.

| 사이즈 | 총장 | 어깨너비 | 가슴단면 | 소매길이 |
|---|---|---|---|---|
| M | 70 | 50 | 55 | 22 |
| L | 72 | 52 | 57 | 23 |

- 엔티티로 바꾸면: 실측(옵션값번호 + 측정항목, 측정값) — 표의 칸 하나가 인스턴스 하나
- 측정 항목은 카테고리마다 다르므로 **9번 속성 정의형**과 연결됩니다 (상의: 총장·어깨너비, 하의: 허리단면·허벅지단면).

### 18. 상품정보고시
- 전자상거래법상 품목별로 제공해야 하는 정보 (의류: 소재, 색상, 치수, 제조자, 제조국, 세탁방법, 제조연월, 품질보증기준, A/S 책임자)
- 품목군마다 항목이 다르므로 **9번 속성 정의형**과 같은 구조로 관리할 수 있습니다.
- 대안: 의류용, 신발용, 화장품용 고시 엔티티를 따로 두는 **8번 서브타입형**

### 19. 상품 상태와 승인 이력
- 상태: 작성중 → 검수요청 → (반려) → 판매중 → 판매중지 → 판매종료
- **품절은 상태가 아니라 파생 값**입니다. 단품 재고가 모두 0이면 품절로 계산합니다. 상태로 저장하면 재고와 상태가 서로 어긋날 수 있습니다.
- 상태 변경 이력(파생 엔티티: 이력)에 반려 사유와 처리자를 남깁니다.

### 20. 구성 상품 (세트·묶음, PPT: 재귀적 관계)
**정의**: 상품이 다른 상품들로 구성됩니다 (예: "티셔츠 3팩", "셋업 = 재킷 + 팬츠").
```
상품 M ──< 상품 구성(세트상품번호, 구성상품번호, 수량) >── M 상품    ← 재귀적 M:N
```
- 카테고리의 재귀적 관계는 1:M이었지만, 구성 상품은 **재귀적 M:N**입니다 (하나의 상품이 여러 세트에 들어갈 수 있음).
- 재고 차감을 세트 단위로 할지, 구성 상품 단위로 할지 정해야 합니다.
- **무신사라면**: 보류

| 보류 | 6. 마스터/판매 분리, 15. 창고별 재고, 20. 구성 상품, 모델 착용 정보 | 실습 범위 조절 |

**속성 체계 통합 아이디어 (이번 설계의 핵심)**
필터(핏, 기장), 상품정보고시(소재, 제조국), 실측 항목(총장, 어깨너비)은 모두 "**카테고리마다 필요한 항목이 다르다**"는 같은 성격을 가집니다. 그래서 **속성 엔티티 하나**에 속성유형(FILTER / NOTICE / MEASURE)으로 구분해서 통합합니다. 엔티티 수가 줄고, 카테고리에 항목을 지정하는 방식도 하나로 통일됩니다.

## 3. 테이블 설계 (논리 모델링 절차)

### 3-1. 엔티티 도출 및 식별
| 엔티티 | 분류 (PPT) | 설명 |
|---|---|---|
| **상품** | 핵심 엔티티 (업무주체 및 대상) | 상세 페이지 단위 |
| **상품 옵션 그룹** | 파생 엔티티 (상세) | 색상, 사이즈, 용량 등 |
| **상품 옵션 값** | 파생 엔티티 (상세) | 블랙, M 등 |
| **단품** | 파생 엔티티 (상세) | 실제 판매·재고 단위 (SKU) |
| **단품 옵션 구성** | 파생 엔티티 (교차) | 단품 M:N 옵션 값 해소 |
| **상품 이미지** | 파생 엔티티 (상세) | |
| **속성** | 핵심 엔티티 (유형 및 분류) | 필터·고시·실측 항목 정의 |
| **속성 선택값** | 파생 엔티티 (상세) | 선택형 속성의 선택지 (핏: 슬림/레귤러/오버) |
| **카테고리 속성** | 파생 엔티티 (교차) | 표준 카테고리 M:N 속성 해소 |
| **상품 속성값** | 파생 엔티티 (교차) | 상품 M:N 속성 해소 (필터·고시 값) |
| **실측 사이즈** | 파생 엔티티 (교차) | 옵션 값(SIZE) M:N 속성(MEASURE) 해소 |
| **상품 가격 이력** | 파생 엔티티 (이력) | 선분 이력 |
| **단품 재고 이력** | 파생 엔티티 (이력) | 점 이력 |
| **상품 상태 이력** | 파생 엔티티 (이력) | 점 이력 |
| 브랜드, 판매자 | 핵심 엔티티 | 참조만. 상세는 브랜드·판매자 회차 |

### 3-2. 엔티티 정의
| 엔티티 | 정의 | 발생 규칙 |
|---|---|---|
| 상품 | 판매자가 등록하는, 고객이 하나의 상세 페이지에서 보는 판매 대상 | 판매자 담당자가 등록 → 무신사 검수 후 판매 |
| 상품 옵션 그룹 | 상품에서 고객이 골라야 하는 선택 항목 | 상품당 0~3개 |
| 상품 옵션 값 | 옵션 그룹 안의 선택지 | 그룹당 1개 이상 |
| 단품 | 모든 옵션 그룹에서 값을 하나씩 고른 조합. 재고와 주문의 단위 | 상품당 1개 이상. **옵션이 없는 상품도 기본 단품 1개** |
| 속성 | 카테고리별로 다른 입력 항목의 정의 | 운영자가 등록 |
| 상품 가격 이력 | 상품의 정가·판매가가 적용된 기간 | 가격이 바뀔 때마다 이전 행을 닫고 새 행 생성 |
| 단품 재고 이력 | 단품 재고 수량이 바뀐 원인과 수량 | 입고, 주문, 취소, 반품, 조정 때마다 생성 |

### 3-3. 관계 도출 및 정의
| 관계 | 관계 유형 | 관계수 | 선택성 | 식별자 상속 | 비고 |
|---|---|---|---|---|---|
| 표준 카테고리 → 상품 | 기본 | 1:M | 선택-필수 | 비식별 | 최하위 카테고리만 |
| 브랜드 → 상품 | 기본 | 1:M | 선택-필수 | 비식별 | 브랜드·판매자 회차에서 확정 |
| 판매자 → 상품 | 기본 | 1:M | 선택-필수 | 비식별 | 〃 |
| 상품 → 옵션 그룹 | 기본 | 1:M | 선택-필수 | 비식별 | 옵션 없는 상품은 그룹 0개 |
| 옵션 그룹 → 옵션 값 | 기본 | 1:M | 필수-필수 | 비식별 | |
| 상품 → 단품 | 기본 | 1:M | **필수**-필수 | 비식별 | 상품은 단품 1개 이상 |
| 단품 → 단품 옵션 구성 | 기본 | 1:M | 선택-필수 | **식별** | M:N 해소 |
| 옵션 그룹 → 단품 옵션 구성 | 기본 | 1:M | 필수-필수 | **식별** | 단품당 그룹별 값 1개를 키로 보장 |
| 옵션 값 → 단품 옵션 구성 | 기본 | 1:M | 필수-필수 | 비식별 | |
| 상품 → 상품 이미지 | 기본 | 1:M | 필수-필수 | 비식별 | 대표 이미지 필수 |
| 옵션 값 → 상품 이미지 | 기본 | 1:M | 선택-선택 | 비식별 | 색상별 이미지 |
| 속성 → 속성 선택값 | 기본 | 1:M | 선택-필수 | 비식별 | 선택형 속성만 |
| 표준 카테고리 ↔ 속성 | M:N → 카테고리 속성 | 1:M, 1:M | | **식별** | |
| 상품 ↔ 속성 | M:N → 상품 속성값 | 1:M, 1:M | | **식별** | |
| 옵션 값(SIZE) ↔ 속성(MEASURE) | M:N → 실측 사이즈 | 1:M, 1:M | | **식별** | |
| 상품 → 상품 가격 이력 | 기본 | 1:M | 필수-필수 | **식별** | PK = 상품번호 + 적용시작일시 |
| 단품 → 단품 재고 이력 | 기본 | 1:M | 선택-필수 | 비식별 | |
| 상품 → 상품 상태 이력 | 기본 | 1:M | 필수-필수 | 비식별 | |

**관계도**
```
[표준 카테고리] ─< [카테고리 속성] >─ [속성] ─< [속성 선택값]
      │1                                │1  │1
      │                                 │   └──────────────┐
      ▼M                                ▼M                 │
[브랜드]─<[상품]─────────────< [상품 속성값]                 │
[판매자]─<  │1                                             │
            ├─< [상품 옵션 그룹] 1─< [상품 옵션 값] ─< [실측 사이즈] >─┘
            │            │1               │1    └─< [상품 이미지](색상별, 선택)
            │            └──< [단품 옵션 구성] >──┘
            ├─< [단품] 1─< [단품 옵션 구성]
            │     └─< [단품 재고 이력]
            ├─< [상품 이미지]
            ├─< [상품 가격 이력]
            └─< [상품 상태 이력]
```

**식별자 선택 포인트 (PPT: 인조 식별자를 쓰는 경우 ② 복합키를 단순히 할 때)**
- 옵션 그룹을 (상품번호 + 그룹순번), 옵션 값을 (상품번호 + 그룹순번 + 값순번)처럼 **식별 관계로 계속 상속하면**, 옵션 값의 키가 3개 속성이 됩니다.
- 옵션 값은 단품 옵션 구성, 이미지, 실측 사이즈 세 곳에서 참조되므로, 키가 길어지면 모든 자식이 길어집니다.
- 그래서 옵션 그룹, 옵션 값, 단품은 **인조 식별자 + 비식별 관계**로 두고, 교차 엔티티는 **식별 관계**로 둡니다.

### 3-5. 데이터 모델 검토

**예시 데이터로 확인: 베이직 반소매 티셔츠 (색상 3 × 사이즈 4)**
| 엔티티 | 인스턴스 수 | 내용 |
|---|---|---|
| 상품 | 1 | 베이직 반소매 티셔츠 |
| 옵션 그룹 | 2 | 색상(COLOR), 사이즈(SIZE) |
| 옵션 값 | 7 | 블랙, 화이트, 네이비 / S, M, L, XL |
| 단품 | 12 | 블랙-S ~ 네이비-XL |
| 단품 옵션 구성 | 24 | 단품 12 × 그룹 2 |
| 실측 사이즈 | 16 | 사이즈 4 × 측정 항목 4 (총장, 어깨너비, 가슴단면, 소매길이) |
| 상품 이미지 | 예: 9 | 색상별 3장씩 |
| 상품 속성값 | 예: 9 | 필터 2(핏, 기장) + 고시 7(소재, 제조국 등) |

**제약 조건 (PPT 4가지)**
| 제약 | 적용 |
|---|---|
| 키 제약조건 | 모든 PK. 대체 식별자: (판매자번호 + 판매자상품코드), (상품번호 + 단품코드), (상품번호 + 옵션그룹명), (옵션그룹번호 + 옵션값명), (속성유형코드 + 속성명) |
| 실체 무결성 | PK와 필수 속성 NOT NULL |
| 영역 무결성 | 판매가 ≤ 정가, 재고수량 ≥ 0, 측정값 > 0, 상태·유형 코드값, 속성선택값번호와 속성값 중 하나만 |
| 참조 무결성 | 모든 FK. 상품의 카테고리번호는 존재하는 표준 카테고리 |

**키 구조로 보장되지 않는 규칙 (업무 규칙)**
| 규칙 | 이유 |
|---|---|
| 상품당 COLOR 유형, SIZE 유형 옵션 그룹은 각각 최대 1개다 | 색상별 이미지·사이즈별 실측이 어느 그룹을 기준으로 할지 하나로 정해져야 하기 때문 (확인 19번) |
| 단품 옵션 구성의 옵션 값은 그 옵션 그룹의 값이어야 한다 | 옵션값번호와 옵션그룹번호를 각각 FK로 걸기 때문 |
| 단품 옵션 구성의 옵션 그룹은 그 단품의 상품에 속해야 한다 | 상품번호가 PK 경로에 없기 때문 (인조 식별자를 쓴 대가) |
| 같은 상품 안에서 옵션 조합이 같은 단품이 두 개 있으면 안 된다 | 조합은 여러 행에 걸쳐 있어 키로 표현 불가 |
| 단품은 상품의 모든 옵션 그룹에 대해 값을 하나씩 가져야 한다 | 〃 |
| 이미지의 옵션 값은 같은 상품의 COLOR 유형이어야 한다 | |
| 실측 사이즈는 SIZE 유형 옵션 값 + MEASURE 유형 속성이어야 한다 | |
| 상품 속성값의 속성은 상품 카테고리(와 그 상위)에 지정된 속성이어야 한다 | 카테고리 재귀 조회 필요 |
| 가격 이력의 적용 기간은 겹치지 않는다 | 선분 이력 공통 문제 |
| 상품의 현재 가격은 가격 이력의 현재 행과 같아야 한다 | 최종 데이터 포함 방식의 중복 |
| 단품 재고수량은 재고 이력의 마지막 변동후수량과 같아야 한다 | 현재값 + 이력 방식의 중복 |

> 📌 이번 회차의 학습 포인트: **인조 식별자로 키를 단순하게 만들면, 식별 관계로 상속했을 때 키가 보장해 주던 규칙("같은 상품의 옵션인가")을 업무 규칙으로 옮겨야 합니다.** 키 단순화와 무결성 보장은 서로 맞바꾸는 관계입니다.

**함수 종속과 정규화**
| 점검 | 결과 |
|---|---|
| 1정규형 | ✅ "블랙 / M"을 단품 옵션 구성으로 분리. 이미지·속성값도 다중 속성을 행으로 분리 |

## 4. 컬럼 확인 포인트와 확정 결과

17개 추천안을 다시 검토해서 15개는 그대로 확정했고, 2개(10번, 11번)는 내용을 보완해서 확정했습니다. 검토하면서 새로 발견한 2개(18번, 19번)도 추가로 확정했습니다. 브랜드·판매자는 이번 회차에서 다루지 않고, 참조 컬럼만 둔 채로 확정합니다.

| # | 쟁점 | 확정 | 검토 의견 |
|---|---|---|---|
| 1 | 상품-판매 단위 구조 | **3. 범용 옵션 + 옵션유형코드** | 의류 외 카테고리(향수 용량, 가방 색상)도 같은 구조로 처리됨. 시나리오 1~4로 확인 |
| 2 | 단품의 옵션 조합 표현 | **교차 엔티티(단품 옵션 구성)** | 옵션값번호1·옵션값번호2 방식은 반복 속성(1정규형 위반)이고, 옵션 축이 늘면 구조가 바뀜 |
| 3 | 컬러별 상품 분리 운영 | **구조 변경 없이 지원.** 스타일 그룹은 보류 | 컬러별 상품 + 사이즈 옵션으로 표현 가능 |
| 4 | 옵션 없는 상품 | **기본 단품 1개** | 주문·장바구니·재고가 항상 단품을 참조하므로 예외 경로가 없어짐 |
| 5 | 품절 표현 | **파생 값** (상태코드에 SOLD_OUT 없음) | 재고와 상태가 어긋나는 것을 구조적으로 막음. 특정 옵션 판매 중지는 단품판매상태코드로 처리 |
| 6 | 할인율 | **계산** (파생 속성) | 정가·판매가로 항상 구할 수 있음 |
| 7 | 가격 이력 방식 | **선분 이력 + 최종 데이터 포함** | 특정 시점 가격 조회(정산, 분쟁 대응)가 쉬움. 현재 가격 중복은 업무 규칙으로 관리 |
| 8 | 옵션 추가금 이력 | **보류** | 주문 시점의 가격은 주문 회차에서 주문상품에 함께 저장(스냅샷)할 예정이라 당장 필요하지 않음 |
| 9 | 속성 체계 | **속성 하나로 통합** (속성유형코드 FILTER/NOTICE/MEASURE) | 세 가지 모두 "카테고리마다 필요한 항목이 다르다"는 같은 성격 |
| 10 | 카테고리 속성 상속 | **상속 + 하위 재지정 우선** (보완) | 상속만 있으면 "상의는 선택, 긴소매만 필수" 같은 경우를 표현할 수 없음. 하위 카테고리에 같은 속성을 다시 지정하면 하위 설정이 우선 |
| 11 | 상품 속성값 다중 선택 | **단일 값으로 시작. 확장 시 선택형 값을 별도 교차 엔티티로 분리** (보완) | 기존 추천안의 "PK에 속성선택값번호 추가"는 그 컬럼이 NULL 허용이라 실체 무결성에 어긋남. 확장할 때는 상품 속성 선택값(상품번호 + 속성번호 + 속성선택값번호)으로 분리 |
| 12 | 재고 | **단품 재고수량 + 변동 이력.** 창고별 재고는 보류 | PB 상품을 무신사 물류센터에서 출고하는 경우는 창고별 재고가 필요할 수 있음 → 주문·배송 회차에서 다시 판단 |
| 13 | 상품 승인 | **검수 후 판매** + 상태 이력 | 입점 판매자 상품을 무신사가 검수하는 흐름. 반려 사유는 상태 이력에 기록 |
| 14 | 후기수·평점·판매량 | **논리 모델에서는 계산.** 물리 단계에서 역정규화 검토 | |
| 15 | 브랜드·판매자 참조 | **상품에 브랜드번호·판매자번호를 각각 FK로 둠** | 참조 대상 테이블과 판매 권한(판매자 브랜드) 검증은 브랜드·판매자 회차에서 설계 |
| 16 | 세트·구성 상품 | **보류** | |
| 17 | 모델 착용 정보 | **보류.** 이미지 유형 MODEL로 사진만 지원 | |
| 18 | 단품코드 유일성 (검토 중 추가) | **(상품번호 + 단품코드)를 대체 식별자로** | 판매자가 직접 정하는 코드라 전체에서 유일하다고 보장할 수 없음. 기존 "단품코드 단독 AK"를 변경 |

## 5. 업무 규칙과 다음 회차로 넘긴 항목

### 키 구조만으로는 보장되지 않는 업무 규칙
3-5의 "키 구조로 보장되지 않는 규칙" 11개에 더해:
- 상품은 사용 중인 표준 카테고리의 최하위에만 연결한다 (2회차 규칙)
- 판매중(ON_SALE) 상품은 대표 이미지(MAIN) 1장 이상, 단품 1개 이상, 카테고리 필수 속성이 모두 입력되어 있어야 한다
- 카테고리를 바꾸면 상품 속성값을 다시 검증한다
- 하위 카테고리에 같은 속성을 다시 지정하면 하위 설정이 우선한다 (확인 10번)

### 다음 회차로 넘긴 항목
- 브랜드·판매자 엔티티와 판매 권한(판매자 브랜드) 검증 → 브랜드·판매자 회차
- 할인 정책, 쿠폰, 즉시할인 → 쿠폰·프로모션 회차
- 단품 재고 이력의 주문 참조, 주문 시점 가격 스냅샷 → 주문 회차
- 창고별 재고, 세트 상품, 모델 착용 정보, 스타일 그룹, 상품 마스터/판매 분리 → 보류
- 후기수·평점·판매량 역정규화 → 물리 모델링
