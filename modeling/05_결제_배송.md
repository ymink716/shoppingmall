# 5회차: 결제·배송 테이블 설계

> 무신사 기반 쇼핑몰 데이터 모델링 실습
> 진행 방식: ① 설계 유형 정리 → ② 테이블 설계 → ③ 컬럼 확인
> 용어는 수업 PPT를 참고합니다. PPT에 없는 실무 용어는 **(PPT 외)** 로 표시합니다.
> DBMS는 미정이므로 컬럼 타입은 도메인으로 표기합니다.

## 목차
0. 결제·배송은 어떤 엔티티인가
1. 결제·배송 설계 유형 (1~21)
2. 추천 조합
3. 테이블 설계 (논리 모델링 절차)
4. 컬럼 확인 포인트와 확정 결과
5. 업무 규칙과 다음 회차로 넘긴 항목

## 0. 결제·배송은 어떤 엔티티인가

- 결제와 배송은 주문(4회차) 다음에 일어나는 **행위**를 기록합니다. 주문이 "무엇을 샀나"라면, 결제는 "어떻게 냈나", 배송은 "어떻게 보냈나"입니다.
- 앞 회차와의 관계
  - 4회차 주문: 주문상태 PENDING → PAID / FAILED는 **결제 결과**로 정해짐. 주문상품 상태 SHIPPING·DELIVERED는 **배송 결과**로 정해짐
  - 4회차에서 넘겨받은 항목: 복합 결제, PG 거래 원장, 가상계좌 입금 대기, 송장, 부분 배송, 배송지 변경 이력, 적립금 배분(4회차 확인 12번) 다시 확인
  - 3회차 상품: 창고별 재고 보류(3회차 확인 12번)를 무신사 물류 출고와 함께 다시 판단
- 이번 회차에서 다루지 않는 것
  - 환불 금액 계산과 결제수단별 환불 순서 → 클레임 회차
  - 적립금 잔액·적립 내역, 무신사머니 충전·잔액 → 등급·적립금 회차, 보류
  - 판매자 엔티티와 판매자 배송 정책 → 브랜드·판매자 회차
- 무신사 관찰
  - 카드, 간편결제(카카오페이, 네이버페이, 토스페이 등), 무신사페이·무신사머니, 무통장입금(가상계좌), 적립금 사용이 가능함 (💭 공개 화면과 업계 관행으로 추론)
  - 무신사 스탠다드 같은 PB와 일부 브랜드는 무신사 물류센터에서 출고하고, 입점 브랜드는 업체가 직접 출고함 (💭 추론)

### 결제·배송 설계의 핵심 질문
1. **결제를 주문과 분리할까? 결제수단마다 다른 속성은?** → 유형 1~4
2. **승인, 취소, 부분취소를 어떻게 기록할까?** → 유형 5~7
3. **환불은 어디에 담을까?** → 유형 8~9
4. **가상계좌 입금 대기는 주문 상태일까 결제 상태일까?** → 유형 10~11
5. **적립금은 할인일까 결제수단일까?** → 유형 12~13
6. **송장을 어디에 둘까? 나눠 보내면?** → 유형 14~16
7. **배송 추적과 배송지 변경을 어떻게 기록할까?** → 유형 17~19
8. **누가, 어디서 출고하나?** → 유형 20~21

### 용어 정리 (이 문서에서)
| 용어 | 뜻 | 예시 |
|---|---|---|
| 청구금액 | 고객이 주문에 대해 치러야 하는 전체 금액 | 상품 97,000 − 할인 8,900 + 배송비 3,000 = 91,100 |
| 결제 | 청구금액 중 **결제수단 하나로 낸 부분** | 카드 87,100 |
| **PG** (PPT 외) | 카드사·은행과 쇼핑몰 사이에서 결제를 대행하는 회사 | 토스페이먼츠, KG이니시스 |
| 결제 거래 | 결제 한 건에 일어난 승인·취소 요청과 응답 한 번 | 카드 87,100 승인, 50,185 부분취소 |
| **망취소** (PPT 외) | PG 응답을 받지 못했을 때 결과를 확인해서 승인됐으면 취소하는 처리 | |
| 배송 | 송장 하나로 나가는 상자 하나 | CJ대한통운 6012-3456-7890 |
| 배송상품 | 배송 상자 안에 든 주문상품과 수량 | 티셔츠 블랙 M × 2 |

### 예시 주문 (4회차와 같은 주문)
```
청구금액 91,100 = 상품 97,000 − 상품쿠폰 5,900 − 장바구니쿠폰 3,000 + 배송비 3,000
결제수단
  적립금       2,000   (4회차 주문상품에 834 + 1,166으로 배분)
  무신사머니   2,000
  카드        87,100   (PG 승인)
────────────────────
합계          91,100   ← 4회차 "결제 금액 89,100"은 적립금을 뺀 실결제금액

배송
  판매자 A (무신사, 무신사 물류센터 출고): 티셔츠 블랙 M × 2
  판매자 B (데님랩, 업체 직접 출고):        데님 연청 30 × 1
```

### 학습 순서
| 단계 | 유형 | 핵심 질문 |
|---|---|---|
| A. 결제 구조 | 1. 주문 결제 컬럼형 → 2. 결제 엔티티 분리형 → 3. 결제수단 슈퍼타입/서브타입형 → 4. PG 응답 원문 저장형 | 결제를 어디에, 몇 개로? |
| B. 결제 상태와 거래 | 5. 결제 상태코드형 → 6. 결제 거래 원장형 → 7. 결제 상태 이력형 | 승인·취소를 어떻게 남길까? |
| C. 환불 | 8. 결제 환불 컬럼형 → 9. 환불 엔티티 분리형 | 환불은 어디에? |
| D. 입금 대기 | 10. 주문 상태 확장형 → 11. 결제 상태 + 재고 선점형 | 가상계좌 입금 전 상태는? |
| E. 적립금·선불 수단 | 12. 할인 처리형 → 13. 결제수단 처리형 | 적립금은 할인인가 결제인가? |
| F. 배송 구조 | 14. 판매자 주문 송장 컬럼형 → 15. 주문상품 송장 컬럼형 → 16. 배송 + 배송상품 분리형 | 송장을 어디에? |
| G. 배송 추적 | 17. 배송 상태코드형 → 18. 배송 추적 이력형 → 19. 배송지 변경 이력형 | 배송 과정과 주소 변경을 어떻게 남길까? |
| H. 출고 | 20. 출고 주체 구분형 → 21. 출고 창고 엔티티형 | 누가, 어디서 보내나? |

## A. 결제 구조

### 1. 주문 결제 컬럼형
**정의**: 주문(4회차 `orders`)에 결제수단, 결제금액, 카드사, 승인번호 컬럼을 둡니다.

| 주문번호 | 결제수단 | 결제금액 | 카드사 | 승인번호 | 가상계좌번호 |
|---|---|---|---|---|---|
| 81234 | CARD | 87,100 | 신한 | 30012345 | NULL |

- **장점**: 단순합니다. 주문 한 건에 결제 한 건인 곳에서는 충분합니다.
- **단점**
  - 예시 주문처럼 **카드 + 무신사머니 + 적립금**을 함께 쓰면 담을 수 없습니다 (결제수단1, 결제수단2…는 반복 그룹).
  - 카드 컬럼과 가상계좌 컬럼이 서로 NULL을 만듭니다.
- **무신사라면**: ❌

---

### 2. 결제 엔티티 분리형
**정의**: 주문 1 : M 결제. 결제수단 하나당 결제 한 행입니다.
```
주문 1 ──< M 결제(결제수단코드, 결제금액, 결제상태)
```
| 결제번호 | 주문번호 | 결제수단 | 결제금액 | 상태 |
|---|---|---|---|---|
| 9001 | 81234 | POINT | 2,000 | APPROVED |
| 9002 | 81234 | MONEY | 2,000 | APPROVED |
| 9003 | 81234 | CARD | 87,100 | APPROVED |

- **장점**: 복합 결제가 자연스럽습니다. 결제 실패 후 다른 수단으로 재시도한 기록도 남습니다 (같은 주문에 FAILED 행 + APPROVED 행).
- **단점**: 카드사, 할부, 가상계좌 은행처럼 **수단별로만 쓰는 속성**을 어디에 둘지 남습니다 → 3번
- **무신사라면**: ✅

---

### 3. 결제수단 슈퍼타입/서브타입형 (PPT: 슈퍼타입/서브타입 관계)
**정의**: 결제(슈퍼타입) 아래에 카드, 가상계좌, 간편결제 서브타입을 1:1로 둡니다.
```
결제 ──┬── 카드 결제   (카드사, 마스킹 카드번호, 할부개월, 승인번호)
       ├── 가상계좌    (은행, 계좌번호, 입금기한, 입금일시)
       └── 간편결제    (간편결제사, 내부 결제수단)
       (무신사머니, 적립금은 추가 속성이 없어 서브타입 없음)
```
- PPT 물리 모델링의 **상호배타적 관계**에 해당합니다. 결제 한 건은 서브타입 중 **하나에만** 대응합니다.
- 물리 테이블 방식 (PPT: 슈퍼타입 기준 / 서브타입 기준 / 슈퍼타입·서브타입 테이블)
  - 슈퍼타입 기준(한 테이블): 서브타입 컬럼이 모두 결제에 들어가고 NULL이 많아짐
  - 서브타입 기준: 결제 테이블이 수단별로 나뉘어 "주문의 결제 전체"를 볼 때 UNION이 필요
  - **슈퍼타입·서브타입 테이블**: 공통은 결제에, 수단별 속성은 서브타입에 → 이 실습에서 사용
- **무신사라면**: ✅

---

### 4. PG 응답 원문 저장형 (PPT 외)
**정의**: PG가 돌려준 응답(JSON)을 통째로 한 컬럼에 저장합니다.
- **장점**: PG사별로 다른 응답 항목을 모두 보존합니다. 분쟁 때 근거가 됩니다.
- **단점**: 원문 안의 값은 검색·제약을 걸 수 없습니다 (1정규형 관점에서 복합 값). 카드번호 같은 민감정보가 섞일 수 있습니다.
- **무신사라면**: 보류. 논리 모델에는 필요한 값만 컬럼으로 두고, 원문은 물리·운영 단계의 로그로 다룸

## B. 결제 상태와 거래

### 5. 결제 상태코드형
**정의**: 결제에 현재 상태(READY / WAITING_DEPOSIT / APPROVED / FAILED / CANCELED)를 둡니다.
- **장점**: "승인된 결제"를 바로 찾을 수 있습니다.
- **단점**: 상태만으로는 **얼마가 언제 취소됐는지** 알 수 없습니다. 카드 87,100 중 50,185만 취소한 부분취소를 표현하지 못합니다.
- **무신사라면**: ✅ 6번과 함께 사용

---

### 6. 결제 거래 원장형 (PPT: 이력 관리, 점 이력)
**정의**: 결제 한 건에 일어난 **요청·응답을 한 번에 한 행씩** 쌓습니다. 수정하거나 지우지 않습니다.

| 거래번호 | 결제번호 | 거래유형 | 금액 | 결과 | PG 거래번호 |
|---|---|---|---|---|---|
| 1 | 9003 (카드) | APPROVE | 87,100 | SUCCESS | T-001 |
| 2 | 9003 | CANCEL | 50,185 | SUCCESS | T-002 |
| 3 | 9003 | CANCEL | 3,000 | SUCCESS | T-003 |

- 취소누계(53,185), 잔액(33,915), 부분취소 여부는 거래를 합산한 **파생 값**입니다.
- **장점**: 정산과 PG 대사(PG사 거래 내역과 우리 기록을 맞춰 보는 일)의 근거가 됩니다. 실패한 시도도 남습니다.
- **무신사라면**: ✅

---

### 7. 결제 상태 이력형
**정의**: 결제 상태가 바뀔 때마다 이력 행을 남깁니다 (고객·상품·주문상품 상태 이력과 같은 패턴).
- **단점**: 결제는 상태 변경이 곧 PG 거래 결과입니다. 6번 거래 원장과 **같은 사건을 두 번 기록**하게 됩니다.
- **무신사라면**: ❌ 6번 거래 원장이 상태 이력 역할을 함

## C. 환불

### 8. 결제 환불 컬럼형
**정의**: 결제에 환불금액, 환불일시 컬럼을 둡니다.
- **단점**: 환불이 두 번 이상이면 담을 수 없습니다. 6번 거래 원장의 CANCEL 거래와 중복됩니다.
- **무신사라면**: ❌

### 9. 환불 엔티티 분리형 — 클레임 회차
**정의**: 환불(클레임 1건의 환불 요청) + 환불 결제수단 배분(어느 결제에서 얼마를 돌려줄지). 실제 돈이 오간 기록은 6번 거래 원장의 CANCEL 거래입니다.
- **이번 회차에 주는 영향**: 거래 원장에 "어떤 환불 때문에 생긴 취소인지"를 가리킬 컬럼이 나중에 필요합니다. 클레임 회차에서 추가합니다.

---

## D. 입금 대기 (가상계좌)

### 10. 주문 상태 확장형
**정의**: 4회차 주문상태코드에 WAITING_DEPOSIT(입금대기)를 추가합니다.
- **단점**: 복합 결제에서 "적립금은 승인, 가상계좌는 입금대기"처럼 **결제마다 상태가 다릅니다.** 주문 상태 하나로는 부족하고, 결제 쪽 정보와 중복됩니다.
- **무신사라면**: ❌

### 11. 결제 상태 + 재고 선점형
**정의**: 입금 대기는 **결제 상태**(WAITING_DEPOSIT)로만 두고, 주문은 PENDING을 유지합니다. 가상계좌를 발급할 때 재고를 미리 차감(선점)하고, 입금 기한이 지나면 복구합니다.

| 시점 | 결제 상태 | 주문 상태 | 재고 |
|---|---|---|---|
| 가상계좌 발급 | WAITING_DEPOSIT | PENDING | 차감 (재고 이력 ORDER) |
| 입금 확인 | APPROVED | PAID | — |
| 입금 기한 만료 | FAILED | FAILED | 복구 (재고 이력 CANCEL) |

- 4회차 확인 17번 "결제 완료 시 차감"의 **예외**입니다. 가상계좌는 입금까지 며칠이 걸릴 수 있어서, 차감하지 않으면 입금하고 나서 품절을 알게 됩니다.
- **무신사라면**: ✅

---

## E. 적립금·선불 수단

### 12. 할인 처리형
**정의**: 적립금 사용액을 할인으로 보고 청구금액에서 미리 뺍니다. 결제 엔티티에는 나타나지 않습니다.
- **단점**: "이 주문을 무엇으로 냈나"를 보려면 결제와 주문상품(적립금 배분)을 따로 봐야 합니다. 환불 때 적립금을 돌려줄지 현금으로 돌려줄지 같은 **결제수단별 환불 규칙**을 한 곳에서 다룰 수 없습니다.

### 13. 결제수단 처리형
**정의**: 적립금, 무신사머니도 **결제 한 행**(결제수단 POINT, MONEY)으로 둡니다. 주문상품의 적립금 배분(4회차)은 그대로 둡니다.
- **장점**: 결제 합계 = 청구금액으로 맞아떨어집니다. 결제수단별 환불 규칙을 한 곳에서 다룹니다.
- **중복 관리**: 결제(POINT)의 금액 = 주문상품 적립금사용금액의 합. 결제 행은 "얼마를 냈나", 주문상품 배분은 "어느 상품에 썼나"라서 둘 다 필요하고, 합계 일치는 업무 규칙으로 관리합니다.
- **무신사라면**: ✅ 4회차 확인 12번("적립금은 결제수단 성격")과 같은 결론

## F. 배송 구조

### 14. 판매자 주문 송장 컬럼형
**정의**: 4회차 판매자 주문에 택배사, 송장번호 컬럼을 둡니다.
- **장점**: 판매자 주문 = 상자 하나인 경우 가장 단순합니다.
- **단점**: 판매자 B가 데님 2벌을 **상자 두 개**로 보내거나, 재고가 늦게 들어와 일부만 먼저 보내면 송장이 2개가 됩니다 (반복 그룹).
- **무신사라면**: ❌

### 15. 주문상품 송장 컬럼형
**정의**: 주문상품에 택배사, 송장번호를 둡니다.
- **단점**: 한 상자에 든 주문상품마다 같은 송장번호가 반복됩니다 (택배사·배송상태가 송장번호에 종속 → 3정규형 위반). 티셔츠 2개를 1개씩 나눠 보내는 경우는 담을 수 없습니다.
- **무신사라면**: ❌

### 16. 배송 + 배송상품 분리형
**정의**: 배송(송장 하나) 1 : M 배송상품(주문상품 + 수량).
```
판매자 주문 1 ──< M 배송 1 ──< M 배송상품 >── 1 주문상품
```
| 배송번호 | 판매자 주문 | 택배사 | 송장번호 | 배송상품 |
|---|---|---|---|---|
| 7001 | (81234, A) | CJ대한통운 | 6012-3456-7890 | 티셔츠 블랙 M × 2 |
| 7002 | (81234, B) | 롯데택배 | 2345-6789-0123 | 데님 연청 30 × 1 |

- **장점**: 부분 배송, 분할 포장, 수량 일부 출고 모두 가능합니다. 교환 재배송·반품 회수도 같은 구조(배송유형만 다름)로 확장됩니다.
- **무신사라면**: ✅

## G. 배송 추적

### 17. 배송 상태코드형
**정의**: 배송에 현재 상태(READY 출고준비 / SHIPPED 출고완료 / IN_TRANSIT 배송중 / DELIVERED 배송완료)를 둡니다.
- **무신사라면**: ✅ 18번과 함께 (3회차 단품 재고수량 + 재고 이력과 같은 "현재값 + 이력" 패턴)

### 18. 배송 추적 이력형 (점 이력)
**정의**: 택배사가 알려 주는 이벤트(집화, 간선 상차, 배송 출발, 배송 완료)를 쌓습니다.
- 택배사마다 상태 이름이 달라서, **표준 추적상태코드**로 바꿔 저장하고 원본 상태명도 함께 둡니다.
- **업무 일시와 시스템 일시**: 이벤트일시(택배사 기록 시각)와 등록일시(우리가 받은 시각)는 몇 시간씩 차이 날 수 있습니다. 1회차 확인 2번 "업무 일시와 시스템 일시를 구분"이 실제로 필요한 사례입니다.
- **무신사라면**: ✅

### 19. 배송지 변경 이력형 (PPT: 이력 관리, 점 이력, 최종 데이터 미포함)
**정의**: 배송 시작 전에 고객이 주소를 바꾸면, 주문의 배송지 컬럼(4회차)을 고치고 **변경 전 값**을 이력에 남깁니다.

| 방식 (PPT 이력 관리) | 내용 | 선택 |
|---|---|---|
| 최종 데이터 포함 | 이력에 현재 주소까지 행으로 둠 | 현재 주소가 주문과 이력 두 곳에 생김 |
| **최종 데이터 미포함** | 이력에는 바뀌기 전 주소만, 현재 주소는 주문에만 | ✅ |

- **무신사라면**: ✅ 주소 변경은 드물고, 현재 주소는 주문에서만 읽으면 됨

### 3-2. 엔티티 정의
| 엔티티 | 정의 | 발생 규칙 |
|---|---|---|
| 결제 | 주문 청구금액 중 결제수단 하나로 내기로 한 금액 | 결제 요청 시 결제수단마다 1행 (READY). 실패 후 재시도하면 새 행 |
| 카드·가상계좌·간편결제 | 결제수단별 추가 정보 | 결제수단코드에 맞는 서브타입 1개 |
| 결제 거래 | 결제 한 건에 대해 PG 또는 내부 원장에 보낸 요청과 그 응답 | 요청할 때마다 1행. 수정·삭제하지 않음 |
| 배송 | 판매자가 송장 하나로 보내는 상자 | 판매자가 출고를 준비할 때 생성 (READY), 송장 등록 후 SHIPPED |

| 배송 추적 이력 | 택배사가 보낸 배송 이벤트 | 택배사 이벤트를 받을 때마다 |
| 주문 배송지 변경 이력 | 주문 배송지가 바뀌기 전 값 | 배송지를 바꿀 때마다 |

### 3-3. 관계 도출 및 정의
| 관계 | 관계 유형 | 관계수 | 선택성 | 식별자 상속 | 비고 |
|---|---|---|---|---|---|
| 주문 → 결제 | 기본 | 1:M | 선택-필수 | 비식별 | 복합 결제, 재시도 |
| 결제 → 카드 결제 | 슈퍼타입/서브타입 | 1:1 | 선택-필수 | **식별** | 상호배타 |
| 결제 → 가상계좌 결제 | 〃 | 1:1 | 선택-필수 | **식별** | 〃 |
| 결제 → 간편결제 | 〃 | 1:1 | 선택-필수 | **식별** | 〃 |
| 결제 → 결제 거래 | 기본 | 1:M | 선택-필수 | 비식별 | |
| 판매자 주문 → 배송 | 기본 | 1:M | 선택-필수 | 비식별 | FK = (주문번호, 판매자번호) |
| 배송 ↔ 주문상품 | M:N → 배송상품 | 1:M, 1:M | | **식별** | PK = 배송번호 + 주문상품번호 |
| 배송 → 배송 추적 이력 | 기본 | 1:M | 선택-필수 | 비식별 | |
| 주문 → 주문 배송지 변경 이력 | 기본 | 1:M | 선택-필수 | 비식별 | |

**관계도**
```
[주문] ─< [결제] ─┬─ [카드 결제]       (상호배타 1:1)
  │        │      ├─ [가상계좌 결제]
  │        │      └─ [간편결제]
  │        └─< [결제 거래]
  ├─< [주문 배송지 변경 이력]
  └─< [판매자 주문] ─< [배송] ─< [배송상품] >─ [주문상품]
                        └─< [배송 추적 이력]
```

**식별자 선택 포인트**
- **서브타입 = 식별 관계 (결제번호가 PK이자 FK)**: 1:1 관계라 부모 키를 그대로 씁니다. 1회차 고객 탈퇴·체형정보와 같은 방식입니다.
- **배송 = 인조 식별자**: 판매자 주문으로 상속하면 (주문번호 + 판매자번호 + 순번)이 되고, 배송상품·추적 이력·(클레임 회차의) 회수 배송이 모두 길어집니다. 송장번호는 등록 전에는 없고 택배사마다 겹칠 수 있어서 주 식별자가 될 수 없습니다 (식별자의 **존재성** 위반). 게다가 택배사는 송장번호를 일정 기간 후 재사용하므로 대체 식별자로도 두지 않고 검색용으로만 둡니다 (**유일성** 위반, 확인 14번).
- **배송상품 = 식별 관계 (배송번호 + 주문상품번호)**: "한 상자에 같은 주문상품은 한 줄"을 키가 보장합니다.
- 4회차와 같은 교훈: 배송상품의 주문상품이 **그 배송의 판매자 주문에 속하는지**는 키로 보장되지 않습니다 (주문상품이 인조 식별자라서). 업무 규칙으로 관리합니다.

### 3-5. 데이터 모델 검토

**예시 데이터로 확인: 예시 주문**
| 엔티티 | 인스턴스 수 | 내용 |
|---|---|---|
| 결제 | 3 | POINT 2,000 / MONEY 2,000 / CARD 87,100 → 합계 91,100 = 청구금액 |
| 카드 결제 | 1 | 신한, 일시불 |
| 결제 거래 | 3 | 세 결제의 APPROVE |
| 배송 | 2 | 7001(판매자 A, MUSINSA 출고), 7002(판매자 B, SELLER 출고) |
| 배송상품 | 2 | 7001: 티셔츠 × 2 / 7002: 데님 × 1 |
| 배송 추적 이력 | 예: 8 | 배송마다 집화 → 이동중 → 배송출발 → 배송완료 |

**금액 검산**
| 항목 | 금액 |
|---|---|
| 상품금액 (4회차) | 97,000 |
| 할인 합계 (상품쿠폰 5,900 + 장바구니쿠폰 3,000) | −8,900 |
| 배송비 (판매자 주문 B) | +3,000 |
| **청구금액** | **91,100** |
| 결제 합계 (2,000 + 2,000 + 87,100) | 91,100 ✅ |
| 결제(POINT) 2,000 = 주문상품 적립금사용금액 834 + 1,166 | ✅ |

**제약 조건 (PPT 4가지)**
| 제약 | 적용 |
|---|---|
| 키 제약조건 | 모든 PK. 대체 식별자(조건부): (PG사코드 + PG결제키) — 값이 있을 때만 유일 |
| 실체 무결성 | PK와 필수 속성 NOT NULL |
| 영역 무결성 | 금액 > 0, 할부개월수 ≥ 0, 수량 ≥ 1, 상태·유형 코드값 |
| 참조 무결성 | 모든 FK. 배송 → 판매자 주문은 (주문번호, 판매자번호) 복합 FK |

**키 구조로 보장되지 않는 규칙 (업무 규칙)**
| 규칙 | 이유 |
|---|---|
| 결제수단코드가 CARD이면 카드 결제, VBANK이면 가상계좌 결제, EASY_PAY이면 간편결제가 **정확히 하나** 있고, 나머지 서브타입은 없다 | 상호배타적 관계는 FK로 표현 불가 |
| 주문의 APPROVED 결제 중 **클레임번호가 없는** 결제 합계 = 청구금액이 되면 주문을 PAID로 바꾼다 | 여러 행 합계 (클레임 비용 추가 결제는 제외, 6회차에서 수정) |
| 결제(POINT) 금액 = 그 주문 주문상품의 적립금사용금액 합계 | 결제와 4회차 배분의 중복 |
| 결제의 취소 거래(SUCCESS) 합계 ≤ 결제금액 | 여러 행 합계 |
| 복합 결제 중 하나라도 실패하면, 이미 승인된 다른 결제를 모두 취소하고 주문을 FAILED로 둔다 | 결제 사이의 원자성 |
| PG 거래가 UNKNOWN이면 PG 결과 조회로 확정하고, 승인돼 있었는데 주문이 실패 처리됐다면 취소(망취소)한다 | 응답 누락 대비 |
| 가상계좌 발급 시 재고를 차감하고, 입금기한까지 입금되지 않으면 재고를 복구한다 | 4회차 확인 17번의 예외 |
| 배송상품의 주문상품은 그 배송의 판매자 주문에 속해야 한다 | 주문상품이 인조 식별자라서 |
| 주문상품별 ORDER 배송의 배송상품 수량 합계 ≤ 주문상품 수량 − 완료된 취소(CANCEL) 클레임 수량 | 여러 행 합계 (취소 수량은 6회차 클레임상품) |
| 주문상품의 남은 수량이 모두 출고되면 SHIPPING, 모두 배송완료되면 DELIVERED | 4회차 확인 10번 "남은 수량 기준"과 같은 원칙 |
| 배송지는 그 주문의 모든 배송이 READY(또는 배송 없음)일 때만 바꿀 수 있다 | 출고 후 주소 변경 불가 |
| (택배사코드 + 송장번호)는 배송완료 전 배송 사이에서 유일하다 | 택배사가 송장번호를 재사용해서 전체 기간 유일은 보장 불가 (확인 14번) |
| 주문당 READY·WAITING_DEPOSIT·APPROVED 상태 결제는 결제수단별 1개다 (클레임번호가 없는 주문 결제 기준) | 재시도로 생긴 FAILED 행 때문에 키로 막을 수 없음 (확인 21번) |

> 📌 이번 회차의 학습 포인트: **현재 상태와 이력을 둘 다 둘 때, 이력이 "사건 기록" 자체라면 별도 상태 이력은 중복입니다.** 결제 거래 원장이 그 예입니다. 반대로 배송은 우리가 정하는 상태(출고준비·출고완료)와 택배사가 알려 주는 사건(추적 이력)이 달라서 둘 다 필요합니다.

## 4. 컬럼 확인 포인트와 확정 결과

20개 추천안을 다시 검토해서 19개는 그대로 확정했고, 1개(14번)는 보완해서 확정했습니다. 검토하면서 새로 발견한 1개(21번)도 추가로 확정했습니다.

| # | 쟁점 | 확정 | 검토 의견 |
|---|---|---|---|
| 1 | 결제 구조 | **결제 분리** (주문 1:M) | 복합 결제와 실패 후 재시도 기록이 모두 자연스러움 |
| 2 | 결제수단별 속성 | **슈퍼타입·서브타입 테이블** (카드, 가상계좌, 간편결제) | 한 테이블이면 수단별 컬럼이 서로 NULL을 만들고, 서브타입별 테이블이면 "주문의 결제 전체"를 볼 때 UNION 필요. 무신사머니·적립금은 추가 속성이 없어 서브타입 없음 |
| 3 | PG 응답 원문 | **보류** | 복합 값이고 민감정보가 섞일 수 있음. 물리·운영 단계 로그로 |
| 4 | 결제 기록 방식 | **상태 + 거래 원장** | 상태 이력은 원장과 같은 사건을 두 번 기록 |
| 5 | 부분취소 표현 | **거래 합계로 계산.** 상태는 APPROVED 유지, 잔액 0이면 CANCELED | 부분취소를 상태로 두면 두 번째 부분취소, 전액취소와의 경계가 모호해짐 |
| 6 | 취소누계금액 | **계산** (파생 속성) | 원장 합계와 어긋날 위험을 없앰 |
| 7 | PG 응답 누락 | **UNKNOWN 저장 후 결과 조회로 확정** | 원장의 "수정하지 않는다" 원칙의 유일한 예외. 확정 전 값(UNKNOWN)은 결과가 아니라 "아직 모름"이라 수정해도 사건 기록이 사라지지 않음 |
| 8 | 적립금 처리 | **결제수단(POINT 결제 행)** + 4회차 주문상품 배분 유지 | 결제 합계 = 청구금액. 4회차 확인 12번을 이것으로 확정 |
| 9 | 무신사머니 | **결제수단(MONEY)으로 기록.** 충전·잔액 원장은 보류 | |
| 10 | 입금 대기 위치 | **결제 상태 WAITING_DEPOSIT.** 주문은 PENDING 유지 | 복합 결제에서 결제마다 상태가 다를 수 있음 |
| 11 | 가상계좌 재고 차감 | **발급 시 선점, 기한 만료 시 복구** | 4회차 확인 17번의 예외. 입금 후 품절을 막음 |
| 12 | 배송 구조 | **배송 + 배송상품** | 분할 포장, 부분 출고, 교환·반품 배송까지 같은 구조 |
| 13 | 수량 일부 출고 | **허용** | 4회차 "남은 수량 기준" 원칙과 맞물려 주문상품 상태가 정해짐 |

## 5. 업무 규칙과 다음 회차로 넘긴 항목

### 키 구조만으로는 보장되지 않는 업무 규칙
3-5의 "키 구조로 보장되지 않는 규칙" 13개에 더해:
- 결제 거래는 수정·삭제하지 않는다. 단, UNKNOWN 결과를 확정할 때만 결과코드·응답일시를 채운다
- 배송완료일시로부터 일정 기간이 지나면 주문상품을 자동 구매확정한다 (기간은 운영 정책)
- 결제 승인 직전 재고 재확인(4회차 확인 17번)은 가상계좌에서는 발급 시점에 한다

### 다음 회차로 넘긴 항목
- 환불, 결제수단별 환불 순서, 거래 원장의 환불 참조, 교환 재배송·반품 회수 배송 → 클레임 회차 ✅ 6회차에서 반영 (결제·결제 거래·배송에 클레임번호 추가)
- 적립금 잔액·사용 내역 원장 → 등급·적립금 회차
- 무신사머니 충전·잔액 원장 → 보류 (선불 전자지급수단)
- 판매자 배송 정책, 택배사 계약 → 브랜드·판매자 회차
- 출고 창고 엔티티, 창고별 재고 → 보류 (3회차 확인 12번과 함께)
- PG 응답 원문 보관, 카드 정보 보안 기준 → 물리·운영 단계
